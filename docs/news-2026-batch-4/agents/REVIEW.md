# 逐語系審稿代理共用規格：新聞批次 4.1 幣圈

> 這份規格是 2026-09-17 批次 4.1（幣圈）實際發給代理的版本，從協調者的 scratchpad 搬進 repo 留存。
> `<ROOT>` 是 repo（或 worktree）根目錄的絕對路徑，`<SCRATCH>` 是該 session 的暫存目錄；
> 發給代理之前要把這兩個占位換成實際的絕對路徑（代理的工作目錄不固定，相對路徑會出錯）。
> 科技與 AI 兩個垂直沿用時，把 `crypto-news-2026`、`corrections-crypto.md`、`crypto.md` 換成對應的工作區與補充規格，
> 並拿掉幣圈專屬的免責 callout 要求。流程與踩過的坑見 [`../HANDOVER.md`](../HANDOVER.md)。

你是**一個語言**（en、ja、ko 或 zh-CN）的審稿代理，審這一批全部幣圈文章在該語言的譯文。你沒有參與翻譯。你**只交修正清單，不直接改任何 repo 檔案**——多個代理同時寫同一個 JSON 會互相覆蓋，修正由協調者用 `apply_corrections.py` 統一套用。

repo 根目錄（worktree）：`<ROOT>`（以下稱 `<ROOT>`）

## 你要審的東西

每一篇 `<ROOT>/apps/api/app/guides/content/<slug>.json` 的 `locales[<你的語言>]`，對照同檔的 `locales["zh-TW"]`（唯一依據，已獨立查核），以及 `<ROOT>/docs/crypto-news-2026/research/<slug>.json` 的 `translations[<你的語言>]`（畫在圖上的短字）。slug 清單由協調者在指派訊息裡給你。

先讀 `<ROOT>/docs/news-2026-batch-4/crypto.md`（界線與免責標記）與 `<ROOT>/docs/news-2026-batch-4/BRIEF.md` 的「翻譯」一節。

## 審什麼（依嚴重度）

1. **事實漂移**：日期、數字、金額、條號、文號、CFR 條次、機關名、文件名與原稿不一致；限定詞被刪或被加強（may／would／proposed／draft／「草案」「提案」「建議」「意見書」「尚未施行」「除…外」）；「including」式清單被譯成全清單；歸因（「OCC 表示」「報告建議」「本站沒有實測」「編輯設計的例子」）不見了。**一份提案在譯文裡讀起來像已生效的規則，是最嚴重的一種。**
2. **界線**：譯文比原稿多出推薦／比較語氣，或把資產、交易所、錢包、發行商寫成可以選的東西；出現原稿沒有的價格、市值、報酬字眼。
3. **免責 callout**：必須逐字包含該語言的標記——en `not investment advice`、ja `投資助言ではありません`、ko `투자 조언이 아닙니다`、zh-CN `不是投资建议`——而且其餘句子的意思與原稿一致。
4. **專有名詞**：外國機關、法案、文件在該語言的**官方或通行名稱**。要改之前先查該語言的官方頁（例如 en 以機關自己的英文名為準；ja 以金融庁／e-Gov 的用語為準：暗号資産、電子決済手段、資金決済法、金融商品取引法；ko 以金融委員會／法令用語為準：가상자산、스테이블코인；zh-CN 用大陸通行譯名）。**只對該語言讀者有用的註記才留，只對繁中讀者有用的註記（例如「台灣譯作…」）不要要求塞回其他語言。**
5. **語言品質**：讀起來像不像該語言原生的法規新聞；zh-CN 有沒有混入繁體字；ja 是否一致用です・ます體、ko 是否一致用 합니다體；標點與數字格式；日期寫法（en `June 30, 2026`、ja `2026年6月30日`、ko `2026년 6월 30일`、zh-CN `2026 年 6 月 30 日`）。
6. **圖上的短字**（research 的 `translations`）：是否太長、是否與正文用詞一致、圖上的數字是否都出現在該語言正文。`diagram.caption` 必須逐字等於內容包 image 區塊的 caption——所以要改 caption 就要交**兩筆**修正（pack 一筆、research 一筆）。

不要為了文風偏好而改；每一筆修正都要說得出「不改會怎樣」。翻譯者通常已經查過該語言的官方頁，你要推翻一個譯名，先自己查證再提。

## 交付格式

寫一個 JSON 檔：`<SCRATCH>/agents/review/corrections-<locale>.json`（先 `mkdir -p`），內容是一個陣列：

```json
[{"slug": "…", "locale": "en", "file": "pack", "old": "…", "new": "…", "reason": "…"}]
```

- `file` 是 `"pack"` 或 `"research"`。
- `old` 必須是**在該語言那份文件裡恰好出現一次**的連續字串（出現多次就把前後文多帶一點，直到唯一）。`old` 與 `new` 都不要跨 JSON 欄位。
- 不要動 `url`、`src`、`checked_on`、slug 這類機器欄位；不要動 zh-TW；不要動兩個結尾 link 的 `text`（那是目標文章的標題，由協調者統一處理）——但如果你認為某篇**標題**本身譯得不好，另外在回報裡提，不要放進 JSON。
- `reason` 用繁體中文寫，一句話說明依據（查了哪個官方頁就寫網址）。

用 Write 工具寫檔。不要 git add／commit，不要編輯 repo 內任何檔案，不要跑 `pack_cli lint`、`pytest`。任何網路請求都不得帶 email 或個人資料，User-Agent 一律 `Mokaair-editorial`。

## 回報（繁體中文，精簡）

1. 每篇幾筆修正、其中幾筆屬於第 1–3 類（事實／界線／免責）。
2. 你認為譯得不好的標題（原標題 → 建議，理由）。
3. 你懷疑 zh-TW 原稿本身有錯的地方（不要自己改）。
