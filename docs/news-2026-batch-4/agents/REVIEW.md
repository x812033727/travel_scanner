> `<ROOT>` 是 repo（或 worktree）根目錄的絕對路徑，`<SCRATCH>` 是該 session 的暫存目錄；
> 發給代理之前要把這兩個占位換成實際的絕對路徑（代理的工作目錄不固定，相對路徑會出錯）。
> 與第一版的差別：代理改讀 [`../review_dumps.py`](../review_dumps.py) 產生的**逐段對照檔**而不是內容包 JSON；

> 拿掉幣圈專屬的免責 callout 要求，並重寫統一用語表。流程與踩過的坑見 [`../HANDOVER.md`](../HANDOVER.md)。
>
> **表裡有兩格在收件後被推翻，沿用前先改**：ko 的「本站沒有實測」不要寫「직접 검증하지 않았고」（會被讀成「沒有查證」），
> 定案是「직접 시험해 보지 않았고」；ko 另加 no-action letter＝「비조치의견서」、免責句的「當期公告」＝「그때그때의 공고」，
> ja 的「當期公告」＝「その時点の」。

你是**一個語言**（en、ja、ko 或 zh-CN）的審稿代理，審協調者指派給你的那一組幣圈文章在該語言的譯文。你沒有參與翻譯。
你**只交修正清單，不直接改任何 repo 檔案**——多個代理同時寫同一個 JSON 會互相覆蓋，修正由協調者用 `apply_corrections.py` 統一套用。

- 暫存目錄：`<SCRATCH>`（以下稱 SCRATCH）

## 你要讀的東西（只讀這些就夠，不要去讀 BRIEF.md、HANDOVER.md 或內容包 JSON 本體）

1. `ROOT\docs\news-2026-batch-4\crypto.md`——這個垂直的界線（只寫法規、技術與產業運作，不碰行情）與免責標記。短，讀一次。
2. 每一篇的**逐段對照檔**：`SCRATCH\agents\review\src\<slug>.<你的語言>.txt`。
   每一格是一組 `[n] 位置`／`ZH: 繁中原稿`／`<語言>: 譯文`，依閱讀順序排列；檔尾附兩個結尾連結（唯讀）與畫在圖上的短字（research 的 `translations`）。
   **繁中原稿（ZH）是唯一依據**，已經過獨立查核，不要動它。對照檔裡的字串就是內容包 JSON 解析後的值，`old` 直接從對照檔複製即可。
3. 需要看來源原文時（例如確認某個機關或文件的官方英文／日文名稱），研究紀錄在 `ROOT\docs\crypto-news-2026\research\<slug>.json`，
   裡面 `verified_facts` 的 `verbatim_quote` 是來源原文。檔案大，**用 Grep 找關鍵字，不要整份讀**。

## 審什麼（依嚴重度）

1. **事實漂移**：日期、數字、金額、條號、文號、CFR 條次、機關名、文件名與原稿不一致；限定詞被刪或被加強
   （may／would／proposed／draft／「草案」「提案」「擬」「建議」「意見書」「尚未施行」「除…外」「一般」「在適當時」）；
   「including」式清單被譯成全清單；歸因（「OCC 表示」「報告建議」「草案說」「本站沒有實測」「編輯設計的例子」）不見了。
   **一份提案在譯文裡讀起來像已生效的規則，是最嚴重的一種。** 逐句對，不要抽查。
2. **界線**：譯文比原稿多出推薦／比較語氣，或把資產、交易所、錢包、發行商寫成可以選的東西；出現原稿沒有的價格、市值、報酬字眼。
3. **免責 callout**：必須逐字包含該語言的標記——en `not investment advice`、ja `投資助言ではありません`、ko `투자 조언이 아닙니다`、zh-CN `不是投资建议`——而且其餘句子的意思與原稿一致。
4. **專有名詞**：外國機關、法案、文件在該語言的**官方或通行名稱**。要改之前先查該語言的官方頁
   （en 以機關自己的英文名為準；ja 以金融庁／e-Gov 的用語為準：暗号資産、電子決済手段、資金決済法、金融商品取引法；
   ko 以金融委員會／法令用語為準：가상자산、스테이블코인；zh-CN 用大陸通行譯名）。
   **只對該語言讀者有用的註記才留；只對繁中讀者有用的註記（例如「台灣譯作…」）不要要求塞回其他語言。**
   翻譯者通常已經查過該語言的官方頁，你要推翻一個譯名，先自己查證再提，並在 reason 寫出你查的網址。
5. **跨篇一致**：同一個機關、法律、制度在你這一組的幾篇裡（以及下面「全批統一用語」表）寫法要一致。
6. **語言品質**：讀起來像不像該語言原生的法規新聞；zh-CN 有沒有混入繁體字或台灣用語；ja 是否一致用です・ます體、ko 是否一致用 합니다體；
   標點與數字格式；日期寫法（en `June 30, 2026`、ja `2026年6月30日`、ko `2026년 6월 30일`、zh-CN `2026 年 6 月 30 日`）。
7. **圖上的短字**（對照檔檔尾的 ARTWORK TEXT）：是否太長（en 小標 ≤ 18 字元、說明 ≤ 30 字元；ja／ko／zh-CN 小標 ≤ 10 字、說明 ≤ 17 字）、
   是否與正文用詞一致、圖上的數字是否都出現在該語言正文。

不要為了文風偏好而改；每一筆修正都要說得出「不改會怎樣」。一篇 0 筆修正是可以接受的結果，不要湊數。

## 交付格式

寫一個 JSON 檔到協調者在指派訊息裡給你的路徑（`SCRATCH\agents\review\corrections-<語言>-<組別>.json`），內容是一個陣列：

```json
[{"slug": "…", "locale": "en", "file": "pack", "old": "…", "new": "…", "reason": "…"}]
```

- `file` 是 `"pack"`（對照檔上半的每一格）或 `"research"`（檔尾 ARTWORK TEXT 的短字）。
- `old` 必須是**在該語言那份文件裡恰好出現一次**的連續字串：同一句話常常在摘要、正文、FAQ 各出現一次，
  所以 `old` 要多帶前後文直到唯一；交付前請自己用 Grep 在對照檔裡確認它只出現在一格裡（同一格裡也只能出現一次）。
  `old` 與 `new` 都不要跨格。要改三個地方就交三筆。
- image 區塊的 caption（位置名是 `blockN.image.caption`）在 research 的 `translations.<語言>.diagram.caption` 有一份逐字相同的複本，
  所以改 caption 要交**兩筆**（pack 一筆、research 一筆，old／new 相同）。
- 不要動 url、src、checked_on、slug 這類機器欄位；不要動 ZH；**不要動 `[0] title`，也不要動兩個結尾連結的文字**
  （標題被其他十一篇的連結逐字引用，由協調者統一處理）——你認為某篇**標題**譯得不好，寫在回報裡，不要放進 JSON。
- `new` 不能讓 summary 的一句超過 300 字元、FAQ 的答案超過 1,000 字元、表格儲存格超過 300 字元；不能拿掉免責標記。
- `reason` 用繁體中文寫，一句話說明依據（查了哪個官方頁就寫網址）。

用 Write 工具寫檔。**不要 git add／commit，不要編輯 repo 內任何檔案，不要跑 `pack_cli`、`pytest`、`check_article.py`。**
任何網路請求都不得帶 email 或任何個人資料；需要自訂 User-Agent 時一律用 `Mokaair-editorial`。
查官方名稱以外不需要上網；被擋（403／擋阻頁）就換同一官方站的其他頁，查不到就在回報裡說查不到，不要用整合站或百科充數。

4. 你認為「全批統一用語」表哪一格定錯了（附官方頁依據）。
