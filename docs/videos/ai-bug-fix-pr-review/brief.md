# 開發者影片 4：AI 修好 Bug 就能合併？

狀態：企劃與示範案例已落地；稿、查核、旁白與成片仍在製作。

## 站主觀點

綠燈是合併的必要證據，但要對照需求與實際差異。片中把已執行的命令、差異與測試說清楚，不假裝有未發生的正式站事故或人工審核結論。

## 觀眾看完能做到的事

用三道關檢查一個 AI 生成的修補：需求契約、實際差異、回歸驗收；知道哪裡需要人作最後判斷。

## 觀眾與問題

會看 Git 差異、基本單元測試的開發者。問題是「AI 說修好了，測試也綠了，這個 PR 就能合併嗎？」目標 8–12 分鐘。示範沿用上一支自己寫的分攤旅費函式與實際產生的 Claude Code 修補；起始兩個測試雖綠卻漏了非整除案例，不宣稱修補本身仍有錯。

## 30 秒開場

三個人分一百分，起始測試全綠，但函式只分出去九十九分。現在 AI 提交一個修補，你會直接合併嗎？我用三道關帶你檢查：需求、差異、回歸。

## 大綱 A（採用）

1. 綠燈的陷阱：起始兩個測試都過，實際輸出卻少一分。
2. 第一關，需求契約：和題目逐字對照，確認總和、差額、餘數順序與輸入規則。
3. 第二關，讀差異：逐行看驗證是否保留、是否只改到預期檔案。
4. 第三關，回歸：事後寫的四類驗收與 property check，示範修補通過。
5. 合併決策：記錄證據，請負責的審查者做最後判斷。

## 大綱 B

把工具內建的「審查」功能走一遍，列功能清單。未採用：沒有這次修補的真實審查證據，容易變成產品宣傳。

## 標題與縮圖方案

- A：〈AI 修好 Bug 就能合併？三個 PR 檢查點〉；縮圖「測試綠了？／先過 3 關」。
- B：〈測試全綠還少一分：AI 修補怎麼審？〉；縮圖「100 分 → 99 分」，副標「綠燈也會漏」。
