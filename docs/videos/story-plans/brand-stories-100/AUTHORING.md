# 怎麼寫一個故事的企劃

這份給寫企劃的人與代理看。設計在 [`../../STORY.md`](../../STORY.md)；範例是 [`stories/A01.json`](stories/A01.json)，照它的形狀寫，不要抄它的文字。

一個故事一個檔：`stories/<代號>.json`。順序只寫在 `schedule.json`，故事檔裡沒有編號。寫完跑：

```bash
node tools/video/story-plans/validate.mjs --partial
```

## 這支影片長什麼樣

12–15 分鐘、只有旁白、卡通插畫約每 9 秒一張。內容是查核過的非虛構故事：一個品牌、一件日用品或一個標準，它怎麼來的、生意怎麼運作、付出過什麼代價。觀眾是台灣的一般人，不是業內人士。

企劃不是稿子。企劃要讓之後的撰稿模型知道：這支要回答什麼問題、六段各講什麼、哪些事實一定要對到來源、來源在哪裡。

## 欄位

| 欄位 | 寫什麼 |
| --- | --- |
| `id` | 代號，跟檔名一樣。`A` 日常用品與隱形標準、`B` 日本、`K` 韓國、`T` 台灣、`C` 科技與軟體 |
| `slug` | `story-` 開頭的英文代號，小寫、數字、連字號，最多 60 字元，例如 `story-rolling-suitcase` |
| `category`、`region` | `A` 是 `everyday`，`B`／`K`／`T` 是 `asia-brand`，`C` 是 `tech`；`region` 是 `global`、`jp`、`kr`、`tw` |
| `subject` | 主題，幾個字 |
| `title` | 暫定標題，最多 60 字，建議 30 字以內。標題裡的每個數字與說法都要是查核過的 |
| `logline` | 一句話說這支影片講什麼，最多 120 字 |
| `question` | 開場要回答的那個問題，最多 120 字 |
| `chapters` | 六段，順序固定：`hook`、`origin`、`idea`、`engine`、`turn`、`now`。每段 60–400 字，寫這一段要講的具體事實，不要寫「介紹背景」這種空話 |
| `takeaway` | 留給觀眾的一句觀察，最多 120 字。是觀察，不是建議，也不是冷知識 |
| `must_verify` | 4–10 個一定要對到來源的事實。每個是 `{ "claim", "sources": [來源的索引], "core"?, "attributed"? }` |
| `sources` | 至少 3 個。每個是 `{ "url", "publisher", "kind", "supports", "checked" }` |
| `names` | 這個故事裡的品牌名、產品名、公司名、真人姓名。這些字不能出現在圖像提示詞裡 |
| `cast` | 0–3 個反覆出現的人物，`{ "id", "role", "appearance" }`；沒有就寫 `[]` |
| `image_notes` | 這個題目的畫面要畫什麼、不能畫什麼 |
| `sensitivity` | `none`，或 `care`（空難、抗爭、官司、醜聞、死亡） |
| `related_guide` | 對應的 Mokaair 文章 slug，沒有就 `null` |
| `thumbnail` | `{ "headline", "idea" }`：縮圖上的字（最多 12 字）與畫面構想 |

除了 `cast` 的 `appearance` 用英文，其他文字都用台灣的繁體中文。專有名詞第一次出現時中文後面可以附原文。

## 六段各是什麼

| 段 | 內容 |
| --- | --- |
| `hook` | 一個反直覺的問題或說法，加上這支影片會回答什麼。30 秒內講完 |
| `origin` | 起點：誰、哪一年、在哪裡、遇到什麼問題 |
| `idea` | 關鍵的那個點子或決定，以及一開始的失敗、拒絕或沒人要 |
| `engine` | 生意怎麼運作：錢從哪裡來、為什麼別人學不來。這段是整支的核心 |
| `turn` | 代價、危機、官司、爭議，或跟大家以為的相反的真相 |
| `now` | 現況，以及跟觀眾的關係（旅行時在哪裡會遇到、日常哪裡看得到），最後回到開場的問題 |

## 來源規則

1. **每個來源都要實際打開讀過。** 讀不到的頁面（403、要登入、付費牆、被機器人驗證擋住）不要列。主機上的工人之後會用一般的 HTTP 請求去抓同一個網址，抓不到就沒有用。
2. `kind` 的意思：

   | `kind` | 是什麼 | 能不能單獨撐起一個事實 |
   | --- | --- | --- |
   | `official` | 公司自己的沿革頁、政府機關、標準組織、專利紀錄 | 可以 |
   | `court` | 判決書、主管機關的裁罰文件 | 可以 |
   | `academic` | 期刊論文、大學或研究機構的頁面 | 可以 |
   | `archive` | 博物館、圖書館、檔案館 | 可以 |
   | `reference` | 百科（含維基百科） | 不行，要再一個 |
   | `news` | 新聞媒體、雜誌 | 不行，要再一個 |
   | `book` | 書的出版社頁面或可讀的摘錄 | 不行，要再一個 |

3. `must_verify` 的每一條，要嘛引用至少一個「可以單獨撐起」的來源，要嘛引用兩個不同發行者、不同網域的來源。
4. 只有一個次級來源的軼事，標 `"attributed": true`。這表示旁白會說「照某某的說法」或「據說」，不會當成事實講。
5. 標題靠的那個事實標 `"core": true`，至少要有一條。**核心事實站不住腳時，不要硬寫。** 先看能不能換成正確的說法（「大家都說 X，其實是 Y」常常是更好的故事）；還是不行，就不要寫這個檔，在回報裡說明原因，由負責人換成備選題目。
6. 公司官網對自己的光榮事蹟是可靠的，對自己的醜聞不一定。負面事件（官司、事故、醜聞）要有判決、主管機關文件或兩家以上的媒體；在世人物的負面說法一定要兩個來源。
7. `supports` 寫這一頁是哪些事實的證據；`checked` 寫你讀它的日期。
8. 不讀也不引用其他 YouTube 影片、影片逐字稿、內容農場。參考頻道「黑猫研究院」做過的內容一律不看。

## 圖像規則

- 畫面是卡通插畫。不畫商標、文字、招牌上的字；不畫有版權的角色；不畫真人的長相。
- `cast` 的人物是一般化的卡通人物：年代、服裝、職業要對，長相不對應任何真人。`appearance` 用英文寫年紀、體型、髮型、衣著與顏色、一個代表性的道具，不能出現 `names` 裡的任何名字。
- 會反覆出現五次以上的人物才放進 `cast`；只出現一兩次的路人不用。
- `image_notes` 要寫出這個題目特有的風險。例如講某個遊樂園時只畫城堡輪廓與人群，不畫它的角色。

## 標題

- 參考這幾種句型：「一家賣 A 的公司，為什麼能決定 B？」「你每天都在用的 X，為什麼…？」「因為 A，才有了 B」。
- 不用「震驚」「驚天」「真相大公開」這類字眼，不用驚嘆號堆疊。
- 數字要查核過；不確定就不要放數字。
- 不貶損任何品牌或人。

## 不要做的事

- 不給投資、醫療、法律或選舉政治建議。
- 不寫業配語氣，不推薦購買。
- 不編造任何人的對話、心情或經歷。
- 不在任何請求的 User-Agent 或網址裡放個人的 email。

## 查核：第二個人讀

寫的人不查自己的稿。每個故事寫完後，由另一個人或另一個代理在新的對話裡查核，結果寫進 `reviews/<代號>.json`。

查核的人要做的事：

1. 把每個來源實際打開。打不開的換掉，或把靠它的說法拿掉。
2. 逐條對 `must_verify`：人名、年份、數字、引述，跟來源寫的一不一樣。不一樣就改成來源寫的。
3. 讀六段要點。裡面每個具體的事實（年份、數字、人名、地名、引述）都要找得到來源；找不到的，補來源、改成「據說」，或拿掉。
4. 看標題：數字與「唯一」「第一」「最老」這類說法有沒有來源；有沒有貶損誰。
5. 看圖像規則：`names` 有沒有漏掉要點裡出現的品牌與人名；`cast` 的外觀是不是一般化的人物。
6. 看用語是不是台灣的說法（影片、軟體、網路、品質、資訊）。

查核紀錄的欄位：

| 欄位 | 內容 |
| --- | --- |
| `id` | 代號 |
| `reviewed` | 查核日期 |
| `reviewer` | 誰查的（人名或模型名稱） |
| `story_sha256` | 查核完成時故事的雜湊，用 `node tools/video/story-plans/validate.mjs --hash <代號>` 取得 |
| `verdict` | `pass`（沒有改動）或 `fixed`（改過，改了什麼寫在 `changes`） |
| `sources_opened` | 實際打開了幾個來源 |
| `changes` | 改了什麼，一條一句；沒有改就是 `[]` |
| `notes` | 還有疑慮但沒有證據改的地方，留給之後的撰稿與查核 |

紀錄綁著故事的內容：故事改了一個字，紀錄就過期，要重新查。只重排欄位或縮排不算改。

連核心說法都不成立、改也改不好的故事，查核的人不寫紀錄，回報給負責人換題目。
