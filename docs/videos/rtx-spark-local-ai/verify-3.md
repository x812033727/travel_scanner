## The physics (point 3)

- Decode is bounded by bandwidth ÷ bytes of weights read per token: **true, with one condition the script did not state.** NVIDIA's blog cited on the slide says decode generates "output tokens autoregressively one at a time" and is "a memory-bound operation" in which "the data (weights, keys, values, activations)" dominates the latency; its co-design post (2026-07-10) says the same for "latency-sensitive decoding". While each pass over the weights yields one token, a token cannot take less than bytes ÷ bandwidth. The same NVIDIA blog also says how to beat it: "Speculative sampling offers a workaround", running the main model "at multiple steps in parallel" on a cheap draft. That is in local use today: NVIDIA's RTX Spark-tagged blog quotes "131 tokens per second on a single GeForce RTX 5090 with MTP" (llama.cpp), and llama.cpp's own gpt-oss-120b package ships NVIDIA's EAGLE-3 draft (nvidia/gpt-oss-120b-Eagle3-v3). So 3s2v's 「實際只會更慢」 overstated it. Wording corrected, idea kept: 「這是每步一個 token 的理論上限：上下文和其他程式也要搶頻寬，實際只會更慢。」 The step is ajv4's 「每一步都要從記憶體搬參數」. The caption's formula (per-token read) stays general and correct.
- The ceiling ignores the KV cache and other traffic, so real speed is lower: **true.** The cache is read every token (the blog lists "keys, values"): from config.json, 0.31 GB per token at 8,192 tokens of context (ceiling 56.5) and 4.84 GB at 131,072 (30.5). The CPU shares the same 300 GB/s ("shared by the CPU and iGPU"). A peak is not sustained: NVIDIA's own DGX Spark llama.cpp run of gpt-oss-120b (55.37 tokens/s at 273 GB/s) is 72.9 % of the ceiling of llama.cpp's standard file, if that is the file it used.
- Prefill is compute-bound: **true** for 「讀進一大段文件」: "a matrix-matrix operation that’s highly parallelized. It effectively saturates GPU utilization."
- Format matters as much as bandwidth: **the reason for the efif change.** 「最多約 60」 holds for OpenAI's files and Ollama's tag (both keep attention and the output layer at 16 bits). llama.cpp's own file stores those at 8 bits and has a ceiling of 83.5. The slide already said 「原版」, and now efif says it too.

## Point 5: do computed ceilings fall under 不做的事?

The bullet reads: 「畫面和旁白不出現任何 RTX Spark 的每秒 token 數，除非是 NVIDIA 自己公布的（標明是廠商說的），或出貨後有名有姓、撰稿當天打開過的獨立評測。」 實算三 adds: 「不換算成每秒幾個 token：實際速度還要看精度、軟體和記憶體頻寬，RTX Spark 的頻寬 NVIDIA 沒有公布」.

My reading: **the ceilings fall inside the letter of the rule and against 實算三. Their labelling meets the rule's purpose. They should stay only with the owner's explicit approval.**

- The letter. 「約 8.6 個」 and 「約 60 個」 under 「每秒最多幾個 token」 are tokens-per-second numbers about RTX Spark. Neither NVIDIA nor a named review published them. The rule's two exceptions are about who publishes a number, not how it is labelled, so the label 理論上限 does not bring them under either exception.
- The purpose. The rule exists so the channel never claims or implies a test and never relays unsourced speeds. The slide says 理論上限 and 不是實測, the narration says 最多 and 實際只會更慢, and the description says the numbers are ceilings from the bandwidth. The inputs are NVIDIA's own 300 GB/s and the model makers' own counts. The numbers are not presented as anyone's measurement.
- The brief anticipated the bandwidth. Its closing note says 「NVIDIA 若公布了 RTX Spark 的記憶體頻寬…第 5 章改放 NVIDIA 的數字並標明是廠商公布的」. That puts NVIDIA's number (the bandwidth) on screen, which the published card does, but it does not license deriving tokens per second. 實算三's other two reasons, 「精度、軟體」, are exactly how the ceilings can mislead: the 60 held only for 原版, and speculative decoding or MTP beats a one-token-per-step ceiling. Both are now said on screen or aloud, but the reasons stand.
- So this is an outline decision. The approved brief says otherwise, and its approval is bound to brief.md's hash. It is not a fact error, so I did not rewrite it. If the owner declines, the lightest cut is to drop `speed-ceiling` and keep `active-bytes` (bytes per token). kpbj's ratio then carries 「可能快很多」 without a tokens/s number, and msnd and rv27, which set up the calculation, would need rewording too.
