# 第二個原創實證：迴圈也要有結束規格

2026-10-25實跑，沿用現成GCC，不安裝、不付費、不下載供應商證明。

```sh
python /workspace/work/ai-tech-next/formal-demo/run_loop_demo.py
```

完整C：loop.c；完整runner：run_loop_demo.py。編譯命令／版本／stdout／stderr在loop-results.json；全部256個n的實際C觀測及完整有限控制狀態結果在loop-all-256.json；五個輸入／產物的bytes及SHA256在loop-manifest.json。本輪確認manifest全吻合。

規格：n∈0..255，i從0開始，每次加1，條件i≤n時繼續；應在n+1次增量後離開，回傳n+1。程式沒有陣列／buffer存取。計數器是本地volatile物件，避免C編譯器將無可觀測作用的空迴圈依前進假設消去；沒有指標逸出或外部寫入者。圖模型涵蓋固定n與變動i的控制狀態，不涵蓋外部干擾。

錯版i為uint8_t，n=0..254實際C正常返回；n=255的實際C子程序於0.25秒限額被終止，記錄timeout。**逾時本身不是永不結束的證明。** 另外完整探索有限控制狀態：i依序0..255，再回0，條件始終成立，因此此確定模型有256步循環。n=255是此域唯一不結束的模型輸入。

修正版i為uint16_t。同一0..255輸入域，全256個編譯C呼叫均正常返回，且每個返回值都和模型n+1一致。n=255時走256次，i到256即可離開。這是正向的修正結果，並非單純列出風險。

它是**原創有限控制狀態完整探索＋實際GCC執行觀察**，沒有用SAT、SMT、Rocq或Lean證明這個迴圈，也沒有匯出經獨立kernel檢查的證書。先前guard範例另有SymPy命題SAT，名稱不要混用。

兩個小程式彼此獨立，只共用0..255輸入域與窄型別問題。不能演成「修正的8byte guard放行255後仍卡住」：正確guard本來就會拒絕255。第二程式用來加上另一條明確規格——迴圈會在指定次數內離開。沒有宣稱這是供應商的真實漏洞、Claude受測碼或239個入口重現。

可用旁白：「這次換一個獨立小程式，要求它數完後離開。逾時只告訴我們這次沒有及時返回；把這256個控制狀態全部走一遍，才看見它確實回到起點。把計數器加寬後，全部256種輸入都返回預期值。」
