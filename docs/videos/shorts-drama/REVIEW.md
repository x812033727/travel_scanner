# Shorts 零台詞短劇的評分與審核機制：從企劃盲評到成片上架與數據覆盤

這份是共用區：任何一部無語音（零台詞）Shorts 短劇，在**花錢前（企劃與分鏡）**、**製作中（首格與成片）**、**上架前（八語包裝）**與**上架後（7／28 天報表）**的四階段完整評分表、硬門檻、獨立審核提示詞範本與複審退修紀律。

站主定下的兩條核心鐵律：
1. **「每一集成片都要過審核才能上架；有問題就修，修完再審；笑點也要夠。」**（2026-11-04）
2. **審核的人與做片的人永遠分開**：寫稿、生圖、剪接的人看自己的作品會自動腦補因果；所有盲評、審分鏡、審成片與笑點評核，一律由**沒參與製作、只讀不改的獨立子代理**執行。

- 分鏡怎麼寫（黃金五拍、單人框、聲音三層結構、第 0 關 AI 避險）：[`WRITING.md`](WRITING.md)。
- 總覽與各系列索引：[`README.md`](README.md)。
- 歷次審核踩過的坑與教訓：[`../lessons/shorts.md`](../lessons/shorts.md)。

## 1. 階段一：企劃與分鏡的 100 分三位獨立評審盲評（花錢前）

### 為什麼零台詞短劇的文字盲評門檻是 70 分（且只用來排名與抓盲點）？
2026-11-03 實測將 Instagram 上 **33.4 萬讚**的狗夫妻零台詞爆紅參考片轉寫成純文字分鏡，混進我們的六集新企劃一起交給三位評審盲評，結果 33 萬讚原片只拿 **55 分**，六個新企劃反而都比它高。
原因：**純文字看不到角色僵住的微表情、慢轉頭的停頓與音效留白**。因此：
- **零台詞短劇的文字盲評門檻定為中位數 `≥ 70 分`**（有對白／內心獨白的短劇維持 `≥ 80 分`、每人 `≥ 65`、`laughs ≥ 14`、`surprise ≥ 10`）。
- 文字盲評的核心用途有三件：**① 擋掉明顯沒梗的企劃**、**② 決定一季 5–7 集的開拍先後順序（高分先拍）**、**③ 抓出「作者以為看得懂、但觀眾看畫面根本推不出因果」的盲點**（透過 `would_scroll_away_at` 與 `fixes` 在畫圖前免費改好）。

### A. 三位固定評審角色（Personas）
每次盲評開三個全新的唯讀子代理（關掉修改工具，讀不到作者的設計理由與集數表），分別賦予以下三個視角：
1. **`shorts-20`（20 歲重度短影音觀眾）**：每天滑 Shorts／Reels／TikTok 兩三個小時，直覺敏銳、毫無耐心；**前 1.2 秒沒看到怪事或中段有一鏡無聊，會立刻標記滑走**。
2. **`married-35` 或 `office-30`（30–35 歲核心共鳴受眾）**：依系列主題切換——家庭寵物系列用 `married-35`（已婚上班族、有小孩或養寵物，對家事、夫妻、闖禍最有共鳴）；職場系列如《社畜地獄》用 `office-30`（30 歲資深社畜，對老闆任性、加班、開會最敏感）。看重「會不會想立刻傳給另一半或同事」。
3. **`comedy-director`（十年經驗的視覺喜劇短片導演）**：專剪零台詞畫面喜劇（Mr. Bean、皮克斯短片、爆款寵物 Reels），**對重複套路（每集都慢轉頭、用爛的時間流逝梗）、鋪陳太慢、以及手機小螢幕看不清楚的細碎伏筆極度挑剔**。

### B. 盲評包格式（`packet-<judge>.md`）
- 把同一批候選集數（通常 5–6 集）代號編為 `作品 A`、`作品 B`…，**三位評審拿到的順序各自隨機打亂**。
- 只放：
  1. 系列共通前提（1 段：畫風、片長、零台詞、固定角色與外觀）；
  2. 每集每一鏡的：**`鏡頭（景別）`、`觀眾看到的那一刻（純畫面描述）`、`音效`、`秒數`**。
- **嚴禁放入**：作者寫的「為什麼這樣設計」「這鏡的笑點是什麼」「AI 避險筆記」，避免引導評審。

### C. 八軸 100 分評分表與強制 JSON 輸出（`judge-instructions.md`）

貼給三位盲評代理的統一指令與評分表：

```markdown
你是 `<judge 代號與角色設定>`。請盲評以下零台詞 Shorts 短劇候選作品。
誠實打分，不要客氣；你在手機上滑 Shorts，這支不好笑或哪一鏡拖沓你會直接滑走。各作品之間必須拉開分數差距。

## 評分表（每一份作品各打一次，滿分 100 分）

| 軸 | 滿分 | 評什麼 |
| --- | --- | --- |
| `hook` | 15 | 前 1.2–2 秒：第一格就有衝突或怪事，讓人不想滑走（還在走進場或靜態鋪陳直接扣分） |
| `premise` | 10 | 一句話說得出的設定，一般人一看就有共鳴、關靜音也秒懂因果 |
| `laughs` | 20 | 笑點密度：真的會笑出來的視覺反差，不是只有動物可愛 |
| `escalation` | 10 | 情況一次比一次誇張或荒謬，不是同一個笑點重複三次 |
| `surprise` | 15 | 至少一個觀眾猜不到、但回頭看完全合理的視覺反轉 |
| `character` | 10 | 角色的反應與動作有個性、具體可演，不是空泛形容詞 |
| `payoff` | 10 | 結尾最後一拍補刀有力，有重看或追下一集的理由（平淡收尾或老套對鏡頭甜笑扣分） |
| `share` | 10 | 看完會想轉傳給某個具體的人（另一半、朋友、同事） |

## 回覆格式

只回一個 JSON 物件，不要任何其他文字：

{
  "judge": "<你的代號>",
  "works": [
    {
      "work": "A",
      "scores": {"hook": 0, "premise": 0, "laughs": 0, "escalation": 0, "surprise": 0, "character": 0, "payoff": 0, "share": 0},
      "total": 0,
      "beats": [{"shot": "s01-xxx", "joke": "你讀到的笑點或問題", "funny": 3}],
      "would_scroll_away_at": "會在哪一鏡滑走的鏡號，或 null（會看完）",
      "fixes": ["具體到哪一鏡、改成什麼畫面或動作"]
    }
  ],
  "most_want_to_see": {"work": "X", "why": "為什麼這一集最想看、會傳給誰"},
  "ranking": ["由好到差的作品代號"]
}

註：`beats` 的 `funny` 為 1–5（1 不好笑、2 普通、3 會心一笑、4 很好笑、5 笑出聲）。
```

### D. 盲評結果怎麼判讀與改稿
收到三位評審的 JSON 後，先用內建彙整腳本自動核對八軸加總、計算中位數、抓出滑走陷阱並排定開拍順序（避免人工加錯分）：

```bash
node docs/videos/shorts-drama/preflight.mjs score-blind judge-shorts-20.json judge-married-35.json judge-comedy-director.json --threshold 70
```

1. **排序開拍**：依三位評審 `total` 的**中位數**由高到低排開拍順序；同分時看最低分誰比較高（全數 `≥ 75` 的優先於有一位給 `< 65` 的）。
2. **必改條件**：
   - 中位數 `< 70 分`；
   - 或任何一鏡被 **`≥ 2` 位評審填進 `would_scroll_away_at`**；
   - 或三位評審在 `beats` 裡讀出的因果跟作者原意不一樣（例如《汪家夫妻》EP3 三位都看不懂為什麼盤子上有髮捲）。
3. **改稿六原則**（從兩輪 12 集盲評歸納）：
   - **前提因果直接畫在物件上**（蛋糕直接畫成平面柴犬臉＋地上柯基短奶油掌印）；
   - **第一格直接從出事那一刻開始**（衣帽架正在斷裂、巨型捲髮已經卡死在門框）；
   - **補刀的家人要給一個「其實早就知道」的小動作**（老花眼鏡反光、低頭看一眼地毯鼓包再面不改色配合）；
   - **最強的一格放最後，或最後一拍再升級**；
   - **同一系列不要每集都用同一個慢轉頭**（換成戴洗碗手套拉泳鏡、順著掌印看、頭頂捲髮豎起一根天線）；
   - **收尾落在苦主的小動作上**（吸奶嘴、聞襪子翻白眼、吹開鼻前青蔥）。

## 2. 階段二：開拍前的自動化前檢、獨立審劇本與首格五項檢查

企劃盲評過關並改完稿後，進入技術審核：
1. **自動化機械前檢（`preflight.mjs`，免費、秒出結果）**：
   ```bash
   node docs/videos/shorts-drama/preflight.mjs check <slug>.json --engine h3   # 走 Google Flow 改帶 --engine flow
   ```
   先清零所有 `ERROR`（片長硬範圍、單鏡動態 ≤ 3.5s、單人框、SFX 落在鏡內、人手／`magazine cover`／畫外伸手、系列專屬規則、縮圖與標題），並逐一確認 `WARN`。
2. **分鏡技術三道檢查**：照 [`WRITING.md` §六](WRITING.md) 跑完寫稿者十項自檢與**獨立審稿代理七大關卡**（五拍秒數、靜音理解度、單人框連戲、第 0 關 AI 6 大陷阱避險、音效在鏡內、9:16 安全區與重播迴圈、系列與引擎適配）。
3. **首格檢查（`colab/ff/` 或 `flow-inputs/`，送影片生成前先擋掉八成重抽）**：
   - 無論 MiniMax H3 或 Google Flow（Veo 3.1 Frames-to-Video）都是圖生影片，**首格已經畫錯的東西，動態片段永遠救不回來**。
   - 首格畫完必逐張看五件事才准送去生片：
     1. **第 3 拍誇張結果造型有沒有畫出來**（是不是真的蹲在花瓶裡、真的頂著巨型粉紅捲髮，而不是站在物件旁邊或抱著一塊布）；
     2. **動物毛爪（`two furry front paws`）**有沒有變成人類五指或塗指甲油；
     3. **背景與文字**有沒有模糊路人、品牌 Logo 或假字；
     4. **9:16 介面安全區（`x: 78–902, y: 180–1380`）**：臉部表情、毛爪與地面／角落線索有沒有落入右側 16.5%（按讚留言欄）或底部 28%（標題區）；
     5. **同機位連戲鏡**（如電視換台 `s03`/`s05`/`s06`/`s07`）是否共用 `s03` 首格當底圖編輯。

## 3. 階段三（第 1 關）：成片自動規格與硬切檢查（`qa_check.py`）

H3 片段生完、用 `edit.py` 照 `edit/plan.json` 合成出 `<VIDEO_WORKDIR>/<slug>/edit/final.mp4` 後，先跑免費的自動檢查：

```bash
python3 production/qa_check.py <slug> --work <VIDEO_WORKDIR>
```

| 檢查項 | 通過標準 | 失敗時怎麼修 |
| --- | --- | --- |
| **畫幅與幀率** | `1080×1920`（9:16 直式）、`30 fps` | 由 `edit.py` 統一輸出規格 |
| **音訊與響度** | `48 kHz` 雙聲道、整體響度 **`-15.0 ~ -13.0 LUFS`**（目標 `-14 LUFS`） | `edit.py` 兩段式 `loudnorm` 自動正規化 |
| **總片長** | **`9.0–20.0 秒`**（黃金區間 `11–16 秒`） | 超過 20 秒砍短反應鏡或拿掉廢鏡；低於 9 秒檢查是否有鏡頭漏接或加 `hold` |
| **鏡中硬切偵測** | 列出 H3 片段中途自己硬切換景的秒數 | `edit.py` 會在偵測到的硬切前自動截斷；慢速漂移或變臉交第 2 關人工看 |
| **檢查聯絡表** | 自動產出每秒 3 格、左上角帶黃字時間碼的 `qa/<slug>.jpg` 與 `<slug>.qa.json` | 交給下一關的獨立畫面審片人與兩位笑點審片人 |

- **9:16 安全區紅框抽驗指令**（驗重要臉部表情、毛爪與地面／角落破綻有無被 Shorts 右側按鈕欄與底部標題區遮住）：
  ```bash
  ffmpeg -v error -y -ss <秒> -i <final.mp4> -frames:v 1 -update 1 \
    -vf "drawbox=x=78:y=180:w=824:h=1200:color=red@0.8:t=4,scale=540:-1" \
    <VIDEO_WORKDIR>/<slug>/qa/safezone-<秒>.png
  ```
  紅框（`x: 78–902, y: 180–1380`）之外的區域會被 YouTube Shorts 介面蓋掉；只要核心笑點道具或臉掉在紅框外，即視為畫面遮擋問題。

## 4. 階段三（第 2 關）：獨立畫面審核＋兩位觀眾角色成片笑點審核

`qa_check.py` 通過後，**開全新的獨立子代理**（沒看過前面的審核紀錄、也不是寫稿或剪這集的人）檢視 `qa/<slug>.jpg`，有疑點就用 `ffmpeg` 從 `final.mp4` 抽 540px 寬的大格（必要時疊安全區紅框）確認。

### A. 畫面上架硬門檻（Visual Defect Gate）
問題嚴重度分三級：**高**＝一眼看出很怪、立刻出戲；**中**＝注意看會發現；**低**＝挑剔細節。

| 等級 | 上架判定規則 |
| --- | --- |
| **高嚴重度** | **0 容忍，一律必修。** |
| **必修改的中嚴重度** | 只要屬於以下六類，就算審片人標「中」也**一律必修，修完才能上架**：<br>1. **人類痕跡**：遠處背景人影、人類手指與手臂、指甲油；<br>2. **多出或缺少的肢體、角色分身**：同框出現兩隻主角、多一隻懸空手或三隻手臂；<br>3. **文字、品牌 Logo、浮水印**：看得懂的字母／漢字、Apple 等品牌標誌、角落浮水印；<br>4. **片段中途換景或角色變臉**：後半段突然變成別的房間、水豚打噴嚏後半臉變成狗；<br>5. **讓核心笑點看不懂的劇情矛盾**：例如說沒電熄燈但螢幕還亮著、說看手錶但手被切掉且沒低頭動作；<br>6. **核心笑點被 Shorts 介面區遮擋**：關鍵破綻道具或主角臉落入右側 16.5%（`x > 902`）或底部 28%（`y > 1380`）安全區外。 |
| **可接受並記錄的中／低嚴重度** | 不影響笑點理解的次要道具連戲差異（如鏡頭間電視外框款式微變、掉了兩根羽毛只畫出一根），在批次品管紀錄 `QA-<日期>.md` 寫明「接受」後上架，不無限抽卡。 |

### B. 成片雙人笑點審核硬門檻（Visual Humor Gate）
成片看得到畫面、定格與聽得到音效節拍，是判斷好不好笑最準的一關。每支成片由**兩位不同觀眾角色**的獨立審片人（**角色 A：21 歲常滑 Shorts 觀眾**；**角色 B：32 歲喜劇導演**）各自看檢查圖與抽格，按五項指標打分：

| # | 評核指標 | 評分規格 | 成片上架硬門檻 |
| --- | --- | --- | --- |
| **1** | **鉤子（Hook）** | `1–5 分`：前 1.2–2 秒有沒有怪事或衝突，讓人不想滑走 | 診斷指標（`< 3 分` 優先砍短第 1 鏡或拿掉開頭廢鏡） |
| **2** | **核心笑點有畫出來（Gag Drawn）** | `是／否`：這集的核心笑點（偽裝造型、誇張結果、假景穿幫、貓老闆動作）在畫面上**不靠文字解釋就看得懂嗎**？只靠腦補算「否」 | **硬門檻：兩位審片人都必須判「是」**（任一位判「否」即不通過） |
| **3** | **收尾（Payoff）** | `1–5 分`：最後一拍有沒有補刀、定格與音效打點有沒有力，以及切回第 1 格重播時是否自然無黑格 | 診斷指標（`< 3 分` 加 `hold`、`music_off`、把音效移回鏡內或砍掉片尾黑畫面） |
| **4** | **好笑度（Funny）** | `1–5 分`：`1` 不好笑、`2` 略悶、`3` 會心一笑、`4` 很好笑、`5` 笑出聲；必附一句理由 | **硬門檻：兩位審片人平均 `≥ 3.0 分`** |
| **5** | **會不會轉傳（Share）** | `是／否`：會不會想丟給某個具體的人（另一半、同事、朋友） | 診斷指標 |

### C. 獨立成片審片人提示詞範本（直接貼給新開的審片子代理，換掉 `【】`）

`ffmpeg -v error -y -ss <秒> -i <final.mp4> -frames:v 1 -update 1 -vf "drawbox=x=78:y=180:w=824:h=1200:color=red@0.8:t=4,scale=540:-1" <VIDEO_WORKDIR>/<slug>/qa/z-<秒>.png`

## 6. 階段四：上架前包裝、雲端備份與上架後 7／28 天數據覆盤

### A. 上架前包裝與匯入檢查
1. **封面（`thumb`／`cover.png`）**：選第 3 拍「誇張結果」或第 2 拍「反轉前最強表情」那一格，縮到手機列表寬度 `120–150px` 仍一眼看懂反差。
2. **八語標題與說明欄（`youtube-meta`）**：
   - 一次產出繁中（`zh-TW`）與八語（`en, ja, ko, es, pt, id, vi, th`）標題與說明；
   - **標題只寫「日常衝突情境＋系列 Hashtag」**（如 `老婆燙了新髮型，老公看都沒看就點頭 #汪家夫妻`），**嚴禁在標題破梗結局**；
   - 說明欄標明 AI 生成，後台匯入設 `synthetic_media: true`。
3. **雲端硬碟備份與後台匯入**：
   - 先將完整製作檔（`workdir/<集>/edit/`、`colab/` 或 `flow-inputs/`＋`flow-clips/`、`qa/`、`production/`、`repo-docs/`）備份至雲端硬碟 `AI/備份/Shorts/<系列名>/`；
   - 再匯入後台。`<DIR>` 放三個檔：`final.mp4`、`cover.png`（選好的封面）與 `meta.json`，**不放 `zh-TW.srt`**：
     ```json
     { "slug": "<集的 slug>", "line": "drama", "silent": true, "series": "<系列 slug>",
       "titles": ["<繁中標題>", "<備用標題>"], "description": "<繁中說明>",
       "hashtags": ["#<系列>"], "tags": ["..."], "synthetic_media": true,
       "localizations": { "en": { "title": "...", "description": "..." }, "ja": { ... }, "...": {} } }
     ```
     `localizations` 直接抄 `youtube-meta.json` 的八語標題與說明（en、ja、ko、es、pt、id、vi、th）；`titles` 要兩個（第二個是備用，同樣不破梗）。然後依序：
     ```bash
     node tools/video/shorts/cli.mjs import --from <DIR> --workdir <VIDEO_WORKDIR>   # 印出 build 目錄
     node tools/video/shorts/cli.mjs check-audio --dir <BUILD_DIR>                  # 零台詞：0 句，不連站
     node tools/video/shorts/cli.mjs qa --dir <BUILD_DIR>
     node tools/video/shorts/cli.mjs package --dir <BUILD_DIR>
     node tools/video/shorts/cli.mjs push --dir <BUILD_DIR>                         # 站主說可以才推
     ```
     `qa` 的片長用短劇自己的 9–20 秒，不看後台 Shorts 設定的「最短」；`layout` 一定不過（匯入的片沒有安全區量測），交站主在後台看一次。手動 `push` 的兩關都由站主核准。

### B. 上架後 7 天／28 天數據覆盤評分表與三點校準
公開滿 7 天與 28 天時，用 `node tools/video/youtube-reports/cli.mjs videos --window 7 --shorts` 讀取實際表現（扣除非自然廣告流量），每項與**同系列中位數**比對（高於中位數記 `+1`、接近記 `0`、低於記 `-1`）：

| 指標 | YouTube 報表欄位 | 零台詞 Shorts 觀察重點 |
| --- | --- | --- |
| **1. 有效觀看** | `engaged_views` | Shorts 演算法有沒有持續推流 |
| **2. 平均觀看百分比** | `average_view_duration_percentage` | **核心指標**：11–16 秒短劇目標衝過 **`100%`**（代表觀眾看完自動重播 Loop） |
| **3. 前段留存／滑走率** | Studio 留存曲線／選擇觀看占比 | 前 1.2 秒鉤子有沒有留住滑動中的觀眾 |
| **4. 每千次觀看分享** | `shares ÷ views × 1000` | 有沒有打中夫妻、情侶、同事共鳴讓人轉傳 |
| **5. 每千次觀看淨訂閱** | `(subscribers_gained - subscribers_lost) ÷ views × 1000` | 觀眾想不想繼續追這個固定角色系列 |
| **6. 每千次觀看留言** | `comments ÷ views × 1000` | 結尾補刀或小破綻（如爸爸扮咕咕鐘、水豚頭冒出瀑布）有沒有引發留言討論 |

- **決策規則**：
  - 六項加總 **`≥ +2`**：該集題型與笑點結構成功，下一批同系列優先複製該結構；
  - 六項加總 **`≤ -2`**：回頭比對「階段一文字盲評」與「階段三成片笑點審核」哪一項給了高分但實際觀眾卻滑走，將差異寫進 [`../lessons/shorts.md`](../lessons/shorts.md) 修正評分標準。

### C. 三點評分校準表（讓評分機制越做越準）
每批 5 集滿 7 天時，在系列紀錄檔補上這張校準表，追蹤「文字盲評 → 成片審片 → 真實觀眾」之間的偏差：

| 集數（`slug`） | 階段一文字盲評中位數 | 階段三成片好笑度（A／B） | 7 天 `engaged_views` | 7 天 `AVD%` | 分享／千次觀看 | 校準結論（要修正哪條評分權重或剪接規則） |
| --- | --- | --- | --- | --- | --- | --- |
| `<slug>` | `82 / 100` | `4 / 4` | （填入實測） | （目標 `>100%`） | （填入實測） | 例：第 1 鏡 0.9s 即破題，留存最高 → 複製此開場結構 |
