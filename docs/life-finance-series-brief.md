# 生活分享 財經系列：撰稿指令（每篇原文重用）

你要為 Mokaair（一個台灣的旅遊網站）的「生活分享」專區寫**一篇**財經文章或教學，讀者是台灣的
一般上班族與小家庭。你會拿到這份指令加一段「指派」；產出是一個工作區目錄，之後由
`python -m app.guides.pack_cli ingest` 驗證、渲染、寫進 repo。工具會拒絕的東西列在最後的檢查表，
先看一遍再動筆。

**第 2 節是這個系列的法遵限制，動筆前一定要讀完。** 其他系列沒有這一節，不要套用你在別的
生活分享文章裡看到的寫法。

## 1. 這是什麼

- 專區：生活分享（`kind: "life"`），網址 `https://mokaair.com/zh-TW/life/<slug>`。
- 語系：只寫 `zh-TW`，用台灣的用語（「軟體」不是「软件」、「網路」不是「网络」、「資料」不是「数据」、
  「影片」不是「视频」、「品質」不是「质量」、「使用者」不是「用户」）。
- 主題用 `finance`，再視內容加一個：操作教學型加 `tutorial`，工具比較型加 `software`，
  生活情境型加 `daily`，效率整理型加 `productivity`，索引型加 `misc`。指派已經給了 topics，照用。
  `destination_id` 一律 `null`。
- 文末會自動接「最新旅遊情報攻略」與目的地連結，你不用寫。

## 2. 不能寫的東西（法遵限制）

財經是 Google 的 YMYL 類別，而且這個系列包含投資題材。台灣《證券投資信託及顧問法》限制
未取得許可者為報酬提供證券投資分析與建議。**這個系列是教育性的，不是投顧。**

1. **不推薦個別商品。** 不推個股、個別基金、個別 ETF、個別保單、個別交易所、個別銀行方案、
   個別信用卡。要舉例就講**類型與成本結構**：
   - 可以：「市值型 ETF 依市值排序選股，高股息 ETF 依配息條件篩選，兩者的成分股週轉率不同。」
   - 不行：「○○ 這檔 ETF 適合長期持有。」
   - 可以：「數位帳戶的優利活存通常設有適用額度上限，超過的部分回到一般利率。」
   - 不行：「××銀行的數位帳戶最划算。」
2. **不給買賣建議。** 不寫進場時機、目標價、預期報酬率、績效預測、回測結果、「現在適合買」、
   「逢低加碼」。制度怎麼運作可以寫，該不該做由讀者自己決定。
3. **不用絕對化措辭。** 沒有「保證」「穩賺」「零風險」「必賺」「無腦存」「躺著賺」「絕對」。
   報酬與風險同時出現，成本與限制寫在好處旁邊，不要分段藏在最後。
   （唯一例外：指派是講投資詐騙的那篇，需要引用這些詞作為話術特徵——引用時要清楚寫明
   那是詐騙的識別特徵，不是本文的主張。）
4. **行情數字不寫進正文。** 股價、匯率、幣價、殖利率、基金淨值、當期利率數值查證日一過就是錯的。
   制度、費率結構、計算方式、申請流程、級距規則可以寫，並註明查證日。
   要舉數字例子時用假設值並寫明是假設（「假設月薪 5 萬」「以 100 萬本金試算」）。
5. **每篇最後固定一個免責 `callout`**（第 4 節的骨架第 8 項），措辭模板寫死在下面，不要自己重寫。

## 2.5 保險篇的額外限制（批次 03 起適用）

保險比銀行多一層執業限制，**而且那層限制管的是「招攬」這個行為**，不是管誰能解釋制度。
`保險法` 第 163 條第 1 項：「保險代理人、經紀人、公證人應經主管機關許可，繳存保證金並投保
相關保險，領有執業證照後，始得經營或執行業務。」`保險業務員管理規則`（`G0390016`）另規定
業務員須經所屬公司向公會登錄、招攬時應出示登錄證並告知授權範圍，登錄證未換發前不得招攬。

**寫險種與條款結構是教育性內容，不是招攬。** 但界線要靠下面這幾條守住，不要自己拿捏：

1. **不得出現任何保險公司名稱、商品名稱或商品代號。** 寫「險種」與「條款結構」，不寫某一張保單。
   - 可以：「實支實付醫療險的給付上限通常分項列在保險單條款的給付項目表裡。」
   - 不行：「○○人壽的××醫療險給付比較高。」
2. **不做費率比較，不給投保金額建議，不算「你該保多少」。** 可以說明額度是怎麼推算的
   （例如以年收入、既有保障與自付風險缺口去推），但**結論留給讀者與合格從業人員**。
3. **不寫「這種險該不該買」。** 寫的是保障範圍、除外責任、給付條件、名詞定義與常見誤解。
   「誰可能用得到」可以寫成情境描述，不要寫成建議句。
4. **條款用語照抄保單條款的正式名稱**，不要用業務話術的代稱：
   實支實付、日額、失能等級、等待期（觀察期）、除外責任、既往症、告知義務、
   批註、復效、寬限期、豁免保費。話術代稱（「還本」「保本」「終身有保障」）只在
   「這句話該換回哪個條款用語」的脈絡下出現。
5. **理賠是個案認定，不要寫成通則。** 「這種情況會賠」是最容易出錯的句型；
   正確寫法是「條款把 X 列在給付項目／除外責任」，然後說明實際認定仍看個案與條款。

**免責 callout 在保險篇要多一句**（接在既有模板之後）：
「理賠與否、給付金額以保單條款與保險公司核定為準。」

**⚠️ 示範條款有兩個版本，金管會網站給的是舊的。** 這是批次 03 三個代理各自從不同角度踩到的同一個坑：

- `law.fsc.gov.tw` 上的示範條款停在舊版（住院醫療費用兩型停在民國 103 年、傷害保險停在民國 99 年）。
- 現行版在 **`law.lia-roc.org.tw/Law/Content?lsid=<FL 編號>`**（壽險公會的保險相關法規查詢系統）。
  住院醫療費用兩型的現行版**修正日期是民國 113 年 6 月 28 日**——中間經過不只一次修正
  （108 年核定、109-01-01 實施的那次只是其中之一），**所以不要用某一次核定函去推斷現行條文**，
  直接讀 lia 站上的現行全文。
- 修正**插入條文並把後半整段重新編號**，所以條次會整個位移。實測對照：

| | 舊版（fsc 站上） | **現行版（lia 站上）** |
| --- | --- | --- |
| 實支實付型 每日病房費用 | 第 5 條 | **第 6 條** |
| 實支實付型 除外責任 | 第 11 條 | **第 12 條** |
| 實支實付型 保險金的申領 | 第 18 條 | **第 19 條** |
| 日額型 住院日額給付 | 第 5 條 | **第 6 條** |
| 日額型 保險金的申領 | 第 14 條 | **第 15 條** |

- 內容也有實質差異，而且正好落在讀者最在意的地方。兩個例子：
  - 現行實支實付型**第 19 條**的申領文件寫的是「醫療費用**收據正本**。但如為電子文件，必要時
    本公司得要求提供紙本文件。」舊版只寫「醫療費用收據」。
  - 現行**第 11 條（保險金給付之限制）**從舊版的一句話擴寫成兩款：第一款是已獲全民健康保險給付
    的部分，**第二款**是「已獲得其他住院醫療費用保險以實支實付給付者，但非以醫療費用收據正本、
    依其他法令投保或主管機關另有規定而獲得住院醫療費用之實支實付給付者不在此限」。
    這一款加上第 19 條的「收據正本」，才是**副本理賠與重複投保的條款依據**；舊版完全看不出來。
  **所以位移不只是改條次，引用的文字本身也要換成現行版**——只把數字加一會得到一個號碼正確、
  內容過期的引用，比原本更難發現。
- 用語也跟著改：傷害保險的附表現行是「**失能**程度與保險金給付表」，舊版寫「殘廢程度」
  （金管會 108-06-21 金管保壽字第 10804920500 號函，109-01-01 起實施）。

**所以：引用示範條款的條次與文字，一律以 `law.lia-roc.org.tw` 的現行版為準**，
並在 `notes.md` 記下你讀的是哪一個站。只在 fsc 站查得到的核定函（`GL` 開頭）仍然可用，
那是函本身，不是條文。

**查證來源的優先順序**（保險篇特有）：

- **各險種的示範條款**（金管會公告）——這是這一批最有價值的來源。它是條款結構的官方版本，
  有明確的給付項目、除外責任與名詞定義，而且不會像費率那樣很快過期。
- 全國法規資料庫：`保險法`（`G0390002`）、`保險法施行細則`、`保險業務員管理規則`（`G0390016`）。
- 金管會保險局；財團法人保險事業發展中心；
  **財團法人金融消費評議中心的評議案例**——它是「什麼情況被拒賠、為什麼」最實際的官方素材，
  引用時只寫爭點與理由，不要寫成「所以你會賠」。
- 健保相關（海外就醫核退那篇）：衛福部中央健康保險署。注意 `nhi.gov.tw` 常回 403，
  照 10.5 的兩種處理方式走。

## 3. 指派（協調者填）

指派會給你：`slug`、標題、topics、切角、必須涵蓋的點、hero 方式（自繪或 Commons）、
可以連過去的站內文章。標題可以微調，slug 不能改。這個系列**沒有任何合作連結**，
指派不會給，你也不要放。

## 4. 交付物與寫檔順序

全部放在 `<workdir>/<slug>/`（工作區路徑在指派裡）：

| 檔案 | 內容 |
| --- | --- |
| `pack.json` | 內容包（第 5 節），**先寫這個** |
| `diagram-1.svg` | 自繪圖解（第 7 節），至少一張；第二張叫 `diagram-2.svg` |
| `hero.svg` | 自繪 hero 插圖（第 8 節）；指派說用 Commons 照片時就不要這個檔，改在 `images.json` 指名 |
| `images.json` | 只有用到 Commons 照片時才需要（第 9 節） |
| `notes.md` | 查證記錄：每一個數字、級距、費率、規則一行，`主張｜來源網址｜查證日` |

**只准在工作區寫檔。** 想先驗證，只能用
`cd apps/api && uv run python -m app.guides.pack_cli ingest --from <workdir> --slug <slug> --dry-run`
（`--dry-run` 不能省，它什麼都不會寫）；不要不加 `--dry-run` 執行、不要刪或改 repo 裡的任何檔案
（`apps/api/app/guides/content/`、`apps/web/public/guides/` 都不要碰）——協調者會在你交件後自己
ingest，你事後「清理」等於刪掉協調者已經收進去的文章。

**先寫 `pack.json`，再畫 SVG，最後寫 `notes.md`。** 你的 session 可能中途被切斷，落在磁碟上的檔案
會留下來，結尾的報告不會。寫完每個檔案就存，不要等到最後一次寫。不要輸出結尾長篇報告，
一句「完成」就好。

## 5. `pack.json` 的形狀

```json
{
  "slug": "<slug>",
  "kind": "life",
  "destination_id": null,
  "topics": ["finance", "tutorial"],
  "featured": false,
  "display_order": 100,
  "locales": {
    "zh-TW": {
      "title": "……（≤ 60 字，含關鍵詞，說清楚讀完能知道什麼）",
      "description": "……（120–200 字，搜尋結果會顯示這段，把涵蓋範圍寫進去）",
      "hero": { "src": "/guides/<slug>/hero.jpg", "alt": "描述插圖畫了什麼", "width": 1, "height": 1 },
      "blocks": [ …見下… ],
      "sources": [
        { "title": "來源名稱（主管機關或業者官網）", "url": "https://…", "checked_on": "2026-09-14" }
      ]
    }
  }
}
```

`width`、`height` 先填 1，`credit` 不要填，工具會覆寫。`display_order`：索引／總覽篇 10，其他 100。

區塊順序（照這個骨架，每種都有）：

1. 兩段 `paragraph` 導言：第一段用一句話講清楚這篇回答什麼問題，第二段講這篇會帶讀者理解到什麼。
2. 三到六個 `{"type":"heading","level":2,"text":"…"}` 章節，每節一到三段 `paragraph`，該用清單就用
   `{"type":"list","items":[…],"ordered":false}`；步驟用 `ordered: true`。
3. 一張圖解：`{"type":"image","src":"/guides/<slug>/diagram-1.svg","alt":"描述圖的內容","width":1,"height":1,"caption":"一句話說這張圖怎麼看"}`，
   放在它解釋的那一節之後。
4. 一個 `{"type":"table","header":[…],"rows":[[…]],"caption":"…（寫查證年月）"}`：最多 6 欄 30 列，
   格子是純文字。制度比較、費率結構、文件清單很適合做成表。
5. 一個 `{"type":"callout","tone":"tip|warning|info","title":"…","text":"…"}`：最有價值的提醒或最常踩的坑。
6. 至少一個站內連結：`{"type":"link","text":"…","url":"https://mokaair.com/zh-TW/life/<其他篇 slug>"}`，
   放在相關段落之後。**指派會給你完整網址，照抄，不要自己組、不要連指派沒給的。**
   旅遊銜接篇的網址長 `https://mokaair.com/zh-TW/guides/<kind>/<slug>`，`kind` 是 `howto` 或 `intel`，
   是網址的一部分，弄錯就是 404——所以指派給的是完整網址，不是 slug。
   站上有一批 `taiwan-` 開頭的旅遊攻略只有英日韓與簡體版，**沒有 zh-TW**，連過去讀者會落到
   一個沒有他語言的頁面；指派不會給你那些，你也不要自己找。
7. **最後一個區塊固定是免責 `callout`**，照抄這個模板，只改中括號的部分：

```json
{
  "type": "callout",
  "tone": "info",
  "title": "這篇是資訊整理，不是投資建議",
  "text": "本文說明的是制度、費率結構與操作流程，不推薦任何個別商品，也不是投資建議。[級距、費率與申請條件]依主管機關與業者當期公告為準，本文查證日為 2026-XX-XX；實際適用請以官方資訊或合格專業人員的意見為準。"
}
```

  中括號依主題替換：稅務篇寫「級距、扣除額與申報時程」，保險篇寫「條款、給付條件與費率」，
  投資篇寫「費用、稅負與交易規則」，銀行篇寫「利率、額度與手續費」。查證日填實際查證日期。

  **`text` 裡的「不是投資建議」六個字一字不能改。** `pack_cli lint` 用它當免責聲明的標記，
  改成「不構成投資建議」「非投資建議」都會被判定成沒有免責聲明，整篇被拒。
  其他句子可以依主題調整。

所以財經文章會有**兩個 callout**（第 5 項和第 7 項），這是正常的。

區塊裡不能有 HTML、Markdown 語法或控制字元；`paragraph` 一段 ≤ 4,000 字；圖片與 hero 的 `alt` ≤ 200 字
（一句話說畫了什麼，細節放 SVG 的 `<desc>`）、`caption` ≤ 300 字、表格格子 ≤ 300 字、
`sources` 每筆 `title` ≤ 200 字（來源名稱加一句括號說明就好，細節寫進 notes.md）；
文字裡的網址一律用 `link` 區塊，不要寫在段落裡。整篇 1,800–3,000 個中文字（不含標題與表格），
寫滿一個主題就停，不要湊字。

## 6. 文字規則

- **事實先查再寫。** 級距、額度、費率、手續費、稅率、申報時程、資格條件、法規名稱，全部在今天用
  WebFetch／WebSearch 到**主管機關或業者官網**確認，寫進 `sources`（每筆都要 `checked_on`，最多 20 筆），
  也寫進 `notes.md`。**你訓練資料裡的稅率與級距多半已經過時，不能憑記憶寫。**
  查不到的就寫「以主管機關公告為準」，不要猜一個數字。
- 優先來源：財政部稅務入口網與各地區國稅局、勞動部勞保局、衛福部健保署、金管會（含保險局、
  證期局、銀行局）、中央銀行、臺灣證券交易所、證券櫃檯買賣中心、聯合徵信中心、財政部關務署、
  全國法規資料庫，以及各銀行、保險公司與券商的官網公告頁。
  **不放新聞轉述、內容農場、理財部落格、YouTube 影片、論壇貼文。**
- 金額寫新台幣；涉及外幣的寫原幣別，不自己換算成台幣。
- 法規引用寫法規名稱與條次，不抄整條條文；不做法律解釋，寫「條文規定的是什麼」而不是
  「所以你可以怎麼做」。
- 系列統一用語：綜合所得稅（不寫「個稅」）、扣除額（不寫「抵稅額」）、勞工退休金／勞退（不寫「退休金帳戶」）、
  勞工保險／勞保、二代健保補充保費、股利所得、內扣費用（不寫「管理費」代稱全部費用）、

## 7. 圖解 `diagram-1.svg` 的規格

工具會機械檢查前五條，第六條靠人看渲染圖：

1. `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 1600 900" width="1600" height="900" role="img" aria-labelledby="title desc" font-family="'Noto Sans TC','Noto Sans JP','PingFang TC','Microsoft JhengHei','Hiragino Sans',system-ui,sans-serif">`
2. 第一個子元素 `<title id="title">中文標題 / English title</title>`，第二個
   `<desc id="desc">用一段話把圖上的資訊講完，給看不到圖的人</desc>`。
3. 不能有 `<script>`、`<image>`、`<use>`、`<foreignObject>`、`@import`、`http(s)://`、`url(…)`
   （`url(#id)` 內部參照可以）。
4. **所有 `font-size` ≥ 15**（標籤 15–17、小標 18–20、大標 28–30）。
5. **圖上出現的每一個數字都必須出現在文章正文裡**（金額、比例、年份、天數、級距都算）。
   圖是正文的摘要，不是另一份資料。
6. 文字不能壓到線、跑出框、互相疊在一起：每個框留 ≥ 20 px 內距，一行中文 ≈ 字級 × 字數，先算再排；
   1600 寬的圖，一行不要超過 45 個中文字；框內文字置中用 `text-anchor="middle"`。

配色與筆法（跟站上其他圖一致）：底色 `#F7F1E8`（第一個元素
`<rect width="1600" height="900" fill="#F7F1E8"/>`），主文字 `#102A2B`，次要文字 `#5C6B6B`，
重點框 `#0D6B68` 邊、`#E3F0EF` 底，藍框 `#2F6F9F` 邊、`#E6F0F7` 底，警告 `#B8442D`，橘 `#D97A2B`，
綠 `#2E7D5B`，框白底 `#FFFFFF`、`rx="14"`、`stroke-width="4"`。箭頭用 `<defs><marker id="arrow" …>`
加 `marker-end="url(#arrow)"`。左上角 `y="52"` 放 30 px 粗體中文標題、`y="84"` 放 18 px 英文副標，
右下角 `x="1540" y="870" text-anchor="end" font-size="15" fill="#5C6B6B"` 放 `© Mokaair 製圖 2026`。

圖解的類型依內容選：決策樹（適用哪一種）、流程（申報或申請步驟）、比較矩陣（幾個制度幾個面向）、
時間軸（申報與繳納時程）、結構圖（費用或保費由哪些部分組成）、金流圖（錢從哪裡到哪裡）。
**畫的是這篇文章的重點**，不是泛用示意圖。

**不要畫任何會被讀成建議的圖**：沒有上升的績效曲線、沒有「推薦配置」圓餅圖、
沒有標示特定商品名稱的比較圖。

## 8. hero 插圖 `hero.svg`

- 同樣 viewBox 1600×900、同樣的 `<title>`／`<desc>` 與禁止項；工具會渲染成 `hero.jpg`，
  這張圖會當社群分享卡片與列表縮圖。

## 10.5 工具會拒絕你的地方（批次 01 試點記錄，2026-09-14）

這一節是查 `pack_ingest.py` 原始碼與實際跑完兩篇之後補的。這些沒有一條寫在別的系列的指令裡，
但每一條都會讓你的稿子被退回。

**流程**

- **`--dry-run` 仍然會渲染 hero，而且絕對不要加 `--no-render`。** 那個旗標不是「跳過渲染」，
  它會讓工具直接丟 `hero.svg needs a renderer` 而失敗。只用 `--dry-run`。
- 工具會**覆寫**你寫的 `hero.src`、`width`、`height`、`credit`，SVG 圖塊也一樣。欄位要在，值不用算對。
- ingest 完全不連網（自繪 hero、沒有 `images.json` 時），所以 `--dry-run` 可以一直重跑。

**JSON**

- 所有模型都是 `extra="forbid"`：**多一個不認得的鍵，整篇失敗**。
- 文字欄位拒絕 **tab 字元**，也拒絕 `<` 後面直接接字母／`!`／`/`／`?`（`n < 10` 這種有空格的沒事）。
- `heading.level` 只有 **2 或 3**；`callout.tone` 只有 **tip／warning／info**（免責用 `info`）。
- `width`／`height` 是 **strict int**：`1600` 可以，`1600.0` 或 `"1600"` 會被拒。
- `table` 的**每一列格數必須剛好等於 header 的格數**；header 最多 6 格、最多 30 列。
- 長度上限：title 200、description 500、paragraph 4000、list 1–30 項、callout.title 80／text 2000、
  表頭格 120／資料格 300、caption 200、alt 200、sources 最多 20 筆。
- 正文計字只算 paragraph／list／table／callout；標題與 caption 不算。1,800–3,000 是目標，
  1,500 只是工具的警告下限，不要瞄準它。（試點兩篇分別是 2,132 與 1,997 字。）

**SVG**

- `viewBox` 必須字面上是 `0 0 1600 900`；`<title>`／`<desc>` 必須是 `<svg>` 的直接子元素。
- `<script>`、`<foreignObject>`、`<image>`、`<use>` 全部禁止——**`<use>` 也禁**，形狀要重畫，不能重複引用。
- **整個檔案的原始文字**（含 `<desc>` 與註解）不能出現 `http(s)://`。
- `font-size` 是掃原始文字比對的，每個值都要 ≥ 15，而且**每個 `<text>` 都要明寫 `font-size`**。
- **最容易中的一條**：圖解頁尾的 `© Mokaair 製圖 2026` 讓 `2026` 變成「圖上的數字」，
  而圖上每個數字都必須出現在正文裡。既有做法是表格 caption 寫「……；查證於 2026 年 9 月。」。
  圖上其他數字同理——試點的兩張圖只放了 `6%`、`60`、`15`，三個正文都有。
  能用中文數字（第一步、第二步）就別用阿拉伯數字，可以少一個失敗點。

**畫圖：試點真的踩到的三件事**

1. **hero 不要畫成由低到高的長條。** 第一版把五個步驟畫成五根遞增的柱子，渲染出來就是一張
   「績效成長圖」——正是第 2 節禁止的視覺語言。改成**同樣大小的五個方塊排成一列**、
   前四個打勾、最後一個留白，意思就對了。順序題材用序列，不要用高度。
2. **粗線條加 `marker-end` 時，`stroke-linecap` 要用 `butt`。** 用 `round` 的話，
   圓頭會從箭頭尖端穿出去，看起來像一根刺。
3. **渲染出來一定要真的看。** 第一版圖解的階梯擠在下半部，上半有一大塊空白，
   機械檢查全過但構圖不能看。畫完先算一次整張圖的視覺範圍（最上緣到最下緣），
   讓它大致置中；有很高的元素（例如植物、箭頭）時特別容易變成頭重腳輕。

4. **前後遮蔽：前景物件會蓋住後面的線。** 批次 02 的天平圖，左盤上的吊牌比右盤上的方塊高，
   結果左邊的吊桿整條被蓋住、右邊的露出來，左盤看起來是浮空的。兩側對稱的結構，
   要確認**兩邊被前景蓋掉的程度一樣**。這和標籤壓線是同一類問題：機械檢查全過，
   只有把圖打開看才會發現。

**怎麼把圖渲染出來看**——`--dry-run` 不會把 PNG 留在工作區，要自己渲染：

```bash
cd /home/user/travel_scanner/apps/api && uv run python -c "
from pathlib import Path
from app.guides.pack_ingest import render_svg
w = Path('<你的工作區>/<slug>')
for n in ('hero','diagram-1'):
    render_svg(w/f'{n}.svg', w/f'{n}.png')
"
```

然後用 Read 工具**實際打開那兩張 PNG**。這一步沒有替代品：你看不到自己畫的版面，
標籤壓線、文字溢出、標籤互疊、前後遮蔽，機械檢查一個都抓不到。

**寫完最後再核對一次 hero 的 `alt`。** 改圖很容易忘了改 `alt`，試點兩篇都發生了。
`alt` 要描述**你最後真的畫出來的東西**，不是你原本打算畫的。

## 10.6 字數：瞄準 2,200–2,600，不要瞄 3,000

批次 01 收稿的實測：代理幾乎每一篇都落在 2,900–3,031 字，等於在寫到上限而不是寫完就停。
工具的警告區間是 1,500–6,000，所以這些都過得了機器檢查，但 brief 的編輯區間是 1,800–3,000，
貼著天花板寫有兩個壞處：一是容易為了補滿而多寫一段，二是沒有餘裕——審稿時想補一句就超線。

**下一批請瞄準 2,200–2,600 字。** 一個主題寫完就停；真的需要更長（例如 50 個名詞的速查篇）
再往上，但要能說出為什麼這篇需要。
