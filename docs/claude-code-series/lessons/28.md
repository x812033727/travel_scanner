對話變長時，Claude Code 需要在有限的上下文中保留需求、檔案與工具結果。本篇會用 /context 查看內容占用，用 /compact 整理仍要繼續的工作，再用 /clear 切換到無關的新任務。你會知道這三個指令分別是在觀察、摘要或開始新對話，不會把它們誤當成刪檔與還原功能。

請在[練習專案](article:claude-code-practice-project-setup)建立一個只讀 session，先閱讀 README、model.js 與測試，並討論篩選需求。這些內容足以做整理實驗，不需要刻意貼入大量無用文字。開始前先看[對話找回](article:claude-code-sessions-resume)，確保你知道如何回到之前的脈絡。

## 上下文包含哪些東西

上下文不只是你打出的聊天訊息，也包含系統指引、CLAUDE.md、載入的規則、工具定義與工具結果。讀入長篇日誌或大量檔案時，即使你只問了一句話，也可能增加很多內容。先理解占用來源，才能選擇有效的整理方式。

| 指令 | 主要作用 | 不會替你做的事 |
|---|---|---|
| /context | 查看目前內容與占用 | 不會修改專案檔案 |
| /compact | 摘要同一份對話 | 不保證逐字保留所有細節 |
| /clear | 開始空白對話 | 不會回復先前檔案修改 |

當工具輸出很多與問題無關的紀錄，可以先請 Claude 縮小搜尋範圍，而不是每次都等滿了才 compact。規則檔過長則應整理[CLAUDE.md 與 rules](article:claude-code-rules-and-imports)。不同來源的負擔需要不同處理，單一指令無法解決所有資訊品質問題。

## 用 /context 查看目前狀態

在對話輸入 /context，查看目前分類與提示。某些版本可展開更細的項目；先找記憶文件、工具與對話歷史占用的大方向即可，不必一開始追求每個數字都最低。真正目標是讓下一步需要的資訊仍可有效使用。

```text Claude Code 對話框：查看上下文
/context
```

例如待辦專案只有幾個檔案，但上下文已很大，可能是載入了過多外掛工具、長規則或先前無關任務。對照實際來源後，再決定是否減少不需要的內容。看到百分比高不代表程式損壞，也不代表必須刪掉整個對話歷史。

## 摘要前先留下驗收重點

compact 是摘要，摘要一定會壓縮細節。對仍在進行的任務，先明確列出目標、限制、已確認事實與下一步，能讓整理後的接續更可靠。尤其尚未解決的失敗、被否決的方案和不能改的區域，不要只埋在早期某一則訊息中。

```text Claude Code 對話框：整理前的工作摘要
請先整理目前篩選功能的狀態：
目標是全部、未完成、已完成三種顯示，不能刪掉原始項目。
列出已確認的資料結構、尚未實作部分、測試需求與下一步。
這次只整理，不改檔案。
```

核對摘要是否正確，再執行帶有重點的 compact。若摘要已把「不加入資料庫」誤寫成「之後加入資料庫」，先更正，再壓縮。不要讓錯誤摘要變成後續工作的主要依據。

```text Claude Code 對話框：保留篩選任務重點
/compact 保留篩選需求、不可刪除原始資料的限制、已確認檔案、測試結果與未完成事項
```

## compact 後重新核對

完成後再用 /context 查看變化，並要求 Claude 說明下一步。官方對不同內容有不同恢復方式：根規則與記憶可重新載入，路徑規則隨讀取觸發，先前讀過的檔案與 Skill 也有各自限制。不要把「會整理並接續」理解成每一行工具輸出都原樣保留。

```text Claude Code 對話框：確認整理沒有改變目標
請用三點說明目前要完成的功能、不能破壞的條件與下一個驗證步驟。
若有不確定的檔案細節，請重新讀取，不要依摘要猜測。
```

如果它遺漏關鍵限制，直接補上並指出這是原本要求，不是新功能。涉及精確程式碼、錯誤堆疊或測試輸出時，重新讀檔或重跑必要命令，比要求模型從摘要還原每個字可靠。保存長期重要決策時，也可寫進版本控管的任務文件。

## 何時使用 /clear

當你要切換到無關工作，例如篩選已收尾，接著只想整理另一份文件，就可以開始新對話。先命名或留下收尾紀錄，再 clear。新對話保留適用的專案指引與記憶機制，但不應假設它還知道剛才所有細節。

```text Claude Code 對話框：為前一段工作命名並開始新對話
/clear todo-filter-notes
```

clear 不會刪除磁碟檔案，也不會撤銷 Git 提交或外部操作。若目的是回復剛才改壞的程式，請看[Checkpoint 與 rewind](article:claude-code-checkpoints-rewind)，並檢查 Git 差異。把對話清空後程式仍然被改，是正常的狀態分離。

## 常見問題與小練習

你也可以先把已確認的長日誌整理成短紀錄：保留執行命令、退出結果、第一個失敗與必要上下文，原始紀錄另存檔案。之後只在需要時讀取那個檔案，不必在每一輪對話重貼全部內容。這種整理會讓錯誤仍可追查，同時讓目前任務保持清楚。

摘要後若要繼續修改，先用一個可驗證的小步驟重新建立基準，例如讀取剛改過的函式並跑相關測試。確認摘要與磁碟一致後再往前，比直接要求一次完成剩餘所有工作更容易發現偏差。

整理後答非所問，先核對摘要是否保留驗收條件；clear 後找不到原脈絡，使用 resume 找回已保存的對話；占用很快又增加，檢查是否反覆載入同一批長日誌。不要把頻繁 compact 當成效率目標，應縮小不必要的讀取與任務範圍。

> 上下文整理不能代替版本管理。對話摘要幫助接續判斷，真正的檔案版本仍要用差異、測試與 Git 紀錄確認。

小練習是比較整理前後的上下文，確認同一份篩選需求仍完整，再 clear 開新對話問一個無關的小問題，最後用 resume 回到原任務。完成判準是能分清楚三個指令的用途、知道哪些資訊需要重新讀取，而且沒有把對話操作誤認成檔案還原。想進一步降低不必要用量，可閱讀[效率與成本調整](article:claude-code-usage-cost-optimization)。
