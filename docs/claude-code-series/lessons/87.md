讓專責代理審查程式，可以分開檢查資料邏輯與畫面，但兩份回報不會自動變成兩次獨立驗證。本篇建立唯讀的 data-reviewer 與 ui-reviewer，要求每項發現都有位置、條件與影響，再由主工作階段重現、去重並駁回沒有依據的意見。

先讀[Subagents 入門](article:claude-code-subagents-guide)、[紅綠除錯](article:claude-code-tdd-debugging-workshop)與[Skill 評分](article:claude-code-skill-regression-testing)。下載[第 87 篇材料](https://mokaair.com/tutorials/claude-code/advanced/lesson-87.zip)，開啟 starter。需要可使用 Subagents 的 Claude CLI 和 Node.js 22；閱讀約 20 分鐘，實作約 45 分鐘。

## 先定義專責角色的輸入與責任

資料代理處理 model.js、filter.js、測試和 toggle.diff，查看 id、狀態切換與來源資料是否被修改；畫面代理處理 app.js、index.html、style.css 和 render.diff，追查輸入如何渲染及互動是否合理。兩者都只讀，不修改、不提交、不使用外部服務。

先讓主工作階段列出待審差異與驗收條件，再交給角色。不要只說「幫我找問題」就讓每個代理重讀整個專案；那會增加重複閱讀，也可能讓兩者都只注意同一個明顯問題，卻漏掉另一個領域。

材料的兩份 diff 是審查輸入，不代表已套用到目前程式。代理回報時應分清楚目前檔案與 diff 提議的變更，不能引用不存在於現場的錯誤行為當作已重現。需要驗證時，主工作階段在獨立副本套用最小變更再測試。

## 建立唯讀代理文件

把 agents/data-reviewer.md 和 agents/ui-reviewer.md 複製到 .claude/agents，確認完整檔名與位置。這些是 Claude 專責代理定義，不是 CLAUDE.md，也不會因為放在一般 agents 素材資料夾就自動載入。

```markdown 寫入 .claude/agents/data-reviewer.md
---
name: data-reviewer
description: 唯讀審查待辦資料邏輯，回報有位置與重現條件的問題。
tools: Read, Grep, Glob
---

只處理 model.js、filter.js、tests 與 fixtures/toggle.diff。
不修改、不提交、不使用外部服務。
每項發現列出檔案行號、觸發條件、影響與驗證狀態。
沒有執行的測試列為待驗證；找不到問題可以明說。
```

這裡的 tools 限定代理可用工具，因此它不能實際執行測試或啟動瀏覽器。回報中的「未執行」是預期的誠實界線。若你希望它執行命令，需要另外擴充範圍與驗證；不能保留唯讀工具設定，卻要求它聲稱測試已通過。

在新的 Claude 工作階段使用 /agents 查看可用來源，確認兩個代理都能找到。若讀者使用的版本或組織政策不支援，保留文件及手動審查流程，將真正的代理啟動標為待測。文件語法通過不等於角色已實際運作。

## 提供兩個可獨立完成的審查任務

主工作階段先指定各自的輸入與預期回報，不讓兩位代理同時改同一份檔案。本課只做閱讀，所以可以平行檢查；後續真正修正由主工作階段統一處理。這樣審查意見不會在驗證前就直接變成修改。

```text Claude Code 對話框：請主工作階段分派審查
請使用 data-reviewer 審查 fixtures/toggle.diff，核對 id 與狀態契約。
請使用 ui-reviewer 審查 fixtures/render.diff，追查標題來源與 DOM 渲染。
兩者只讀，分別回報位置、條件、影響、證據與未執行項目。
不要讓角色自行修正、提交或建立 PR；收到結果後先由你核對。
```

觀察實際代理啟動紀錄與完成回報，保存每個角色的輸入。不要只因主工作階段說「已請專家檢查」就當成真的建立兩個代理；若介面或日誌無法確認，記錄證據不足。也不要把你手動讀過的結論偽裝成代理獨立發現。

角色之間可以需要相同的少量共同契約，例如 id 必須穩定，但不必複製全部對話。將必要背景寫清楚，避免代理因缺少需求而猜測。當任務邊界變動，重新提供更新後的範圍，不要求角色靠別的對話自行得知。

## 主工作階段逐項核對

收到發現後，先確認引用的檔案與行號存在，再看觸發條件是否能產生描述的影響。資料代理指出比較反轉時，用兩筆不同 id 的資料重現；畫面代理指出 innerHTML 風險時，追查不受信任文字是否真的進入該渲染位置。

不要只因兩位代理提出相同意見就加倍信心。它們可能引用同一段文字或受到相同提示影響。將重複發現合併成一項，保留各自證據來源；真正需要的是獨立可重現的條件，不是相同結論出現的次數。

```markdown 寫入 review-verification.md 的核對格式
# 主工作階段核對
發現識別：
提出角色：
檔案與行號：
具體觸發條件：
實際重現命令或瀏覽器步驟：
結果：採納／駁回／待驗證
理由及未完成項目：
```

駁回也要有理由。例如只是修改 h1 文案，卻被說成沒有驗證輸入的漏洞，主工作階段應指出沒有連到資料流的證據。不要把所有「可能」都變成正式缺陷清單，讓讀者承擔不必要的修正工作。

## 再做正常與資訊不足的對照

使用 clean.diff 測試沒有已確認問題的情境。若要交給角色，先明確擴充該次讀取範圍，避免角色為了讀對照檔自行忽略其原定 scope。預期能說明沒有足夠證據支持缺陷，而不是一定要交出至少三個問題。

再提供缺少相關檔案的差異，觀察代理是否指出資訊不足。這個結果不應被當成能力差而扣分；在沒有資料時誠實停止，正是可維護流程需要的行為。主工作階段補上必要檔案後再重跑，確認新證據如何改變判斷。

角色工具限制也會影響證據種類。只有 Read、Grep、Glob 的代理可以做靜態分析，不能用自己的敘述取代瀏覽器實測。由主工作階段或讀者執行實際驗證後，再把狀態從待測改成已確認。

## 修正與最終驗收由整體流程負責

採納的問題依[紅綠除錯](article:claude-code-tdd-debugging-workshop)建立失敗案例，再做最小修正。修正後重跑相關測試，必要時再請角色檢查差異，但不要把「角色完成」當成整套功能完成。最終仍要確認原需求及所有採納發現的狀態。

若多個角色都需要修改檔案，先使用[Worktree 整合](article:claude-code-worktree-integration-workshop)或明確分配寫入範圍。唯讀審查容易並行，不代表有狀態的實作也能直接套相同模式。共用設定、暫存檔與埠號仍可能互相影響。

| 回報情況 | 主工作階段處理 |
|---|---|
| 有位置、條件及可重現結果 | 採納並連到修正驗證 |
| 相同根因由多角色提出 | 去重，保存證據來源 |
| 只有泛泛建議 | 要求具體依據或駁回 |
| 缺少資料、未執行測試 | 保留待驗證，不假報完成 |


## 由主工作階段統一判斷衝突建議

兩個審查代理可能對相同修改提出不同建議。主工作階段先找出各自引用的檔案與條件，再以需求和測試判斷，不用多數票決定程式是否正確。若其中一份建議超出指定範圍，記錄原因並忽略該項，保留可驗證的部分。

整合報告時去除重複發現，但不要刪掉不同觸發條件。例如相同一行程式可能同時造成資料遺失與顯示錯誤，兩項都需要各自的重現方式。最後交付一份含檔案位置、影響、修正建議和實測限制的清單，讓使用者能逐項處理。

代理名稱出現在畫面上，只能證明建立了角色；需要查看它實際讀取的內容與回報，才能判斷分工是否發揮作用。本文的角色檔和假 diff 是可重現材料，實際多代理操作仍要在可用的 Claude 工作階段中完成。

## 完成判準與小練習

交付兩份代理 MD、實際分派紀錄、各自報告與主工作階段核對表。每個採納發現都有獨立驗證，未執行項目保持清楚。若只有手動角色演練，文件應如實標示，不能寫成已通過真正 Subagent 整合。

小練習是讓兩個角色收到同一份 diff，但給不同明確檢查範圍，再比較重複與互補之處。記錄總耗時與核對工作，而不只看角色數量。需要更多角色直接協調時，再進入[Agent Teams 實驗](article:claude-code-agent-teams-integration-lab)，比較額外協調是否值得。
