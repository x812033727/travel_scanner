舊專案可能把自訂指令放在 .claude/commands/，新教學則使用 .claude/skills/。本篇會保留既有呼叫習慣，將一個簡單審查指令移轉成 Skill，並檢查名稱、參數、附屬檔案與工具授權，避免移動檔案後表面可用、實際流程卻不同。

先閱讀[技能主檔](article:claude-code-skills-skill-md)與[參數用法](article:claude-code-skill-arguments-resources)。你可以從乾淨的練習專案開始建立下面的舊格式範例，不需要先找到真正的舊專案。實際團隊移轉時，先保存 Git 基準並盤點使用者目前輸入的名稱。

## 舊格式仍然可以使用

目前 Claude Code 將自訂 commands 納入 Skills 的功能範圍，既有 Markdown 指令檔仍可運作。因此移轉的主要好處是把流程、範本與腳本放在同一資料夾，並使用更完整的呼叫控制；不是看到 commands 資料夾就必須立刻刪除。

內建斜線指令、自訂指令與 CLI 啟動參數仍要分開。/help 由產品提供，/todo-audit 是你新增的流程，而 claude --help 是在終端機使用的參數。只有後兩者剛好都有 help 文字，並不代表它們能互換位置。

## 建立可比較的移轉起點

在練習專案新增 `.claude/commands/todo-audit.md`，使用下面這份只讀範例。先從同一資料夾開啟 Claude Code，呼叫一次並保存回報，作為移轉前的行為基準。

```markdown 寫入 .claude/commands/todo-audit.md
---
description: 檢查待辦資料操作並列出證據。
disable-model-invocation: true
---
檢查 model.js 中新增、切換與刪除待辦的識別碼使用方式。
使用者補充重點：$ARGUMENTS
不修改檔案，不執行外部操作。
回報每個發現的檔名、條件與影響；沒執行測試就註明。
```

```text Claude Code 對話框：移轉前先記錄結果
/todo-audit 注意不存在的識別碼
```

記錄輸入、讀取檔案與報告欄位，不要求模型每次逐字輸出完全相同內容。可驗收的重點是同樣的工作範圍、相同的關鍵限制，以及沒有把未執行項目寫成通過。

## 搬到技能目錄

建立 `.claude/skills/todo-audit/SKILL.md`，先完整複製舊檔內容，再視需要加入 name。專案技能的手動指令名稱來自資料夾名稱，因此保留 todo-audit 資料夾，才能保留 /todo-audit 入口。只改 frontmatter 的 name 並不會替本機專案技能重新命名指令。

```markdown 寫入 .claude/skills/todo-audit/SKILL.md
---
name: todo-audit
description: 檢查待辦資料操作並列出證據。
disable-model-invocation: true
argument-hint: "[review-focus]"
---
檢查 model.js 中新增、切換與刪除待辦的識別碼使用方式。
使用者補充重點：$ARGUMENTS
不修改檔案，不執行外部操作。
回報每個發現的檔名、條件與影響；沒執行測試就註明。
```

確認新檔已保存後，把舊檔移到掃描資料夾以外的備份位置，再開新 session。相同名稱同時存在時 Skill 優先，但依賴這個優先順序會讓團隊難以判斷目前修改的是哪份內容；移轉完成應保留單一有效來源。

## 子目錄名稱需要另外處理

舊格式若是 .claude/commands/frontend/check.md，指令會包含子目錄命名，例如 /frontend:check。直接搬成 .claude/skills/check/SKILL.md 會改成 /check，不能只比較最後的檔名就宣稱相容。外掛技能則可能有外掛命名空間，還有不同名稱規則。

遇到這類情況先列出舊名稱與新名稱對照表，更新團隊文件及保存的提示詞。不要假設所有冒號命名都能用 name 欄位重現；需要維持舊入口時，可暫時保留舊指令並明確規劃切換日期，等使用者更新後再移除。

## 重新檢查路徑與授權

舊指令中的相對檔案引用可能因搬移失效。把範本放在技能資料夾內，並明確指出相對於哪個位置；需要穩定引用時使用 CLAUDE_SKILL_DIR。腳本不要只搬主檔而漏掉依賴，應盤點它讀取哪些設定與資料。

allowed-tools 並不是純說明欄位，它會給呼叫當回合相應的工具預先授權。移轉時逐項閱讀，移除已不需要的範圍，不能直接從網路範本帶入廣泛命令。新格式仍受正常[權限流程](article:claude-code-permissions-plan-mode)影響，名稱變了不會自動使某個操作安全。

如果舊流程包含動態 shell 內容，先在獨立練習副本檢查命令會做什麼。建立一張輸入、輸出、副作用與錯誤碼的表，再決定是否保留。單純的檔案審查範例通常不需要在技能載入時先執行程式。


移轉前也要搜尋 README、團隊文件與常用提示中的舊指令名稱。入口改名卻沒有更新使用說明，常讓使用者以為功能已壞掉。把名稱、作用範圍與停用舊版的日期列在同一份紀錄中，讓切換可追蹤。

## 完成移轉的驗證矩陣

| 檢查情境 | 預期結果 | 需要保存的證據 |
|---|---|---|
| 不帶參數呼叫 | 仍有預設審查範圍 | 實際讀取的檔名 |
| 帶重點文字 | 報告有回應重點 | 具體發現與條件 |
| 附屬材料缺失 | 明確指出缺檔 | 不捏造範本內容 |
| 新 session 再呼叫 | 只載入新來源 | 名稱與輸出結構 |

若移轉後失敗，先恢復舊指令到原位置，將新 Skill 移出掃描範圍，再開新 session 驗證恢復。不要同時保留兩份不同版本並靠反覆重啟碰運氣，這會讓之後的維護更難追蹤。

小練習是完成 todo-audit 的移轉，保存前後各一份報告與名稱對照。完成判準是入口、參數和限制皆符合預期，Git 差異能清楚看出搬移與必要調整，且知道回復方式。需要分享給多個專案時，再閱讀[Plugins 管理](article:claude-code-plugins-guide)。
