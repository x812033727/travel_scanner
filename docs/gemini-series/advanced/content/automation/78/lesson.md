一次處理二十份文件時，最難的通常不是第一次成功，而是中途停止後知道哪些已完成、哪些必須重做。本篇建立可續跑的 Headless 批次程式，用文件識別、輸入雜湊、輸出驗證與檢查點管理進度，並將固定測試資料與真實模型產出清楚分開。

## 成品、先修與使用條件

先完成 [[45|Headless 入門]] 與 [[49|API 費用及錯誤處理]]。下載 78 練習包，內含二十份合成文件、pipeline.py、模型設定範例與禁止工具呼叫的政策檔。Python 程式主要使用標準函式庫；fixture 模式不需要模型帳號，也不會連線呼叫 Gemini。

本文於 2026-09-14 使用 Windows、Python 3.13.15、CLI 0.59.0 與 Node 24.19.0 驗證。實測範圍包括批次狀態、輸出契約、故障續跑及 CLI 政策模組。真實模型呼叫與費用尚未量測，不能拿 fixture 的速度、摘要品質或零費用來推估正式批次。

## 第一階段：建立可以比對的輸入

documents 目錄有 doc01.md 到 doc20.md，每份文件保留獨立身分。檔名只接受小寫英文、數字和連字號，來源檔案不能是符號連結，單檔大小也有限制。輸出目錄要放在輸入之外，避免第二次執行把自己剛生成的內容再當成新資料處理。

先閱讀幾份資料，確認它們都是作者建立的虛構活動，沒有個人資訊或金鑰。程式把內容、提示詞版本、執行模式、模型與命令設定一起算入雜湊。因此同一份文件換模型或提示詞契約後，舊結果不會被直接視為本次完成；只比較檔案修改時間做不到這一點。

```bash 終端機：先在第五份之後停止
python pipeline.py documents output --fixture --stop-after 5
```

預期結果是 processed 為 5、interrupted 為 true，命令結束碼為 3。這是教材刻意安排的中斷，不代表前五份結果毀損。打開 output/results 與 checkpoint.json，核對成品數量和記錄；每個結果都應帶 authored-fixture 標記，不會假裝是模型摘要。

## 第二階段：恢復、重跑與只重做一份

使用同一個輸出目錄再執行，不加 stop-after。程式會核對輸入雜湊、成品存在與成品雜湊，符合三項條件才跳過。若檢查點寫著已完成，但輸出被刪除或改壞，不能只相信狀態文字；這份工作應重新處理，才不會把不完整交付藏起來。

```bash 終端機：接續同一批工作
python pipeline.py documents output --fixture
python pipeline.py documents output --fixture
```

本次實測的第二次執行處理 15 份、跳過 5 份，第三次處理 0 份、跳過 20 份。接著在 doc07.md 補一行更正文字，再執行同一命令，結果只重做 1 份、跳過 19 份。這些數字來自真正執行批次程式，輸出內容仍是作者固定摘要。

| 操作 | 實際處理 | 實際跳過 |
| --- | --- | --- |
| 第五份後停止 | 5 | 0 |
| 從檢查點恢復 | 15 | 5 |
| 無變更重跑 | 0 | 20 |
| 修改一份來源 | 1 | 19 |
| 損壞一份成品 | 1 | 19 |

程式採單一寫入者模式，以 .pipeline.lock 避免兩個程序同時改同一份檢查點。正常結束會移除鎖；若電腦斷電留下舊鎖，先確認原程序已停止，備份輸出並核對檢查點，再處理它。不要看到鎖就自動刪除，否則可能讓兩個仍在工作的程序互相覆寫。

## 第三階段：驗證 CLI 外層與內容內層

真實 Headless 的 JSON 輸出包含 response 字串、統計與可能的 error。本文要求 response 裡再放一個只有 id、title、summary、quote 的 JSON 物件。因此解析分兩次：先確認 CLI 外層成功，再驗證裡面的資料契約。外層能解析，不代表模型回答一定符合你的格式。

```json 內容契約示意，非模型實際輸出
{
  "id": "doc01",
  "title": "海風活動 01",
  "summary": "這裡必須是依原文整理的摘要。",
  "quote": "# 海風活動 01"
}
```

驗證器檢查欄位集合、文件 ID、文字長度與引用句是否真的存在原文。故意把 quote 換成不存在的句子，應得到 quote_not_in_input。這能抓出一種明顯錯誤，但不能證明整段摘要沒有誤解；即使引用句正確，摘要仍須回到來源核對，尤其涉及數字、日期或否定句時。

如果改用 stream-json，會收到多行事件。tool_result 只表示一次工具結果，message 也可能只是局部文字，都不能當成整份完成。教材的分類器要求最後有唯一且成功的 result，仍將內容契約標成未驗證；事件流結束與業務資料合格是兩個條件，不能省掉第二層檢查。

## 失敗、重試與成本怎麼處理

本教材每次最多處理二十份，逐份執行；遇到失敗就保存原因並停止後續工作，不做無限制重試。程序退出非零、結果不是 JSON、缺少最後回答或引用錯誤，都不能寫成已完成。你可以修正原因後再從檢查點執行，已驗證的成品會保留。

逾時尤其需要小心：你沒收到結果，不代表服務端一定沒有處理或計費。因此教材不自動重送逾時請求，也不宣稱付款上的「恰好一次」。本機成品避免重複、API 實際呼叫次數、SDK 內部重試與帳號費用，是不同層次的問題；需配合真實用量紀錄判斷。

每份成功先寫成品，再寫檢查點，最後附加 journal.jsonl。若中斷發生在成品寫好但檢查點未完成之間，下次可能重新生成那份資料；它會檢查並替換指定成品，不會任意追加一份同名結果。這是可理解的恢復策略，不能將它描述為跨所有系統的交易保證。

> 本批已實測二十份文件的中斷、續跑、單份修改、成品損壞、寫入鎖及失敗停止。CLI 政策判斷另有實際模組紀錄；雲端摘要、延遲與計費尚未量測。

## 常見問題

### 為什麼切換模型後全部重新處理？

模型與提示詞契約是結果來源的一部分，換了條件就不能沿用舊成功標記。先小批量驗證，避免沒有核對用量就重做整批。

### 中途失敗要刪掉所有 output 嗎？

不需要。先看 run-summary.json 與 journal，修正失敗來源，再使用原檢查點。若要做新實驗，選新的輸出目錄以保留比較證據。

### 可以放到 GitHub Actions 嗎？

可以依 [[79|受控工作流教學]] 從手動觸發與單份文件開始。後續做 [[80|文件維護專案]] 時，摘要與候選修正仍要分開驗證，不直接將模型文字覆蓋正式文件。
