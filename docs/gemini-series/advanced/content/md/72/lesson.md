自訂斜線指令可以把常做的程式審查、測試規劃與文件比對保存成固定入口。本篇製作三個 TOML 指令，先定義輸入與輸出，再測空參數、中文空格路徑和特殊字元，讓指令庫能被檢查、修改與交接，而不是只收集一堆看似有用的提示詞。

## 成果、版本與先修

先完成 [[40|自訂指令基礎]] 與 [[70|共用規則範本]]。下載包的 command-lab 內含 .gemini/commands/lesson/，三個檔案是 review、test-plan、docs-sync。准備 CLI 0.59.0、Node 與文字編輯器。本文於 2026-09-14 重查官方文件，以 Windows、Node 24.19.0 驗證真實指令載入器與提示詞展開。

這裡先把兩種結果分開：CLI 能否載入 TOML、能否正確送出提示詞，是本機可測的；模型最後提出的問題是否正確、測試計畫是否完整，則必須另用真實對話核對。練習包附前者的實際紀錄，後者是文中列出的驗收要求，沒有冒充模型的實際回答。

## 第一階段：先定義三個工作契約

review 只找有證據的問題，不直接改程式。test-plan 要列正常與邊界案例，沒有執行的測試只能叫建議。docs-sync 比較程式現況與文件，找不到對應程式就說待確認。把這三個任務拆開，讀者才知道自己按下某個指令後應檢查哪種成果。

| 指令 | 必要輸入 | 預期輸出順序 |
| --- | --- | --- |
| lesson:review | 檔案或範圍 | 範圍、證據、問題、待確認 |
| lesson:test-plan | 函式或需求 | 範圍、正常案例、邊界案例、預期結果 |
| lesson:docs-sync | 程式及文件 | 範圍、程式現況、文件差異、建議段落 |

空參數不能默默變成「檢查整個專案」，所以三個提示詞都要求先索取範圍。這只是提示詞約定，不能取代執行層的讀取權限；需要更嚴格限制時，再搭配工具核准與沙箱。輸出順序讓人工容易比對，不表示模型生成的結論自然就會正確。

## 第二階段：建立容易辨識的命名

從 command-lab 根目錄開啟 CLI。子目錄 lesson 會形成命名空間，例如 lesson/review.toml 對應 /lesson:review。指令檔名使用簡單英文，中文留在 description、提示詞及工作資料；這樣可以降低終端補全與不同檔名正規化造成的混淆。

!include-code examples/72/command-lab/.gemini/commands/lesson/review.toml

TOML 的 prompt 以三引號保存多行文字，description 說明用途。{{args}} 是使用者在命令後面輸入的原始參數；它不是自動讀檔器。請求處理某個路徑後，仍要確認實際工具讀到了正確檔案，尤其是相同檔名散落在不同模組時。

建立或修改檔案後先輸入 /commands reload，再用 /commands list 核對檔案來源。若全域也有同名命令，要確認實際使用的是專案版本。清單沒有出現時先查 TOML 是否缺 prompt，不能只反覆重開終端機，忽略載入器已經提供的格式診斷。

```text Gemini CLI 內輸入
/commands reload
/commands list
/lesson:review 文件 範例/brief.md
/lesson:test-plan src/title.mjs
/lesson:docs-sync 程式：src/title.mjs；文件：README.md
```

後兩行展示如何指定任務，若你的練習目錄沒有那些檔案，應先指向真實存在的樣本或讓助手回報缺檔。不要為了得到漂亮回答就接受它虛構的檔案內容。command-lab 已提供「文件 範例/brief.md」，可先用第一個命令完成路徑辨識練習。

## 第三階段：測參數，不把文字變成 shell

先使用空參數，觀察是否要求範圍；再依序輸入英文檔名、中文與空格路徑、單引號、雙引號，最後輸入含分號與 $() 的純文字。這三個教材 TOML 沒有 !{...} shell 插入區塊，因此本機展開階段只會保留參數文字，不應自行執行裡面的內容。

```text 參數測試文字：只貼入本篇的純提示詞指令
文件 範例/brief.md
It's a test
a "quote"
x; $(echo NEVER_EXECUTE)
```

實際載入器驗證跑了三個命令乘六種參數，共十八組展開，回傳類型均為 submit_prompt，參數完整出現在指定位置。這只能證明提示詞傳遞正確，不表示後續模型不會提出工具請求；在真實對話中仍要查看工具紀錄，並依自己允許的範圍核准操作。

若未來加入 @{...} 檔案插入或 !{...} shell 插入，處理順序、權限與錯誤方式都會改變，不能沿用本篇十八組測試就宣稱新版本安全。特別不要把 {{args}} 改寫成自行拼接的 shell 命令。純提示詞版能滿足這三個任務時，先維持小而可測的設計。

## 第四階段：故障、重新載入與版本紀錄

複製一份故障 TOML，只放 description、不放 prompt，再執行 reload 與 list。本機載入器測試確認它會被排除，原三個有效命令仍能載入。修正後再載入才算恢復，不應把「無效檔案被略過」誤寫成「全部命令正常」。每次保存變更也核對是否仍有 {{args}} 漏在最終提示詞。

另一個反例是未信任的工作區：啟用資料夾信任檢查後，載入器回傳零個自訂命令。這與格式錯誤的三個成功、一個排除不同。診斷時先分清楚是整個來源被限制，還是只有某一個檔案壞掉，再回到正確的設定處理，不要任意放寬所有目錄。

本篇驗收表另外列出模型階段：review 的問題需有檔案與重現條件，test-plan 的每個案例需有具體預期結果，docs-sync 不得假裝已修改或已執行。若模型只是按標題排版卻沒有證據，仍屬不合格。把原問題、模型名稱、日期與實際回應保存後，才比較不同提示詞版本。

> 本篇已實測三指令載入、十八組參數展開、缺 prompt 與不信任工作區反例。雲端模型回答品質尚未實測；文中的回答格式是驗收契約，不是實際生成紀錄。

## 常見問題

### 把中文路徑加引號就一定能讀到嗎？

參數替換會保留引號與空格，但文字提示詞仍需由助手辨識路徑。用工具紀錄核對真正讀到的檔案；找不到時先列出該資料夾，而不是直接猜一個相似名稱。

### description 出現在清單就代表提示詞沒錯嗎？

只能證明基本載入與顯示可用。仍需測參數展開、讀取來源與模型成果。更改 prompt 後要 reload，測試也應使用新版，避免拿昨天的輸出證明今天的檔案。

### 要怎麼分享給另一個專案？

可以將三份命令與操作表一起複製，先確認名稱不衝突，再做相同測試。若還有腳本、參考資料或技能觸發需求，接著讀 [[73|技能與擴充套件打包]]，把安裝、更新與回退一併整理。
