改了 settings.json 卻沒有看到預期效果，不一定是檔案位置錯了；也可能是其他來源覆蓋、資料型別不對，或該工作區尚未受到信任。本篇以八組互相獨立的設定案例，建立可重做的除錯順序，讓每個觀察都能追到版本、來源與實際有效值。

## 成品、版本與準備

先讀 [[38|settings.json 基礎]]，完成 [[69|隔離環境實驗]]。下載包包含八個 settings-cases 子目錄，每組有 user.json、workspace.json、system.json。這些是準備用的測試輸入，不會因為放在這些名稱下就自動生效；實際位置仍是使用者或專案的 .gemini/settings.json，系統來源另有對應路徑。

本次於 2026-09-14 以 Windows、Node 24.19.0、CLI 0.59.0 的真實 loadSettings 載入器實測八組。來源路徑、環境變數與設定檔都在新建暫存區，沒有更動既有個人設定。正文的實際結果指載入器輸出，不是每個互動 UI 控制項均已人工點選驗收。

## 第一階段：保存可以還原的基準

先記錄 gemini --version、node --version、目前目錄與完整啟動命令。把正式設定另存到你管理的備份位置，只在新的練習資料夾操作。第一次測試不要帶模型或其他額外引數，否則很難判斷畫面變化來自設定檔還是命令列。分享診斷時只列非秘密的測試值。

使用者設定與專案設定會合併，系統管理的強制設定又可能覆蓋它們。這裡先比較相同的 ui.theme：使用者為 DefaultLight，專案改為 DefaultDark，最後加入系統 GitHub。比對時固定其他條件，避免一次把模型、工具權限和色彩都改掉。

若你沿用前篇的隔離家目錄，可把第一組 user.json 的內容複製到測試家目錄 .gemini/settings.json，再把 workspace.json 複製到測試專案同名檔。原來的 GEMINI.md 不必跟著改。每次換案例先退出 CLI、核對新檔案內容，再從同一根目錄重新啟動；不要同時開多個會寫設定的實例。

## 第二階段：一次只改一個來源

第一組只有使用者值，實際得到 DefaultLight。第二組加入專案值，得到 DefaultDark。第三組加入系統強制值，得到 GitHub。系統路徑在教材驗證中以專用環境變數指向暫存檔，沒有把練習值寫入電腦的 ProgramData；一般讀者可以先完成前兩組，再閱讀第三組的可重現紀錄。

第四組示範設定值中的環境變數展開。user.json 使用 ${LESSON_MODEL}，測試程式設定一個刻意不存在的模型標記，再確認載入器輸出相同文字。這只驗證字串替換，沒有呼叫模型，也不代表該模型可用；不要把這個標記當成真正模型名稱去送出對話。

```powershell PowerShell：非秘密的測試標記
$env:LESSON_MODEL = "offline-sentinel-not-a-real-model"
```

若正式環境需要選模型，回到目前官方模型清單核對可用名稱。環境變數替換成功、CLI 接受設定、帳號可用模型，是三個不同檢查。本文不在其他地方重列價格與額度；需要評估實際呼叫時再讀 [[49|API 計費與錯誤教學]]，並確認使用的認證管道。

## 第三階段：讓錯誤自己浮現

第五組放入 lessonUnknownField。0.59.0 的載入器保留該未知鍵，本次沒有警告，但這不會憑空新增功能。這是「設定物件裡看得到」與「程式有讀取並使用」的差別。不能因為 JSON 解析成功，就把未受支援的欄位推薦給其他人。

第六組把 ui.hideWindowTitle 寫成文字 not-a-boolean。實測出現 Expected boolean, received string 警告；載入後仍能看到錯誤的原值。修正方式是將它改成真正的 true 或 false，重新載入後確認警告消失。不要把這次「只有警告」推論成所有設定錯誤都安全或都會被忽略。

第七組故意留下不完整 JSON，載入器直接拋出 fatal configuration error。先修括號與引號，讓檔案可以解析，再討論優先順序。Python 的 json.tool 可先檢查純 JSON 語法；它不認識 CLI 的所有欄位與型別，因此語法通過後仍須讀取 CLI 自己的診斷。

```bash 終端機：先核對練習檔語法
python -m json.tool settings-cases/02-workspace/workspace.json
```

## 第四階段：比較信任與升級條件

第八組使用與第二組相同的主題值，但把工作區設為不信任。實際合併結果回到使用者的 DefaultLight，專案 DefaultDark 沒被套入。這是在診斷來源，不是鼓勵關掉信任檢查；真實環境應先理解新目錄的內容，再決定是否授予信任。

| 案例 | 實際觀察 | 判斷重點 |
| --- | --- | --- |
| 只有使用者 | DefaultLight | 基準存在 |
| 加入專案 | DefaultDark | 專案來源覆蓋 |
| 加入系統 | GitHub | 系統強制來源 |
| 環境變數 | 替換成測試標記 | 未驗模型可用性 |
| 未知欄位 | 保留、無警告 | 不代表有功能 |
| 型別錯誤 | 有警告、保留錯值 | 修正型別 |
| JSON 損壞 | 致命設定錯誤 | 先修語法 |
| 不信任工作區 | DefaultLight | 專案值不套入 |

升級前把八組結果另存，加上版本與實際命令。升級後在第二份隔離目錄重做，不直接覆蓋舊紀錄。本篇只測了 0.59.0，沒有捏造新舊版本比較結果；migration-checklist.md 留給你填入真正測量值。若某個鍵被移除，先從官方 schema 查替代位置，再寫轉換步驟。

## 如何把修正搬回正式專案

回到正式檔案只修改已定位的那個鍵。檢查差異，確保沒有連同範例的主題、假模型值或隔離路徑整份貼回去。重新啟動後再次核對行為與診斷，保留原有工具、認證與其他不相關設定。成功的交付是一段能說清楚來源的修正紀錄，而不只是一張不同顏色的截圖。

> 教材中的未知鍵與型別錯誤是故障樣本。它們用來觀察 0.59.0 行為，不是可直接沿用的設定建議；完整實際值見練習包 verified-local.json。

## 常見問題

### 為什麼 /settings 沒顯示某個鍵？

不是所有設定都一定出現在互動對話框。先核對同版本的設定參考與實際來源檔，再確認程式是否使用該鍵。不要只因找不到控制項，就把舊版網路文章的路徑拼進設定。

### JSON 沒錯，為什麼仍然出現警告？

語法與資料型別是不同檢查。雙引號包住的 false 是文字，沒有引號才是布林值。看診斷指出的完整欄位路徑，修正後重新測量，不要只刪掉警告文字。

### 所有自訂內容都應放 settings.json 嗎？

重複提示詞應做成 [[72|TOML 指令庫]]，專案文字要求則由 GEMINI.md 管理。先確認你要改的是程式選項、自然語言指示，還是一次工作流程，才能選對檔案與驗證方式。
