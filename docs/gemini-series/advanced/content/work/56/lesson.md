每週摘要最需要的，是固定資料範圍與可停止的執行方式。本篇用 Gemini Spark 整理三個 Google 官方資訊入口，先手動驗證一次，再建立每週排程，保存來源、發布日期與執行紀錄。你會分辨「沒有更新」「來源取不到」與「任務還沒執行」，並練習暫停、恢復及刪除。

## 學完成果與準備

先讀 [[16|Spark 任務與使用條件]] 及 [[13|研究報告來源查核]]。依 2026-09-14 官方說明，Spark 需要年滿十八歲的個人 Google 帳號、Google AI Pro 或 Ultra，以及開啟 Keep activity 活動記錄；部分地區不提供。台灣讀者仍要以自己帳號是否出現入口為準，工作或學校帳號不能直接套用個人帳號條件。

價格、額度與方案集中查 [[2|方案教學]]。本篇不重複容易變動的數量限制，也不把一般 Gemini 的排程動作與 Spark Schedules 當成同一套介面。要完成本篇驗收，需要可用 Spark 帳號與等待真實觸發的時間；本機程式不能替代這兩個條件。

下載包有任務範本、六步觀察表與期間檢查程式。本文尚未建立 Spark 排程，沒有真實每週執行輸出。已執行的是合成資料的日期與來源狀態測試；範例新聞使用 example.invalid 明確標示虛構，避免把作者示意當成 Google 公告。

## 第一階段：先限定摘要任務

先選三個固定入口：Google 官方 Gemini 部落格、Google Workspace Updates，以及 Gemini API 更新紀錄。它們分別涵蓋應用產品、工作套件與開發者介面。任務可追到這些入口的具日期文章，但不能因為取不到其中一站，就自行換成未審查的社群貼文。

將摘要期間寫成明確起訖與時區。例如九月十四日執行時，查九月七日零時起、九月十四日零時前的資料，使用 Asia/Taipei。這是左含右不含的區間，避免相鄰兩週重複計入邊界文章。若來源只有日期而無時刻，保留原精度，邊界有疑義時標待確認。

每項摘要記錄發布日、標題、實際連結、支持結論的原文與可用條件。新文章提到功能推出，不代表所有帳號已取得；整理時分開寫官方公告與自己的可用性觀察。對讀者沒有影響的純宣傳項目可省略，但要留下取捨標準，避免每週摘要的範圍任意漂移。

## 第二階段：先手動跑一次並查核

在 Gemini 網頁切換至 Spark，貼上任務範本並補上當次期間。第一次只產生文字，不連接私人郵件、不寄信，也不要求購買或訂閱。開始後保存任務入口與時間；若頁面顯示正在執行，先觀察狀態，不因等待就重複提交同一份工作。

拿到結果後逐項開啟來源，核對發布日是否落在期間、摘要是否受原文支持，以及是否提到帳號或地區限制。來源狀態分成 read 已讀取、unavailable 無法取得、needs_date 日期待確認。只有確實讀到來源且沒有符合期間的內容，才可以寫「本週未找到符合條件的更新」。

若某站無法取得，讓結果直接列出缺口與影響，不把它解讀為該產品沒有新消息。若引用落到首頁而找不到指定文章，就回到來源補查；查不到時移到待確認，不補寫一個看似合理的標題。人工查核後保存原始輸出與修正版，先不要刪掉錯誤紀錄。

## 第三階段：建立每週排程並觀察一次

只有手動內容符合要求後，才在 Spark 的 Schedules 排程區建立任務。依官方文件可在對話中設定，也可選 Create manually 手動建立，填寫名稱、執行時間與指示。名稱可用「Google AI 每週來源摘要」，時間設每週一上午九點，明確指定 Asia/Taipei。

儲存後打開排程詳情，核對頻率、時區、指示及下一次預定執行時間。不要只相信對話裡「已設定」的文字。官方說明排程時間可能受到額度或同時執行任務影響，不保證精確到指定分鐘；因此紀錄要分開保存預定時間、實際開始及完成時間。

真正等到一次排程觸發後，將輸出與來源查核填到 schedule-log.csv 的 scheduled 列。手動按開始不能冒充排程成功；改電腦時間、跑本機測試或建立其他工具的提醒也不能代替 Spark。若沒觸發，先查看排程狀態、時區與額度，再記錄失敗原因，不悄悄手動補跑後標成功。

排程使用建立時設定的時區；旅行或裝置時區改變時，仍要回到詳情確認下一次時間，不能假設它會自動跟著所在地調整。每週相對期間也應在結果展開成絕對日期，方便你事後核對是哪一週，而不是只留「最近七天」。

| 控制 | 需要核對的結果 |
| --- | --- |
| Pause 暫停 | 排程狀態改變，另查執行中工作 |
| Resume 恢復 | 狀態與下一次時間正確 |
| Stop 停止 | 當次工作停止，不等於取消未來排程 |
| Delete 刪除 | 列表消失，再觀察原定下一次時間 |

> 來源無法取得，不等於沒有更新。排程尚未觸發，也不能用手動完成或本機測試改填為成功。

## 第四階段：故障練習與停止驗證

先複製合成 JSON，把唯一文章日期改到區間外，程式應拒絕；再把文章來源改成 unavailable 的那一站，也應拒絕。修正時回復實際日期與來源狀態，不為了通過檢查改寫文章發布日。這是在本機可重做的故障練習，與真實任務能否取到網站分開驗證。

在自己的練習排程詳情，使用更多選單中的 Pause 暫停，確認狀態改變；再用 Resume 恢復，核對下一次時間。暫停後若有一個任務已經開始，不能只靠排程狀態判斷它也已停止；應另檢查執行中的工作。關閉瀏覽器也不代表 Spark 停止。

需要結束目前工作時，使用 Spark 對話的 Stop；需要取消未來工作時，在 Schedules 刪除對應排程，兩個動作分開確認。刪除前核對名稱，完成後重開列表，確認該排程不存在。官方亦說明刪除相關任務對話會刪除排程，但本練習保留必要紀錄後，以排程管理介面清楚操作。

最後觀察原本下一次應觸發的時間，確認刪除後沒有新工作。如果還沒等到那個時間，就把 next_time_check 留在 not_run；立即看見列表消失，只能證明當下已刪除。完整交付需手動與真實排程輸出、暫停與恢復狀態、刪除紀錄及下一次時間觀察，不提前宣稱整套已驗收。

## 常見問題

### 找不到 Spark，可以先用一般聊天替代嗎？

可以練習摘要範本與人工查核，但要標為一般聊天練習，不能算 Spark 排程驗收。先確認帳號、方案、活動記錄與地區條件。

### 任務晚幾分鐘才開始就是失敗嗎？

不一定。排程不是精準計時器，應先查實際狀態與原因；若工作有嚴格期限，另訂可接受延遲與人工接手方式，不把預定時間當成完成保證。

### 刪除後為什麼還要等下一次時間？

因為「列表已刪除」與「不再觸發」是不同觀察。保留下一次時間的驗證，才能完整交接停止結果；等待期間不要建立另一份同名任務造成混淆。
