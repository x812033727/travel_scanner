# 搜尋最佳化名詞系列：撰稿指令（每篇原文重用）

你要為 Mokaair（一個台灣的旅遊網站）的「生活分享」專區寫**一篇**搜尋最佳化名詞的解說文章。
你會拿到這份指令加一段「指派」（在 `catalogue.json` 裡）；產出是一個工作區目錄，之後由
`python -m app.guides.pack_cli ingest` 驗證、渲染、寫進 repo。

**先讀 [`docs/life-ai-series-brief.md`](../life-ai-series-brief.md) 全文**：`pack.json` 的形狀、
區塊骨架、SVG 的配色與尺寸規則、台灣用語、交出前自查清單，全部沿用那一份。
這份只寫**這個系列特有的**規則，衝突時以這份為準。

## 這個系列在做什麼

這組名詞——SEO、GEO、AEO、AIO、LLMO、E-E-A-T、結構化資料、llms.txt——的中文搜尋結果幾乎全是
行銷公司的內容，彼此定義互相矛盾。

**所以這系列的價值不是「再給一個定義」，而是把各家定義的分歧點講清楚。**
讀者讀完應該能分辨：眼前這篇行銷文用的是哪一種定義、它的主張有沒有一手來源、
哪些部分從外面根本測不出來。

讀者是台灣的一般網站經營者與內容工作者，不是 SEO 從業人員。

## 交付物

全部放在 `docs/ai-search-series/staging/<slug>/`，寫檔順序照這個：

| 檔案 | 內容 |
| --- | --- |
| `pack.json` | 內容包，**先寫這個** |
| `diagram-1.svg` | 自繪圖解，至少一張 |
| `hero.svg` | 自繪 hero 插圖（本系列全部自繪，不用 Commons 照片） |
| `notes.md` | 查證記錄：每個數字、功能名、「誰說了什麼」一行，`主張｜來源網址｜查證日｜實際讀取方式` |
| `research.json` | `{"slug","status":"verified"\|"needs_evidence","checked_on","sources":[{"url","title","access","claims":[]}],"running_text_characters":N,"notes":""}` |

**只准在自己的 `staging/<slug>/` 寫檔。** 不要碰 `apps/api/app/guides/content/`、
`apps/web/public/guides/`、別人的 staging 目錄、任務票或 `catalogue.json`。
批次 01 有代理「清理」掉協調者已經收進去的文章，不要重演。

自驗只能加 `--dry-run`（它什麼都不會寫）：

```bash
cd apps/api && uv run python -m app.guides.pack_cli ingest \
  --from ../../docs/ai-search-series/staging --slug <slug> --dry-run
```

## 內容包欄位（11 篇一致）

`kind: "life"`、`destination_id: null`、`topics: ["ai", "tutorial"]`、`valid_until: null`、
`featured: false`、`display_order: 100`。`hero.src` 是 `/guides/<slug>/hero.jpg`，
`width`／`height` 先填 1，`credit` 不要填，工具會覆寫。

## 不承諾成效——這是本系列的核心規則

- **不寫「做了會被引用」「排名會上升」「AI 曝光會增加」。** 站上的 `docs/seo.md` 已經明文
  拒絕承諾索引與排名，不可以換一個縮寫又寫回來。
- **每個主張分三級，並在句子裡標明是哪一級：**
  1. **官方文件說明的機制** —— 搜尋引擎自己的開發者文件、廠商自己的說明中心寫的。
  2. **業界普遍做法，但沒有官方確認** —— 寫「業界普遍這樣做，官方文件沒有說明」。
  3. **廠商或代理商的行銷主張** —— 一律寫明是誰說的（「某某公司的行銷資料稱⋯⋯」），
     不可以寫成無主詞的斷言。
- **沒有前後對照數字、沒有「提升 X%」、沒有案例成效。** 我們沒做過實驗。
  論文有數字就寫「該論文在它自己設定的查詢集上量到⋯⋯」，並寫出那個設定是什麼，
  絕不推廣成「所以你這樣做也會⋯⋯」。
- **不用第一人稱聲稱測試過任何東西。**
- 每個實作示例都是假設案例：輸入→步驟→預期結果→失敗怎麼判讀。前面加「示例：」，
  並在文中說明未做實測。**不可以把想像的搜尋結果頁、想像的 AI 回答、想像的引用清單
  寫成觀察到的。**

## 來源

- **只收一手**：原始論文、搜尋引擎自己的開發者文件、廠商自己的說明中心、提案本身的網站、
  規範原文。
- **代理商部落格不可以當事實依據。** 只能當「確實有人這樣用這個詞」的佐證，
  而且句子裡要標明它是行銷內容。這一點在這個題目上特別重要，因為搜尋結果九成是這種東西。
- 每篇 **≥2 個獨立一手來源**。`sources` 每筆帶 `checked_on`，用**你實際查證的那一天**，
  不要抄這份指令或別篇的日期。`sources` 最多 20 筆，網址不帶追蹤參數。
- **定義有爭議的地方，`sources` 要同時放兩邊**，正文要說明採用的是誰的定義。
- 官網常被 Cloudflare 擋（403）。已知可行的讀法：OpenAI help center 文章網址後加 `.json`；
  其他站用 Wayback Machine 的最新快照（CDX 查 `statuscode:200` 再抓
  `web/<時間戳>id_/<網址>`）；或 WebSearch 限定官方網域取摘要交叉比對。
  `sources` 仍寫原始官網網址，實際讀法記進 `notes.md`。查不到就寫「以官方文件為準」，不要猜。

## 逐題的禁止與替代說法

| 題目 | 不可主張 | 該怎麼寫 |
| --- | --- | --- |
| llms.txt | 它是標準；主流引擎會讀它；放了就會增加 AI 曝光 | 它是社群提案。寫出哪些引擎表態過、哪些沒有，附日期；沒有引擎公布過消費它的證據 |
| robots.txt | 它能把頁面移出索引；它是一種安全控制 | 被擋的網址根本不會被抓取，所以上面的 `noindex` 永遠讀不到；robots 指令不是授權控制 |
| E-E-A-T | 它是排名訊號、分數，或可以用標記宣告 | 它是人工品質評分者指南裡的詞彙；評分者不排名任何東西，沒有 E-E-A-T 欄位或分數 |
| 結構化資料 | 標記能提升排名或保證被 AI 引用 | 它讓頁面**有資格**取得特定的複合式搜尋結果。寫出站方拒絕假造 FAQ／評論／商品標記的立場與理由 |
| LLMO | 可以刻意讓內容進入訓練資料；全網品牌提及能證實改變模型輸出 | 把檢索當下（可觀察）與訓練當下（外部無法驗證）分開，直說哪些主張從外面測不出來 |
| GEO | 論文的指標可以套用到任何網站或任何引擎 | 先寫論文自己的查詢集與指標定義，再寫業界用法與它的落差 |
| AIO | 它只有一個意思 | 三個現行所指（功能／服務／套裝），加一條辨識規則 |
| 量測引用 | 任何「AI 能見度分數」可測量或可稽核 | 寫清楚 referrer 日誌看得到什麼、看不到什麼；寫出報表本身的邊界 |
| AI 摘要／AI 模式 | 任何超出官方文件的排序或挑選機制說法 | 只描述有文件的機制與有文件的控制項 |

## 站方立場：標日期，不當通則

第 7（`ai-search-structured-data`）與第 8（`ai-search-llms-txt`）篇會引述 Mokaair 自己的做法：
`apps/web/app/robots.ts` 拒絕 `GPTBot`、`ClaudeBot`、`CCBot`、`Google-Extended`、
`Applebot-Extended`、`PerplexityBot` 等抓取式爬蟲，卻刻意放行 `ChatGPT-User` 與 `OAI-SearchBot`；
`docs/seo.md` 拒絕假造 FAQ／評論／商品標記。

寫成**「本站目前的做法（附查證日）」並說明理由**——

- 不是普世建議，不要寫成「你也應該這樣設」。
- 不是叫讀者照抄的爬蟲清單。
- **不可以暗示這樣做提升了本站自己的曝光**（我們沒有量測）。

## 不重複既有文章

站上已有三篇相鄰文章，它們負責「怎麼操作」：

- `google-ai-overviews-for-site-owners` —— 站長用 Search Console 看生成式 AI 成效的流程。
- `google-ai-mode-search` —— 讀者怎麼用 AI 模式追問與判讀來源。
- `chatgpt-search-vs-google` —— 讀者什麼時候該用哪一個。

本系列講**名詞與機制**，不重寫它們的操作步驟。
`ai-search-generated-answers` 與 `ai-search-measuring-citations` 最容易漂過去，
**這兩篇的第一段就要明寫「這篇不重複⋯⋯」並附上連結。**

## 結構

- **≥5 個 level: 2 的 heading**（工具低於 3 才報錯，但這個系列的標準是 5）。
- 正文 **1,800–3,000 中文字**。算法跟工具的 `_body_length` 一樣：段落＋`rich_paragraph`＋
  清單項目＋表格格子＋callout 的標題與內文；**不含**標題、圖說、連結文字與來源。
  工具的警告帶是 1,500–6,000，接不住 1,600 字的半成品——**自己數一次，寫進
  `research.json` 的 `running_text_characters`。**
- 每篇要有：1 張 hero、≥1 個 `diagram-1.svg` 圖片區塊、**恰好一個比較表**（2–4 欄為佳）、
  ≥1 個 callout、≥3 個站內連結。
- **站內交叉連結用 `rich_paragraph` 的 `article` inline**，放在相關段落裡：
  `{"type": "article", "text": "連結文字", "kind": "life", "slug": "ai-search-geo"}`。
  這是語系相對的，不寫死網域。**只連指派列出的 slug**，不要自己加。
- 全系列**不放截圖、不放產品 logo／字標／吉祥物、不放任何合作連結**。

## 圖解

沿用 `docs/life-ai-series-brief.md` 第 6、7 節的全部規則（viewBox `0 0 1600 900`、
`<title>`／`<desc>`、字級全部 ≥15、沒有外部參照、配色、hero 最多一行字）。

這個系列特別容易踩的一條：**圖上出現的每一個數字都必須原字串出現在正文裡**
（年份、版本號、數量都算）。GEO、AIO、llms.txt 三張圖天生數字多——
**能畫標籤就不要畫數字。**

圖解要畫的是這篇的分歧點或機制，不是泛用示意圖。建議形式：
辨識決策樹（聽到這個詞怎麼判斷對方指什麼）、三層對照（機制／慣例／行銷主張）、
流程（查詢展開→檢索→接地→挑引用）、範圍圖（哪些可觀察、哪些不可）。
