## 字數：README 的上限比站上實際出貨嚴

普吉跳島篇的撰稿者用 `pack_ingest._body_length` 量了 main 上 88 篇 zh-TW `howto`：**中位數 3,183 字、最長 4,178 字**，而 `pack_cli lint` 的機械區間是 1,500 到 6,000。
README 寫的 1,800 到 3,000（沿用第六批）比實際出貨的分布嚴，本批前三篇寫完都落在 3,000 到 4,050 之間，
每一篇都刪過兩到三輪，再刪就要砍規格點名的事實。

**協調者 2026-09-17 的決定：上限放到 4,200 字**（站上既有文章的最長值），不要為了湊 3,000 砍掉查證過的資訊，
但也不要超過站上既有文章的分布——澳門篇初稿 5,097 字，比 main 上最長的還長，已退回壓縮，指定可砍的是
世遺步行路線的站名清單與計程車附加費細項，官方票價、班距與入境規定一個都不砍。
第八批規劃時把 README 的字數規則改成貼近實際的區間（例如 1,800 到 4,200），或者在規格階段就把內容量壓下來——
真正的問題是規格把太多東西塞進一篇，不是撰稿者寫太長。

### intel 的字數也一樣

農曆新年篇的撰稿者量了 main 上 17 篇 zh-TW `intel`：**實際區間 1,574 到 2,174 字、中位數 1,794，沒有一篇低於 1,500**，
而 README 寫的是 800 到 1,500（`pack_cli lint` 的機械區間是 700 到 3,000）。本篇 2,153 字，刪過兩輪，主表就占 617 字。

**協調者 2026-09-17 的決定：intel 的上限比照辦理，定在 2,200 字。** 理由和 howto 那條一樣：規則沿用第六批，比站上實際出貨嚴。

### 香港那列引用「每個星期日」

規格的注意事項禁止推論「星期日本來就是公眾假期」。撰稿者在 gov.hk 的 2027 年清單上讀到**第一項原文就是「每個星期日」**，
排在一月一日之前，於是在香港那列的備註引用了這一句。**協調者判定可以**：那是同一份官方清單的原文，不是推論，
而且正好解釋了為什麼初二逢週日不另外補假、補假落在 2 月 9 日。仍然不准寫「香港初二不放假」這種自己下的結論。

### 康文署改引 2026 年的公告

規格引康文署 2025-01-06 的新聞稿當慣例，撰稿當天在 info.gov.hk 找到 **2026-01-27** 的同名新聞稿，正文改引新的那篇，
2025 那篇留在 sources 當「每年 1 月會出公告」的佐證。這是「官方頁改了就照新的寫」的正常結果，記在這裡供日後查對。

### hero 壓不進 200 KB 時怎麼辦

`pack_ingest.fit_bytes` 的品質下限是 55（`range(85, 55, -5)` 實際停在 60），有些 Commons 原圖在那個下限壓不進
`HERO_MAX_BYTES`（200 KB），工具就把檔案留在 200 到 300 KB 之間並發 `hero_over_guideline` 警告（硬上限是 300 KB，
測試不會紅）。山寺篇就是這樣，240,746 bytes。

**做法照第六批**：正式 ingest 之後，對 `apps/web/public/guides/<slug>/hero.jpg` 再壓一次。
規劃工作區留了 `write7/shrink_heroes.py`（品質 60 往下掃到 38，必要時加 0.4 到 0.8 px 模糊，目標 198 KB）。
山寺那張實測品質 54、不加模糊就能到 196,986 bytes。壓不下去的才換照片——硬壓會糊掉。
