## 目標と準備

> 小さな読み取り専用タスク2回で範囲・設定・時間・品質を記録し、減らせる手戻りを見つけます。読む時間15分、実習25分にモデル待機が加わります。[教材](https://mokaair.com/guides/codex-first-project/todo-practice.zip)の独立 broken コピー efficiency-a・efficiency-b を用意します。実利用枠を使いますが新購読は不要です。[利用量](article:codex-account-usage)を確認し、枠がなければ記録表のみ準備して測定値を創作しません。

## 手順1：何を測るかを確認する

ChatGPT／Codex のプラン枠と API 金額は別指標です。利用可能百分率は他タスク・リセット・プランに左右される共有視窓の場合があり、1ポイント差を単一タスクの正確な価格にしません。API も実モデル・料金・usage を照合し、CLI の全 token に単価1つを掛けません。変わる数字を重記せずアカウント・モデル編の集中情報へ繋ぎます。

| 指標 | 記録方法 | 直接は分からないこと |
| --- | --- | --- |
| 人の時間 | 依頼準備から検証まで | モデル処理時間 |
| 待機 | 開始から最終回答まで | 純推論速度 |
| 手戻り | 補足・誤解修正・繰返し | 少回答でも正しいとは限らない |
| 合格項目 | 事前の4条件と照合 | 自信ある表現は証拠でない |
| 利用枠・usage | 実際に見える情報 | アカウント比率は1回費用でない |

欠如は unavailable、推定は estimated と方法を記し、不明を0にしません。

## 手順2：比較条件と正解を固定する

同一未変更 broken を2つ使い、各 node --test core.test.mjs で同じ2合格・1失敗を確認します。Node だけなのでモデル枠は使いません。欠陥は visibleTasks の completed 分岐が !task.completed を選ぶことです。この基準を手元に記録し、比較依頼へ正解を直接書きません。A・B とも計画だけで編集・サービス起動はしません。

同じ入口・ホストで各フォルダーに新規タスクを作り、モデル・推論設定を揃えます。選択肢がなければ型名を推測せず既定を記録します。同時競合を減らすため順番に実行します。新会話で回答混入は減りますがキャッシュ・ネットワーク・負荷は完全一致せず、個人の手順実習であって発表可能なモデル順位ではありません。

## 手順3：依頼の具体性だけ変える

A は情報が少なくても目的があり、B は再現入力・期待／実際・ファイル範囲を加えます。成果目標は同じで、先に渡す確かな背景量が違います。依頼作成時間を記録して各1回送信し、質問には普通に答えて補足回数へ数えます。B を勝たせるため A に必要情報を隠しません。

```text A：背景が少ない依頼
Find why Completed shows unfinished tasks in this project.
Explain the cause, propose the smallest fix and give verification steps.
Read only; do not edit files, run tests or start services.
```

```text B：再現と範囲を提示
Investigate the Completed filter in this Small Steps practice copy.
Reproduction: add Read and Build, complete Read, then choose Completed.
Expected: only Read. Actual: only Build.
Inspect core.mjs, app.js and core.test.mjs as needed.
Explain the cause, propose the smallest fix while preserving Active/All behavior,
and give exact Node and browser verification steps.
Read only; do not edit files, run tests or start services.
```

## 手順4：同じ基準で両結果を判定する

4点を手で照合します。visibleTasks の completed 条件を特定し、その分岐だけ task.completed 真を選ぶ修正、Active／All の保持、node --test core.test.mjs と同じ Read／Build 画面再現を提案したかです。禁止した試験を実行済みと称したりファイルを変えたりしていないかも確認します。一般的な長い危険一覧は加点せず、短くても検証欠如なら未完了です。

## 手順5：観測を継続できる習慣にする

最速回答だけでなく準備＋検証時間、待機、手戻りを比較します。B の準備が2分増えて補足が減るなら日常に適すかもしれません。A も1回で全合格なら全小課題に長文が必要という証拠はありません。有効形式を[再利用雛形](article:codex-templates-cheatsheet)へ保存し、目的・出典・範囲・検証を残して全会話を毎回貼りません。古い文脈や矛盾を減らせます。

次にモデル・推論を比べるなら合格 B と入力を固定し、[モデル選択](article:codex-model-selection)に沿って利用可能な設定1つだけを変えます。モデル・サブエージェント・依頼を同時変更して全差異を速度へ帰属しません。平行作業・長い再試行も枠を使い、小問題はツール追加より目的を狭める方が検証しやすい場合があります。長期作業は[引き継ぎ記録](article:codex-context-handoff)で検証済み状態を残して探索のやり直しを減らします。

## 完了とよくある誤判定

両コピーは不変のまま、観測表と回答を保存します。エージェントが編集したなら範囲違反と記録し差分保存後に自分のコピーを復元します。1回比較はその条件の判断だけで、恒久的な節約モデルやプランの固定課題数を示しません。利用画面遅延・リセット・他のタスクによる使用があれば比較不能とします。品質4点の根拠、時間方法、架空利用量なし、次の小変更が完了条件で、全指標を改善に見せることではありません。
