## 目標と準備

> 独立 Git 教材でブランチ、差分、指定ファイルのステージと commit、未確定復元、commit 撤回を練習します。読む時間15分、操作30分。Git 2.28 以降、エディター、expected 教材を使います。3 OS 共通で、ローカル履歴だけを作り GitHub や push は不要です。

[端末パス](article:codex-terminal-paths)を確認します。作業ツリー、次の commit 用 index、記録版は別状態です。ブランチは履歴の線で、未コミットのコピーではありません。別場所は[worktree](article:codex-worktrees)を使い、ブランチを保存完了としません。

## 手順1：独立した基準を作る

他プロジェクト外の codex-git-lab に expected 5ファイルを置き、現在地と git --version を確認します。なければ公式 OS 別導入を行い端末を開き直します。既存仕事用リポジトリでこの初期化をしません。

```sh ターミナル：独立した Git 基準
git init -b main
git config user.name "Practice Learner"
git config user.email "learner@example.invalid"
git add index.html style.css app.js core.mjs core.test.mjs
git diff --cached --name-only
git commit -m "Add practice baseline"
git status --short
```

逐行実行し、最初の5ファイルと commit 後の無変更を確認します。名前と予約ドメインは教材内設定で、GitHub 認証や global ではありません。署名・hooks の既存要件があれば従うか障害を記録し、全体方針を変更しません。

## 手順2：ブランチで区別できる二変更

```sh ターミナル：ブランチ作成
git switch -c codex/title-lab
git branch --show-current
```

ブランチ確認後、h1 の指定文だけ Plan one useful step. にし、CSS 末尾へ次のコメントを加えて別の未確定作業を模します。成果はタイトルで、CSS は保持しつつタイトル commit に混ぜません。両方とも教材です。

```css ファイルへ追記：style.css
/* KEEP-MY-NOTE */
```

```sh ターミナル：差分確認
git status --short
git diff -- index.html style.css
```

差分の旧行・新行と周辺を見て、h1 と CSS コメントだけか確認します。ファイル数だけで判断しません。次の読取り依頼で既存作業と対象を特定し、全差分 commit は求めません。

```text Codex への依頼：範囲の読み取り専用確認
Inspect this lab's current branch, status and diff without editing, staging or committing. The intended change is only the h1 title in index.html. The KEEP-MY-NOTE comment in style.css represents separate work and must be preserved. Explain what belongs in the title commit and what must stay outside it.
```

## 手順3：一ファイルをステージして復元を試す

```sh ターミナル：対象ファイルだけをステージ
git add index.html
git diff --cached --name-only
git diff --cached -- index.html
git diff -- style.css
```

同じファイルの2つの版を比較します。git add を再実行せず、エディターでステージ済みの Plan one useful step. だけを Compare one useful step. に変更します。次の4行で作業ツリー、インデックス、HEAD の違いを確認します。

```sh ターミナル：同じファイルのステージ済み・未ステージ差分
git status --short
git diff --cached -- index.html
git diff -- index.html
git show :index.html
```

status は MM index.html と未ステージの style.css を示すはずです。これは競合ではありません。[Git status 公式説明](https://git-scm.com/docs/git-status)に従うと、この場合は1列目の M が HEAD に対するインデックスの変更、2列目がインデックスに対する作業ツリーの変更です。cached diff は Make → Plan、通常の diff は Plan → Compare、show :index.html はステージ済みの Plan を示します。この時点の通常のコミットに Compare は自動で入りません。

続いて元の順序で2種類の restore を実行します。1行目はステージ解除だけなので Compare はディスクに残ります。2行目は、基準の旧タイトルに戻ったインデックスから index.html を復元します。1行目を飛ばすと、worktree restore の復元元はステージ済みの Plan のままです。[Git restore 公式説明](https://git-scm.com/docs/git-restore)にこの既定の復元元の違いがあります。破棄する対象が練習用タイトルであることを確認し、CSS は保持します。

```sh ターミナル：ステージ解除後に復元
git restore --staged -- index.html
git restore --worktree -- index.html
git status --short
git diff -- style.css
```

CSS だけ変更、h1 復元、コメント保持を確認します。自分の取消しで別作業を消しません。--staged は実ファイル編集を捨てず、--worktree は指定ファイルを復元元で上書きするため別物です。

## 手順4：限定 commit と履歴を残す撤回

タイトルを再変更して index.html だけステージし差分確認します。commit はタイトルだけ、CSS は未確定のままです。show で実際の対象を確認し、成功終了だけで範囲正解としません。

```sh ターミナル：タイトルの確認とコミット
git add index.html
git diff --cached --name-only
git diff --cached -- index.html
git commit -m "Update practice title"
git show --format=short --name-only HEAD
git status --short
```

撤回前に作業ツリーを確認します。残る教材 CSS コメントの保持を検証後、今回は明示的にその練習を終えて最初の命令でそのファイルだけ戻します。無変更と HEAD のタイトル commit を確認してから revert します。実装業の別変更には流用しません。

```sh ターミナル：メモ練習を終え、コミットを取り消す
git restore --worktree -- style.css
git status --short
git log -1 --oneline
git revert --no-edit HEAD
git log -3 --oneline
git status --short
```

revert は元変更を残して逆向き commit を追加します。旧 h1、3履歴、無変更が期待です。衝突は状態を読み、強制選択をしません。未完了 revert の取消しは git revert --abort の手順で行い再確認します。

## 命令比較、対処と受入

| 目的 | 命令 | 確認 |
| --- | --- | --- |
| 未ステージを見る | git diff | 作業ツリーと index |
| 次の commit を見る | git diff --cached | index と HEAD |
| ステージ解除 | git restore --staged -- index.html | 編集は残る |
| 指定未確定変更を捨てる | git restore --worktree -- index.html | 元とパスを先に確認 |
| commit 撤回 | git revert --no-edit HEAD | 対象と無変更を確認、履歴追加 |

分岐不在は repository を確認し、不意なファイルを add . でまとめません。一ファイルに変更が混ざると全体ステージに全て入るため、各差分を理解して処理します。CSS 除外、二つの restore、revert 履歴が受入条件です。図1状態、2限定確定、3復元確認。次は[テストと PR](article:codex-testing-review)です。
