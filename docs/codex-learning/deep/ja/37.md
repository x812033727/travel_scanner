## 目標と二つの入口

> Linux または WSL2 で CLI を導入し、ホスト、ディストリビューション、ファイルの場所を区別して、印付きファイルの読み取り検証と更新を行います。読む時間約12分、操作約30分で、WSL 初回導入や再起動、取得時間は別です。2026-09-14の公式資料による確認で、Linux / WSL 実機では実行していません。Windows 画像を Linux 画面として使っていません。

Linux PC ならその端末を開いて手順2へ進みます。Windows では Linux ツールが必要か判断します。ネイティブ PowerShell でも使えるため WSL は必須ではありません。Linux の開発環境や依存関係がある場合に WSL2 を選びます。[Windows CLI](article:codex-cli-windows)と並ぶ選択肢で、Windows のエラーすべてを移行で解決するわけではありません。

図の 1 は入力環境の識別、2 は導入と Linux プロジェクトへの移動、3 は同じ環境での検証です。Linux のホーム、ツール、認証情報は既定では別です。Windows の codex --version が成功しても Ubuntu 内の導入確認にはならず、WSL の認証だけで Windows デスクトップ側のログインも確認したとはいえません。

## 手順1：Windows で WSL2 を確認する

Windows PowerShell で次を実行し、ディストリビューションと VERSION が 2 かを確認します。Linux シェルのコマンドではありません。既存の WSL2 は保ち、再導入や削除はしません。現行 Codex の Linux サンドボックスは WSL1 非対応です。WSL1 の作業は先にバックアップし、Microsoft 資料で変換を計画します。唯一のコピーで試さないでください。

```powershell Windows PowerShell：導入済み WSL ディストリビューションを確認する
wsl --list --verbose
```

未導入なら仮想化と WSL が許可されているか確認し、Microsoft の案内で管理者 PowerShell から wsl --install を実行します。必要な再起動と Linux ユーザー作成を終えます。npm パッケージだけでなく OS 環境を追加するので、他の作業を中断する時間も確保します。管理端末では規則に従います。

```powershell 管理者 PowerShell：WSL が未導入で、導入すると決めた場合のみ
wsl --install
```

複数のディストリビューションがある場合は、PowerShell で wsl --distribution の後に一覧にある完全な名前を必要に応じて引用符付きで指定します。導入前に対象を選んでください。A で codex が見つかっても B で利用できる証拠にはなりません。後で PowerShell に戻ったらコマンドの解決先を確認し直し、Linux の導入やハッシュ記録を Windows に当てはめないでください。

導入後は Terminal で対象を選ぶか、通常の PowerShell で wsl を実行して既定の環境を開きます。複数ある場合は一覧の実名を選び、Ubuntu があると決めつけません。入るとプロンプトとパスが Linux 形式になります。以降はすべてこの Linux シェルで行います。

## 手順2：シェル、CLI、ホームを識別する

```bash Linux／WSL シェル：システム、場所、コマンド候補を確認する
uname -s
pwd
printf '%s\n' "$WSL_DISTRO_NAME"
command -v codex
type -a codex
```

uname は Linux を示します。WSL_DISTRO_NAME は WSL のディストリビューションを示し、通常 Linux では空でも正常です。command -v と type -a で目的の Linux 導入元か調べます。/mnt/c の Windows ラッパーは Linux ネイティブ導入の証拠ではありません。元を記録し、Linux 内で導入して選択されるコマンドを確認します。

新規導入は公式の独立コマンドを照合して実行し、PATH の案内を読んで新しい Linux 端末を開きます。npm 利用者は同じ Linux 内の node / npm を確認して npm install -g @openai/codex を使えます。Windows の Node.js は代わりになりません。一つの経路を選んで更新も統一します。

```bash Linux／WSL シェル：公式の独立インストーラーで導入する
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

```bash Linux／WSL シェル：導入後の新しい端末で場所と版を確認する
command -v codex
codex --version
codex --help
```

導入出力、実行パス、版を一致させます。curl、sh、基本ツールがなければ自分のディストリビューションの資料で準備し、別のパッケージ管理命令を流用しません。起動だけでは依存関係やサンドボックスの動作確認にならないため、次の読み取りで確認します。

## 手順3：Linux ホームに課題を作る

Linux ツールで動かす WSL 作業は ~/code など Linux ホームを優先します。/mnt/c は Windows のマウント先で、/home と同じプロジェクトの別名ではありません。この課題のために本番を移動しません。次は既存なら上書きせず停止する新規フォルダー作成です。必要なら別名を選びます。サブシェルなので終了後に明示的に移動します。

```bash Linux／WSL シェル：ブロック全体で新しい練習フォルダーを作る
(
  set -e
  cd ~
  mkdir 'codex linux lab'
  cd 'codex linux lab'
  printf '%s\n' 'LINUX-CLI-01' > note.txt
  cp note.txt note.original.txt
  pwd
  ls
)
```

作成成功後だけ次へ進みます。mkdir の File exists は既存データを保護した結果で、sudo を付ける理由ではありません。新しい名前を選びます。移動後は二つのファイル、LINUX-CLI-01、一致する SHA-256 を確認します。ローカルのバイト比較であり、Windows のハッシュとの一致は要求しません。

```bash Linux／WSL シェル：作成成功後に移動、読み取り、照合する
cd ~/"codex linux lab"
pwd
cat note.txt
sha256sum note.txt note.original.txt
```

## 手順4：同じ Linux 環境で認証して読む

```bash Linux／WSL シェル：一行が完了してから次を実行する
codex login
codex login status
codex --sandbox read-only
```

各コマンドの完了を待ち、実際の認証案内に従います。WSL でホストのブラウザーを使っても、Linux 端末へ戻って完了を確認します。ブラウザーやローカル回帰が使えなければ login --help と公式認証ページを確認します。アカウントと組織が許可する場合だけ --device-auth を使い、Windows の認証ファイルをプロジェクトへコピーして解決しません。

```text 自然言語の依頼：Linux 側の Codex CLI に入力する
Read note.txt and note.original.txt in the current Linux practice directory. Report the current directory and the exact marker, and check whether both files match. Do not edit, create files, or use external services. Stop and report any missing file or access error.
```

これは bash ではなく Codex の依頼です。Linux 練習フォルダー、LINUX-CLI-01、実際の読み取り記録を確認します。/exit 後に sha256sum、cat、ls で不変を確かめます。次にない note-missing.txt を要求し、作成せず欠落を示すことを確認します。二種類の結果で導入、認証、場所、読み取りの流れを検証します。

## ファイルの場所、更新、問題解決

| 場所やツール | 環境 | 確認 |
| --- | --- | --- |
| C:\Users のパス | Windows ネイティブ | PowerShell の Get-Location |
| /home のプロジェクト | Linux / WSL ファイルシステム | Linux の pwd |
| /mnt/c のプロジェクト | Linux から見た Windows ドライブ | /home のコピーと混同しない |
| Linux の codex | Linux シェルが選ぶ CLI | command -v と版を照合 |

/mnt/c の Linux 作業が遅ければ、唯一の原稿を移動や削除する前に Linux ホームの新しい練習コピーで比較します。エクスプローラーからは公式資料の `\\wsl$` 入口で実際の環境を選びます。Linux ファイルへのアクセスであって二つのコピーの同期ではありません。同名だけで判断せず、印と pwd を照合します。

更新前に CLI を終了して要約を残します。独立版は Linux の公式インストーラー、npm 版は同じ Linux の npm を使い、新しいシェルでパスと版を確認します。wsl --update は WSL の更新で Codex の代用ではありません。wsl --shutdown は動作中の WSL 作業を止めるため、毎回の Codex 導入手順にはしません。

シェルでは読めて Codex では読めなければ起動や権限のエラーを記録し、WSL2 と環境を確認して[権限](article:codex-permissions)を調べます。一律にサンドボックスを無効にしません。古いセッションがなければ環境、Linux ユーザー、CODEX_HOME の違いを確認します。本記事では認証ディレクトリを共有しません。[CLI 基礎](article:codex-cli-getting-started)で変更と復元、その後[引き継ぎ](article:codex-context-handoff)へ進みます。
