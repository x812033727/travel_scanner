## 讀完能做到什麼

> 你會把一句模糊需求改成 Codex 可以執行、自己也能驗收的任務，並在結果不符合時補充資訊而不必整段重來。閱讀約 12 分鐘，實作約 20 分鐘。本篇使用同一個待辦網站修改表單文字；重點是需求的可驗證性，不是背誦固定的提示詞公式。

## 準備可重複的起點

從[練習材料](https://mokaair.com/guides/codex-first-project/todo-practice.zip)複製 expected 到全新的 codex-prompt-lab；不要沿用上一課已改過文字的副本。根目錄應有五個檔案，先開啟 index.html，找到 New task 標籤、Add task 按鈕與 Read the project README 提示文字。這三個可見字串就是本篇的來源；不需要貼整個專案進對話。

已完成[第一個小專案](article:codex-first-project)者可使用相同預覽方式。Windows 在副本執行 py -m http.server 4173 --bind 127.0.0.1；macOS／Linux 執行 python3 -m http.server 4173 --bind 127.0.0.1，瀏覽 http://127.0.0.1:4173。這一課不需要先學 Git，但要保留原版，以便確認差異或取回自己改過的檔案。

## 第一步：找出模糊要求缺了什麼

「幫我把表單改得更好」沒有說給誰用、哪裡不好、能改哪些地方，或怎樣算完成。Codex 可能改色彩、欄位、按鈕、資料結構，甚至加入你沒需要的新套件；這不一定是它做錯，而是需求允許太多不同解讀。先用一句話說出讀者要做到的事，例如「新使用者能看懂怎麼新增一筆小任務」。

接著補四種資訊：目標、現況來源、限制、驗收。它們不是每次都要四個標題的格式，而是防止重要資訊漏掉的檢查方式。小幅改字只需幾行；跨多個檔案的新功能，才需要背景與分段計畫。不要為了看起來專業而塞入沒用的角色設定、工具清單或假裝精確的工時。

## 第二步：寫出完整可執行需求

下方是本篇完整提示詞，輸入到已選定 codex-prompt-lab 的 Codex 任務，而不是作業系統終端機。它明確指出一個 HTML 檔案與兩個字串變更，保留可及性標籤、事件繫結與資料格式，最後要求實際檢查。New task 保持不變是為了保留表單的可見標籤，不是要把所有文字強行改成同一個詞。

```text
Goal: make the existing todo form wording clearer for a first-time visitor.
Context: this folder is the unchanged Small Steps expected practice version.
In index.html only:
- Change the submit button text from "Add task" to "Save task".
- Change the input placeholder to "Plan one small step".
Keep the visible "New task" label, input id/name, maxlength, required attribute,
button type, JavaScript behavior, stored data and all other files unchanged.
Do not install packages or deploy anything.
Validate by adding Read, completing it, checking Completed, and refreshing.
Check that whitespace-only input does not create a task.
Run node --test core.test.mjs. If browser checks are unavailable, list them as not run.
Report the exact changed strings, files and evidence.
```

背景已經在檔案裡的資訊，讓 Codex 先讀檔即可；指向精確檔名比複製整份歷史紀錄更有用。如果實際畫面沒有 Add task，先停下核對是否使用原版。不要將不符合起點的要求硬套上去，或讓它在所有檔案搜尋相似文字後全部替換。可重現範例的第一個條件就是起點一致。

## 第三步：用成果判斷，而不是看回答長度

完成後開啟 index.html，應只看到按鈕文字與 placeholder 改動。New task 仍是與輸入框相連的標籤，type="submit"、id、name、maxlength、required 都保留。再開其他四個檔案與原版比較，確認沒有順手改架構。若 Codex 回覆很短但差異正確、驗證完整，這仍然是好交付；很長的說明不能替代缺少的檔案與結果。

在 http 預覽新增 Read，勾選完成，Completed 應只顯示已完成專案，重新整理後保留。空白輸入不能增加專案；Tab 焦點仍可到達輸入與提交按鈕。這些行為應與修改前一致。若只有文字改對、按鈕不能提交，表示驗收失敗，下一輪要指出實際現象，而不是籠統說「不好用」。

## 結果不符時，補充一個可重現例子

假設只看到 Save task 改對，而 placeholder 還是舊文。先確認瀏覽器重新整理及檔案已存檔，再發下方追補。這裡明列已正確的部分、目前錯誤與預期，不要求把整個頁面重做。若是你在中途改了需求，也要說明哪個條件取代前一版，避免兩組相反要求同時留在任務裡。

```text
The button text is correct; preserve that change.
After saving and refreshing, the placeholder still reads "Read the project README".
Expected placeholder: "Plan one small step".
Inspect index.html and correct only the remaining placeholder mismatch.
Report the relevant diff and any verification you can actually perform.
```

更複雜的情況可以先用[Plan 模式](article:codex-plan-mode)列出步驟與不確定點，但規劃不是驗證。計畫說會跑測試，不代表測試已執行；回答說會保留資料，也要檢查真實資料與程式。當需求有會改變方案的缺口，例如是否需要登入或同步，先回答這種問題，再開始相依功能，通常比做完重工更省事。

## 三種常見問題與修正

改太多：檢查需求是否用了「全面最佳化」「順便全部整理」等擴張範圍的字句，改為列出指定檔案與保留專案，再逐項還原無關差異。一直問問題：補足真正影響決策的條件，普通字型或檔名選擇可授權它依既有風格決定。回答看似完成卻沒證據：要求列出實際命令結果與未執行專案，不要求它換句話說「已完成」。

遇到反覆失敗，先保留最小重現資料、錯誤文字與最後已知正常狀態，再縮小到一個問題；不要每次都重貼整段無關歷史。若任務長到需要交接，可用[上下文交接](article:codex-context-handoff)儲存目前決策。反覆要求的專案慣例則放入 [AGENTS.md](article:codex-agents-md)，每次提示詞只留下這次要完成的變更。

## 小練習、還原與來源

把本篇目標改成「只把按鈕改為 Create task，placeholder 保留原文」，自行寫出新提示詞。驗收要明確指出 index.html 唯一改動的字串，並重做新增、空值與重新整理。結束後用保留的 expected 原版恢復 index.html，其他檔案不需替換；Python 伺服器用 Ctrl+C 停止。關閉 Codex 對話不會自動撤銷本次改字。

提示詞原則依 2026-09-14 的[官方 Prompting 檔案](https://learn.chatgpt.com/docs/prompting)核對，表單需求、輸入範例與驗收方法是本系列原創。相同英文提示詞在五語內容保持一致；模型回應不保證逐字相同，驗收看實際成果。下一步可練[新增功能](article:codex-implement-feature)或[修 Bug](article:codex-debugging)，把可重現輸入與預期結果帶入更大任務。
