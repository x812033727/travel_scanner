## 목표와 준비

> 작은 읽기 전용 작업 두 번으로 범위·설정·시간·품질을 기록하고 줄일 재작업을 찾습니다. 읽기 15분, 실습 25분에 모델 대기가 추가됩니다. [자료](https://mokaair.com/guides/codex-first-project/todo-practice.zip)의 독립 broken 복사본 efficiency-a·efficiency-b를 준비하세요. 실제 사용량을 쓰지만 새 구독은 필요 없습니다. [계정 사용량](article:codex-account-usage)을 확인하고 한도가 없으면 기록표만 준비하며 측정값을 만들지 않습니다.

## 1단계: 무엇을 측정하는지 확인

ChatGPT/Codex 요금제 한도와 API 비용은 다른 지표입니다. 잔여 비율은 다른 작업·초기화·요금제에 영향을 받는 계정 공유 구간일 수 있어 1% 차이를 해당 작업의 정확한 가격으로 보지 않습니다. API도 실제 모델·요금·usage 기록을 확인하며 CLI의 모든 token에 단일 단가를 곱하지 않습니다. 변하는 숫자를 반복하지 않고 계정·모델 편의 통합 정보로 연결합니다.

| 지표 | 기록 방법 | 바로 알 수 없는 것 |
| --- | --- | --- |
| 사람 시간 | 요청 준비부터 검증까지 | 모델 처리 시간 |
| 대기 | 시작부터 최종 답변까지 | 순수 추론 속도 |
| 재작업 | 보충·오해 수정·반복 | 답이 적어도 정확한 것은 아님 |
| 승인 항목 | 사전 조건 네 개와 비교 | 자신 있는 표현은 증거 아님 |
| 한도·usage | 실제 보이는 정보 | 계정 비율은 단일 비용 아님 |

없으면 unavailable, 추정이면 estimated와 방법을 적고 모르는 값을 0으로 쓰지 않습니다.

## 2단계: 비교 조건과 정답 고정

같은 미수정 broken을 두 개 쓰고 각각 node --test core.test.mjs로 같은 두 통과·한 실패를 확인합니다. Node만 써 모델 한도를 소비하지 않습니다. 결함은 visibleTasks의 completed 분기가 !task.completed를 고르는 것입니다. 기준을 따로 기록하되 비교 요청에 정답을 넣지 않습니다. A·B 모두 계획만 제안하며 수정·서비스 시작은 하지 않습니다.

같은 진입점·호스트에서 각 폴더의 새 작업을 만들고 모델·추론 설정을 맞춥니다. 선택이 없으면 이름을 추측하지 말고 기본값을 기록하세요. 동시 경합을 줄이도록 순차 실행합니다. 새 대화는 답변 유입을 줄이지만 캐시·네트워크·부하는 같지 않으므로 개인 절차 실습이며 발표 가능한 모델 순위가 아닙니다.

## 3단계: 요청의 구체성만 변경

A는 정보가 적어도 목표가 있고 B는 재현 입력·예상/실제·파일 범위를 추가합니다. 결과 목표는 같으며 미리 주는 확실한 배경의 양이 다릅니다. 작성 시간을 기록하고 각각 한 번 보내세요. 질문에는 정상 답변하고 보충 횟수로 세며 B를 이기게 하려고 A에 필요한 정보를 숨기지 않습니다.

```text A: 배경이 적은 요청
Find why Completed shows unfinished tasks in this project.
Explain the cause, propose the smallest fix and give verification steps.
Read only; do not edit files, run tests or start services.
```

```text B: 재현과 범위 제공
Investigate the Completed filter in this Small Steps practice copy.
Reproduction: add Read and Build, complete Read, then choose Completed.
Expected: only Read. Actual: only Build.
Inspect core.mjs, app.js and core.test.mjs as needed.
Explain the cause, propose the smallest fix while preserving Active/All behavior,
and give exact Node and browser verification steps.
Read only; do not edit files, run tests or start services.
```

## 4단계: 같은 기준으로 두 결과 평가

네 항목을 수동 확인합니다. visibleTasks의 completed 조건 식별, 해당 분기만 task.completed 참을 고르는 수정, Active/All 유지, node --test core.test.mjs와 같은 Read/Build 화면 재현 제안입니다. 금지한 시험을 실행했다고 주장하거나 파일을 수정하지 않았는지도 확인하세요. 긴 일반 위험 목록은 가점이 아니며 짧아도 검증이 없으면 미완료입니다.

# Workflow comparison

## 5단계: 관측을 지속 가능한 습관으로 만들기

가장 빠른 답변뿐 아니라 준비+검증 시간·대기·재작업을 비교합니다. B 준비가 2분 늘어도 보충 여러 번을 줄이면 일상에 적합할 수 있습니다. A도 한 번에 모두 통과하면 모든 작은 작업에 긴 문서가 필요하다는 증거는 없습니다. 효과적인 형식을 [재사용 템플릿](article:codex-templates-cheatsheet)에 저장하고 목표·출처·범위·검증을 유지하되 전체 대화를 매번 붙이지 마세요. 오래되거나 충돌하는 맥락을 줄입니다.

명확한 가상 사례로 판단을 연습합니다. A는 준비 1분·대기 3분·검증 4분에 네 조건 중 세 개, B는 3분·4분·1분에 네 조건 모두를 충족합니다. 기록한 합계는 둘 다 8분입니다. B의 첫 대기는 더 길지만 결과가 완전하고 A의 보완 시간은 미측정이므로 전체 완료 시간이 같다고 결론낼 수 없습니다. 모델 성능 실측값도 아닙니다.

기준을 미리 정했는지, 품질을 실제 확인했는지, 사용량 누락을 unavailable로 남겼는지도 확인합니다. 둘 다 네 조건을 충족한 뒤 전체 시간과 재작업을 비교하세요. 가상 숫자는 관찰표와 분리하고 다음에도 같은 기준에서 한 요인만 바꿔 차이 원인을 해석합니다.

다음에 모델·추론을 비교하려면 합격한 B 요청과 입력을 고정하고 [모델 선택](article:codex-model-selection)에 따라 사용 가능한 설정 하나만 바꿉니다. 모델·하위 에이전트·요청을 함께 바꾸고 모든 차이를 속도 탓으로 돌리지 마세요. 병렬 작업·긴 재시도도 사용량을 쓰며 작은 문제는 도구 추가보다 목표 축소가 검증하기 쉬울 수 있습니다. 긴 작업은 [인계 기록](article:codex-context-handoff)에 검증 상태를 남겨 탐색 반복을 줄입니다.

## 완료와 흔한 오판

두 복사본은 그대로여야 하며 관측표·답변을 저장합니다. 에이전트가 수정했으면 범위 위반으로 기록하고 차이를 보존한 뒤 자신의 복사본을 복원하세요. 한 번 비교는 해당 조건의 선택만 지지하며 영구적으로 저렴한 모델·요금제별 고정 작업 수를 뜻하지 않습니다. 사용량 표시 지연·초기화·다른 작업 사용은 비교 불가로 적습니다. 품질 네 항목의 근거·시간 측정법·가짜 사용량 없음·다음 작은 조정이 완료 조건이며 모든 지표를 개선처럼 보이게 하는 것이 아닙니다.
