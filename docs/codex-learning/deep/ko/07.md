## 이 강의의 목표

> 모호한 요청을 Codex가 실행하고 직접 검증할 수 있는 작업으로 바꾸고, 결과가 다르면 처음부터 다시 하지 않고 정보를 보완합니다. 읽기 약 12분, 실습 약 20분입니다. 공통 할 일 사이트의 폼 문구를 바꾸며 고정된 주문을 외우는 대신 검증 가능한 요구를 만듭니다.

## 반복 가능한 시작 상태 준비하기

[실습 자료](https://mokaair.com/guides/codex-first-project/todo-practice.zip)의 expected를 새 codex-prompt-lab으로 복사하고 이전에 수정한 복사본은 쓰지 않습니다. 파일 다섯 개를 확인한 뒤 index.html에서 New task 레이블, Add task 버튼, Read the project README 자리표시자를 찾습니다. 이 세 문자열이 필요한 근거이며 프로젝트 전체를 대화에 붙일 필요는 없습니다.

[첫 프로젝트](article:codex-first-project)의 미리보기 절차를 사용합니다. Windows는 py -m http.server 4173 --bind 127.0.0.1, macOS/Linux는 python3 -m http.server 4173 --bind 127.0.0.1을 복사본에서 실행하고 http://127.0.0.1:4173을 엽니다. Git은 필요 없지만 비교하거나 수정 파일을 복원할 수 있도록 원본은 남깁니다.

## 1단계: 모호한 요청의 빈틈 찾기

‘폼을 더 좋게 바꿔 줘’에는 사용자, 문제, 허용 범위, 완료 기준이 없습니다. Codex가 색상, 필드, 버튼, 데이터 구조를 바꾸거나 필요 없는 패키지를 추가할 수도 있습니다. 반드시 잘못이라기보다 해석 범위가 너무 넓은 요청일 수 있습니다. ‘처음 방문한 사용자가 작은 할 일을 추가하는 방법을 이해한다’처럼 사용자 성과부터 적으세요.

목표, 현재 상태의 근거, 제한, 검증 기준을 보완합니다. 매번 네 개의 제목이 필수라는 뜻이 아니라 빠진 정보를 확인하는 방법입니다. 문구 수정은 몇 줄이면 충분하고 여러 파일에 걸친 기능은 배경과 단계별 계획이 필요할 수 있습니다. 전문적으로 보이려고 불필요한 역할 설정, 도구 목록, 근거 없는 시간 추정을 넣지 않습니다.

## 2단계: 실행 가능한 전체 요청 작성

아래 전체 요청을 codex-prompt-lab의 Codex 작업에 보내며 운영체제 셸에 입력하지 않습니다. HTML 파일 하나와 문자열 변경 두 개를 지정하고 접근성 레이블, 이벤트 연결, 데이터 형식을 보존하며 실제 검사를 요청합니다. New task는 보이는 입력 레이블로 남기는 것이며 모든 문구를 같은 단어로 바꾸는 것이 아닙니다.

```text
Goal: make the existing todo form wording clearer for a first-time visitor.
Context: this folder is the unchanged Small Steps expected practice version.
In index.html only:
- Change the submit button text from "Add task" to "Save task".
- Change the input placeholder to "Plan one small step".
Keep the visible "New task" label, input id/name, maxlength, required attribute,
button type, JavaScript behavior, stored data and all other files unchanged.
Do not install packages or deploy anything.
Validate by adding Read, completing it, checking Completed, and refreshing.
Check that whitespace-only input does not create a task.
Run node --test core.test.mjs. If browser checks are unavailable, list them as not run.
Report the exact changed strings, files and evidence.
```

파일에 있는 배경은 Codex가 읽도록 하고 전체 대화 이력보다 정확한 파일 이름을 알려 주세요. 실제 화면에 Add task가 없다면 원본인지 먼저 확인합니다. 다른 시작 상태에 요청을 억지로 적용하거나 프로젝트 전체의 비슷한 문자열을 일괄 변경하게 하지 않습니다. 재현성의 첫 조건은 같은 기준 상태입니다.

## 3단계: 답변 길이가 아닌 결과로 판단

완료 후 index.html에는 버튼 문구와 placeholder만 바뀌어야 합니다. New task와 입력 연결, type="submit", id, name, maxlength, required는 그대로여야 합니다. 나머지 네 파일도 원본과 비교해 불필요한 구조 변경을 확인하세요. 답변이 짧아도 차이가 정확하고 검증이 충분하면 좋은 결과입니다. 긴 설명은 빠진 파일 변경이나 결과를 대신하지 않습니다.

HTTP 미리보기에서 Read를 추가하고 완료한 뒤 Completed 필터와 새로고침 후 저장 상태를 확인합니다. 공백으로 항목이 늘어나면 안 되고 Tab으로 입력창과 제출 버튼에 도달해야 합니다. 수정 전과 같은 동작이어야 합니다. 문구만 맞고 제출이 안 되면 검증 실패이므로 다음 요청에는 ‘별로야’가 아니라 실제 증상을 적습니다.

## 결과가 다르면 재현 사례 추가하기

Save task는 맞지만 placeholder가 그대로라면 저장과 새로고침부터 확인한 뒤 아래 보완 요청을 보냅니다. 이미 맞는 부분, 현재 오류, 기대 결과를 나누며 페이지 전체 재작성을 요구하지 않습니다. 중간에 요구를 바꿨다면 어떤 조건이 이전 조건을 대체하는지 명시해 모순된 요구가 동시에 남지 않게 합니다.

```text
The button text is correct; preserve that change.
After saving and refreshing, the placeholder still reads "Read the project README".
Expected placeholder: "Plan one small step".
Inspect index.html and correct only the remaining placeholder mismatch.
Report the relevant diff and any verification you can actually perform.
```

큰 작업은 [Plan 모드](article:codex-plan-mode)로 단계와 불확실성을 정리할 수 있지만 계획은 검증이 아닙니다. 테스트하겠다는 말은 결과가 아니고 데이터를 보존하겠다는 말도 코드와 데이터로 확인해야 합니다. 로그인이나 동기화 필요 여부처럼 구조를 바꾸는 빈틈은 관련 구현 전에 답하면 재작업을 줄일 수 있습니다.

## 자주 생기는 세 문제와 수정

수정이 너무 많다면 ‘전부 최적화’ 같은 범위 확장 표현을 빼고 허용 파일과 보존 동작을 명시한 뒤 무관한 변경만 각각 되돌립니다. 질문이 계속되면 판단에 영향을 주는 조건을 보완하고 일반 글꼴이나 이름은 기존 스타일을 따르도록 맡깁니다. 완료 주장에 근거가 없으면 ‘완료’의 다른 표현 대신 실제 명령 결과와 미실행 항목을 요청합니다.

반복 실패 시 최소 재현 자료, 오류 문구, 마지막 정상 상태를 남기고 문제 하나로 좁히세요. 관련 없는 이력을 매번 다시 붙이지 않습니다. 긴 작업은 [문맥 인수인계](article:codex-context-handoff)를 사용하고 반복되는 규칙은 [AGENTS.md](article:codex-agents-md)에 두어 개별 요청은 이번 변경에 집중시킵니다.

## 추가 연습, 복원과 출처

‘버튼만 Create task로 바꾸고 placeholder는 원문을 유지한다’는 새 요청을 직접 작성하세요. index.html에서 바뀐 문자열 하나를 명시하고 추가, 빈 입력, 새로고침을 다시 확인합니다. 종료 후 expected 원본으로 index.html만 복원하고 Python은 Ctrl+C로 중단합니다. Codex 대화를 닫아도 문구 수정은 취소되지 않습니다.

요청 원칙은 2026-09-14의 [공식 Prompting 문서](https://learn.chatgpt.com/docs/prompting)로 확인했고 폼 요구, 입력 예제, 검증 절차는 직접 만들었습니다. 영어 요청은 모든 번역에서 동일하지만 모델 답변이 글자까지 같을 필요는 없으며 실제 결과로 검증합니다. 다음으로 [기능 구현](article:codex-implement-feature)이나 [버그 수정](article:codex-debugging)에 재현 입력과 기대 결과를 적용합니다.
