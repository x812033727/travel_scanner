## 이 강의의 목표

> 현재 작업에 맞는 기본 진입점을 선택하고 파일 위치, 명령 실행 위치, 결과 확인 위치를 설명한 뒤 읽기 전용 작업으로 확인합니다. 읽기 약 10분, 실습 약 15분입니다. 모든 버전을 설치할 필요는 없습니다. 먼저 한 가지 작업 흐름을 완성한 뒤 다른 화면을 추가합니다.

## 사용 화면과 실행 환경 구분하기

사용 화면은 요청을 보내는 곳이고 환경은 에이전트가 실제로 일하는 곳입니다. 데스크톱, CLI, IDE는 로컬 프로젝트를 다룰 수 있고 원격 프로젝트나 클라우드 작업은 별도 환경을 사용합니다. 휴대전화 화면이 작다고 작업 규모가 작지는 않고 같은 모양의 창이라고 같은 컴퓨터에서 실행되는 것도 아닙니다. 버튼 수보다 요청 출발점, 실행 컴퓨터, 결과 위치를 먼저 정리하세요.

| 화면 | 주요 작업 방식 | 첫 확인 사항 |
| --- | --- | --- |
| 데스크톱 | 프로젝트, 작업, 파일, 차이 보기 | 선택한 프로젝트와 호스트 |
| CLI | 터미널 명령과 대화 | 현재 작업 디렉터리 |
| IDE | 편집기 파일과 코드 문맥 | 열린 폴더와 파일 |
| 클라우드 | 설정된 원격 환경과 작업 | 저장소, 브랜치, 환경 |
| 모바일 Remote | 연결된 호스트의 작업 | 페어링한 호스트의 가용 상태 |

## 1단계: 현재 작업 방식으로 선택하기

그래픽 화면과 여러 작업 관리가 편하다면 [데스크톱 입문](article:codex-desktop-getting-started)부터 시작합니다. Windows와 macOS는 각 운영체제의 공식 설치 절차를 따릅니다. Linux는 데스크톱 미리보기에서 지원하는 배포판과 아키텍처에 맞는 패키지를 고르며 Windows 설치 파일을 대신 쓰지 않습니다. Linux 데스크톱 지원이 Remote 호스트 지원과 같다는 뜻도 아니므로 각각 확인하세요.

터미널에서 폴더를 이동하거나 테스트를 실행하고 스크립트와 연결하려면 [CLI](article:codex-cli-getting-started)를 선택하세요. Windows 네이티브와 WSL은 설치, 홈 디렉터리, 경로가 다른 환경입니다. macOS와 Linux의 사용자 경로도 그대로 바꿔 쓸 수는 없습니다. 터미널이 낯설면 두 셸을 한꺼번에 배우기보다 [터미널과 경로](article:codex-terminal-paths)부터 익힙니다.

공식 지원 편집기에서 현재 파일이나 선택 영역을 전달하려면 [IDE 확장](article:codex-ide-getting-started)을 사용합니다. 마켓플레이스에서 이름이 비슷하다는 이유만으로 설치하지 말고 현재 편집기의 공식 지원을 확인하세요. 데스크톱과 IDE를 모두 설치했어도 첫 수정은 한쪽에서만 합니다. 두 작업이 같은 파일을 동시에 바꾸면 변경 원인을 찾기 어렵습니다.

## 2단계: 클라우드나 모바일이 필요한지 판단하기

GitHub 저장소를 구성된 원격 환경에서 작업하게 한 뒤 차이 또는 PR을 검토하려면 [클라우드 작업](article:codex-cloud-tasks-github)을 사용합니다. 먼저 저장소와 브랜치를 기록하세요. 로컬에서 수정하고 커밋하지 않은 파일은 프로젝트 이름이 같다고 클라우드에 나타나지 않습니다. 모호한 요청을 다시 보내기보다 올바른 버전을 환경에 제공해야 합니다. 연습용 GitHub 저장소가 없어도 로컬로 입문 과정을 진행할 수 있습니다.

외출 중 컴퓨터 작업을 확인하거나 이어 가려면 [모바일 Remote](article:codex-mobile-guide)를 고려합니다. 공식 문서는 iOS와 Android에서 사용 가능한 macOS 또는 Windows 데스크톱 호스트를 제어하는 방식을 설명하며 호스트 연결, 페어링, 워크스페이스 권한이 필요합니다. npm, 프로젝트, 로컬 브라우저가 휴대전화 저장소로 옮겨지는 것은 아닙니다. 호스트가 꺼졌거나 오프라인이면 호스트를 복구하고 휴대전화 터미널에 패키지를 설치해 연결을 고치려 하지 마세요.

## 3단계: 작은 작업으로 확인하기

빈 codex-platform-check 폴더에 location.txt를 만들고 Practice marker: local-copy-A 한 줄을 씁니다. 데스크톱이나 IDE에서는 해당 폴더를 열고 CLI에서는 먼저 이동한 뒤 시작합니다. 클라우드라면 연습용 저장소에 같은 파일을 만들고 커밋한 후 그 파일이 있는 브랜치를 선택하세요. 진입점 확인만을 위해 실제 운영 프로젝트를 업로드하지 않습니다.

```text
Read location.txt without changing files.
Report the exact marker, working directory, and where commands for this task run.
Distinguish verified facts from anything you cannot determine.
Do not install tools, create files, or change settings.
```

local-copy-A와 도구 결과로 뒷받침되는 작업 경로가 나와야 합니다. 격리된 작업 복사본을 쓰는 화면도 있으므로 경로가 데스크톱 경로와 글자까지 같을 필요는 없습니다. 선택한 브랜치, 표식, 환경이 맞는지가 중요합니다. 호스트를 확인할 수 없으면 모름으로 기록하고 추측을 성공으로 처리하지 말고 연결 설정을 확인하세요.

경계 사례로 로컬 표식만 local-copy-B로 바꾸고 커밋하지 않습니다. 기존 클라우드 복사본에서 A를 읽는다면 이는 모델이 잊은 것이 아니라 버전 차이의 증거일 수 있습니다. 동일 호스트와 폴더를 제어하는 휴대전화는 호스트의 현재 파일을 기준으로 해야 합니다. 최신인지 묻기보다 출처와 표식을 매번 보고하게 하면 판단하기 쉽습니다.

## 문제 해결과 완료 기준

화면이 없다면 공식 지원, 앱 버전, 계정 워크스페이스, 순차 제공 상태를 확인하고 미확인 상태를 남깁니다. 파일이 없다면 폴더, 클라우드 브랜치, 호스트, 커밋 여부를 확인합니다. 명령이 없다면 실제 실행 환경의 도구를 확인하세요. 노트북에 Node.js가 있다는 사실이 클라우드에도 있다는 증거는 아닙니다. 화면, 파일 버전, 실행 환경 문제를 모두 재로그인으로 해결하려 하지 않습니다.

마치면 표식을 A로 복원하고 폴더는 이후 강의를 위해 남깁니다. 이번 실습에서 만든 작업만 중단하세요. ‘나는 __ 화면을 쓰고 파일은 __ 환경에 있으며 __로 결과를 확인한다’라는 문장을 완성할 수 있으면 됩니다. 화면을 바꿨을 때 파일 위치를 모르면 여러 작업을 시작하기 전에 읽기 확인부터 마칩니다. 그림의 1, 2, 3은 화면 선택, 환경 확인, 결과 검증을 뜻합니다.
