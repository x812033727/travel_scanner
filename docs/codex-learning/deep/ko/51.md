## 목표와 준비

> 자신의 템플릿 폴더를 만들고 작업에 맞는 항목을 선택해 실제 관찰값을 채우며 불필요한 절차를 제거합니다. 읽기 15분, 실습 20분입니다. 완성 내용을 Codex 입력창에 붙여 넣고 제출해야 요청이 됩니다. 데스크톱은 새 작업을 열고, CLI는 프로젝트 폴더에서 codex를 시작해 대화 입력창을 사용하세요. 새로운 슬래시 명령이나 자동 실행 플러그인이 아닙니다. [요청 작성](article:codex-prompting)과 [Markdown](article:codex-markdown-basics)을 먼저 읽으세요.

## 1단계: 용도를 나눠 템플릿 저장

실습 디렉터리에 templates 폴더를 만들고 편집기로 아래 파일을 추가합니다. Windows는 .md.txt로 저장되지 않았는지, macOS는 일반 텍스트인지 확인하고 Linux는 익숙한 편집기에서 UTF-8로 저장하세요. 모든 OS에서 실습 루트를 기준으로 같은 파일명을 사용합니다. 자동 로드 기능이 없으며 추가 패키지·사이트 로그인·전역 설정도 필요하지 않습니다.

```text 만들 폴더와 파일
templates/
  task.md
  bug.md
  review.md
  handoff.md
  rules.example.md
  connection-check.md
```

| 작업 | 템플릿 | 대체할 수 없는 것 |
| --- | --- | --- |
| 작은 기능 구현 | task.md | 실제 파일과 검증 |
| 재현 가능한 버그 수정 | bug.md | 원래 오류와 재현 |
| 변경 검토 | review.md | 테스트와 판단 |
| 긴 작업 인계 | handoff.md | 최신 Git 상태 |
| 규칙 초안 | rules.example.md | 올바른 위치의 AGENTS.md |
| 외부 도구 확인 | connection-check.md | 실제 도구 응답 |

## 2단계: 검증 가능한 요청 작성

```markdown templates/task.md
# Task
Goal: Verify the active-task filter and repair it only if the acceptance case fails.
Context: Use the complete reference copy in this practice folder.
Inspect first: index.html, app.js, core.mjs, style.css and core.test.mjs.
Scope: Only files needed for the filter and its focused tests.
Behavior: All shows every task; Active shows tasks whose completed value is false.
Preserve: Existing task IDs, titles, ordering and stored data format.
Acceptance: With three tasks (two complete), Active shows exactly one.
Boundary: An empty list shows a useful empty state and does not throw.
Validation: Run node --test core.test.mjs and verify the browser behavior; report actual results.
If the existing behavior passes, report that evidence without unnecessary edits.
Delivery: Explain changed behavior, tests actually run and remaining limitations.
```

이 작성 예시는 Small Steps용입니다. expected 복사본에 코드 파일 다섯 개가 있는지 확인하세요. 설명 README.md는 expected 안이 아니라 다운로드 루트에 있습니다. 다른 프로젝트는 각 README로 검증 명령을 확인합니다. 타당성 논의는 [Plan 모드](article:codex-plan-mode)에서 절차·미결정을 결과물로 정하고 구현이라면 수정 범위를 명시합니다.

웹사이트를 정리해 달라는 문장을 이 형식으로 바꿔 보세요. 화면, 보존할 동작, 검증 데이터, 배포 포함 여부가 보여야 합니다. 파일명이 없으면 목록 표시 담당 파일을 찾아 보고하도록 요청하고 경로를 지어내지 않습니다. 설명은 편한 언어로 쓰되 식별자, 경로, 조건은 유지하세요.

## 3단계: 버그 보고에 증거 보존

```markdown templates/bug.md
# Bug report
Environment: <OS, browser/runtime and version>
Practice folder or branch: <actual location>
Starting state: <fixture or steps to create it>
Reproduction:
1. <first action>
2. <next action>
Expected: <observable result>
Actual: <observed result>
Error: <exact message, with secrets removed>
Frequency: <always / intermittent / unknown>
Already tried: <one change and its result, or none>
Fix scope: <allowed behavior and files>
Verification: Reproduce first, fix, rerun the original case and a boundary case.
```

꺾쇠 안은 채울 항목이며 터미널 문법이 아닙니다. [버그 연습](article:codex-debugging)은 ‘broken 복사본에 Read와 Build를 추가하고 Read만 완료했는데 Completed에 Build가 나옴’처럼 적습니다. Actual에는 직접 관찰한 내용만 적고 미실행이면 NOT RUN으로 두어 예시를 실측처럼 쓰지 않습니다. 확인하지 않은 데이터베이스 고장을 원인으로 단정하지 말고 오류 메시지가 없으면 none observed와 동작 및 단계를 적습니다.

수정 후 원래 절차와 빈 데이터 또는 중복 제목 경계를 다시 실행합니다. 실패와 미실행을 구분하고 통과할 것이라는 예상을 결과로 적지 마세요. 실행할 수 없다면 한계와 재현 명령을 전달하며 Verification 항목을 완료로 보지 않습니다. 과거 증거를 새 결과로 쓰지 않도록 통과 개수는 미리 넣지 않습니다.

## 4단계: 검토와 인계 구분

```markdown templates/review.md
# Review request
Compare: <base branch or exact before-state> -> <current change>
Purpose: <user-visible behavior>
Read first: <requirements and relevant files>
Review for: correctness, regressions and missing meaningful tests.
For each finding: give the trigger, impact, file/location and suggested correction.
Evidence: <commands actually run, exit codes and relevant output>
Unknowns: <tests or environments not checked>
Report no findings if none are supported; do not invent issues to fill a quota.
Do not modify files in this review task unless I request a fix.
```

```markdown templates/handoff.md
# Handoff
Goal:
Working directory and branch:
Current commit:
Existing uncommitted changes and owners:
Completed work with evidence:
Pending work:
Decisions and constraints:
Files to inspect next:
Last command and result:
Known limitations:
Next smallest action:
Before continuing: verify the current files and Git state against this record.
```

검토 기준은 현재 Git 저장소에서 찾을 수 있어야 합니다. 없으면 [Git과 차이](article:codex-git-basics)를 확인하고 main을 가정하지 마세요. 인계는 현재 위치와 상태를 매번 갱신합니다. 이전 작업의 커밋 보고가 현재 폴더의 깨끗함을 증명하지 않으므로 미커밋 변경과 담당자를 적어 덮어쓰기를 막습니다.

인계 파일은 공유에 적합한 위치라면 프로젝트에 둘 수 있습니다. 고객 정보, 인증 정보, 전체 대화 대신 경로, 문제 요약, 검증 결과를 남기세요. 저장했다고 새 작업이 읽은 것은 아니므로 명시적으로 읽도록 요청하고 다음 행동을 확인합니다. [맥락과 인계](article:codex-context-handoff)를 참고하세요.

## 5단계: 규칙과 외부 도구 템플릿

```markdown templates/rules.example.md: 규칙 초안
# Practice project rules
Read index.html, app.js, core.mjs and core.test.mjs before changing this practice app.
Preserve task IDs and the existing data format.
Keep changes within the requested behavior.
Run node --test core.test.mjs and report actual results.
Do not commit credentials or private practice data.
If required files are missing, report the missing paths before making assumptions.
```

rules.example.md는 검토 전 초안이므로 AGENTS.md로 부르지 않습니다. 프로젝트에 맞는지 확인한 뒤 기존 조건을 보존하며 [AGENTS.md](article:codex-agents-md)의 올바른 계층에 합칩니다. 일회 작업은 요청에 넣으세요. 반복되고 범위가 안정적인 작업을 [SKILL.md](article:codex-skills)로 만들며 모든 임시 요청을 스킬로 설치할 필요는 없습니다.

```markdown templates/connection-check.md
# Connection check
Surface / host / version:
Plugin or MCP server name and source:
Configured:
Authenticated (if required):
Tool available in a new task:
Read-only target (fictional or public):
Expected marker or source:
Actual tool call and result:
Original data unchanged:
Disconnect or disable action, if performed:
Retest after change:
Never include tokens, passwords or one-time login URLs in this report.
```

설정·인증·기능·실제 호출을 따로 채웁니다. 불필요한 인증은 not required, 미확인은 not checked로 적으세요. 설정 파일만으로 연결 성공을 판단하거나 true를 미리 넣지 않습니다. [Plugins](article:codex-plugins)나 [MCP](article:codex-mcp)는 이번 진입점과 호스트만 기록하며 다른 PC의 같은 이름 설정을 동일하게 보지 않습니다.

### 서로 충돌하는 템플릿을 하나의 작업으로 고치기

잘못된 요청인 ‘expected를 읽기 전용으로 검토하면서 수정하고 커밋도 해줘. npm test로 세 개 통과했다고 보고해’를 봅니다. 읽기와 수정이 충돌하고 package.json이 없는 자료에 잘못된 명령을 지정하며 관찰하지 않은 결과를 미리 정합니다. 이번에는 읽기 전용 확인을 선택하고 아래 완성 요청을 연습 루트의 adapted-task.md로 저장합니다. 원래 템플릿 여섯 개는 보존합니다.

```markdown 작업 사본: adapted-task.md
# Read-only practice check
Goal: Verify the existing Active-filter behavior in this expected copy.
Confirm the absolute working directory and the five expected source files first.
Read core.mjs and core.test.mjs; explain the filter condition and test coverage.
Run node --test core.test.mjs and report the actual exit code, passes and failures.
Do not edit, stage, commit, push or deploy anything in this task.
Browser behavior: NOT RUN unless actually checked; core tests do not prove it.
If required files are missing, report the paths and stop before guessing commands.
Delivery: observed evidence, unverified behavior and the next smallest step.
```

깨끗한 expected 복사본의 참고 결과는 3개 통과, 0개 실패지만 현재 출력을 기록하고 소스 파일은 그대로 둡니다. broken을 열었다면 2개 통과, 1개 실패와 시작 상태가 다름을 보고하고 경로를 고치거나 별도 수정 작업을 만듭니다. 템플릿에 expected라고 적혔다고 실제 실패를 무시하지 않습니다. 이는 목표, 배경, 경계, 사용할 결과를 다루는 [공식 프롬프트 안내](https://learn.chatgpt.com/docs/prompting)를 이 자료에 적용한 예입니다.

## 오류·복원·연습

전송 전에 <를 검색해 미완성 항목을 채우거나 제거하세요. 다른 프로젝트의 오래된 명령은 README와 작업 폴더 확인으로 방지합니다. 읽기 전용 검토와 추가 수정처럼 충돌하는 요구는 한 목표로 정리합니다. 동명 템플릿은 별도 사본이나 Git 차이로 보존하고 복원도 자신이 바꾼 템플릿만 대상으로 합니다.

연습으로 관찰한 오류를 bug.md에, 다음 단계를 handoff.md에 채워 원래 작업을 모르는 사람에게 전달하세요. 폴더·재현·미확인 사항을 알 수 있어야 합니다. 기기나 데이터를 추측해야 하면 그 항목만 추가하세요. 작성하지 않은 원본 템플릿을 보존하고 작업별 사본을 저장해 이전 결과가 다음 기본 답이 되지 않게 합니다.

이 원본 교육 템플릿에는 실행 권한이 없으며 계정을 바꾸지 않습니다. 읽을 수 있는 템플릿 여섯 개, 작성한 버그 보고와 인계, 찾은 모호한 조건 하나가 검증 결과입니다. 모델에 특정 문장을 요구하지 않습니다. 다음 [MCP 설정](article:codex-mcp)에서 연결 템플릿을 실제 읽기 전용 시험에 사용하세요.
