## What you will accomplish

> Install the appropriate desktop app, open an isolated practice folder, ask Codex to update a todo website and verify the result through a diff and a browser. Allow 15 minutes to read and 25 minutes for setup and practice. This lesson uses the official name as checked on 2026-09-14: the ChatGPT desktop app, with Codex selected inside it. Older screens or shortcuts may still say Codex.

The desktop app organizes tasks, files and outputs. The model interprets requests; a task holds the conversation and its working environment. Distinguishing these prevents confusing a model change with a change of folder. See [the Codex introduction](article:codex-beginner-guide) to compare entry points.

## Before you begin

Prepare an internet connection and a ChatGPT account with Codex access. Use [account and usage guidance](article:codex-account-usage) to check the workspace you are signed into. Plans, limits and model menus vary, so this lesson does not prescribe a fixed price or model. If the app is installed already, use its supported update method before checking the entry points below.

Download the [Small Steps practice package](https://mokaair.com/guides/codex-first-project/todo-practice.zip), extract it and copy expected into your own codex-practice folder. It contains five source files, fictional data, no login and no backend. This lesson changes only a heading and its styling. Use this copy before opening a production project. Previewing requires Python 3; data tests require Node.js.

### Keep an untouched copy first

After extracting expected, use your file manager to make two sibling folders: codex-practice for edits and codex-practice-before for comparison. Each must directly contain the five source files. Keep the backup outside the working folder, not in a child directory. Use File Explorer on Windows, Finder on macOS, or your Linux file manager.

The app's Git diff features may be unavailable before you create a Git repository. You can still compare matching files in a text editor. You do not need to commit or restore an entire repository for this exercise; continue to the [Git lesson](article:codex-git-basics) when you need version control.

## Step 1: install for your operating system

Windows: choose Windows on the [official ChatGPT download page](https://chatgpt.com/download/), complete the official installer and open ChatGPT from Start. If you use PowerShell, the Windows documentation also provides the following command. Open the app after installation finishes; if the shortcut is missing, check installation progress before downloading more copies.

```powershell Windows PowerShell; optional official installation method
winget install --id 9PLM9XGG6VKS -s msstore
```

macOS: choose macOS on the official download page, open the downloaded installer and follow its instructions to place the app in the indicated location. Open ChatGPT from Applications. If the system reports incompatibility, check the current requirements on the download page; disabling system protections will not make an unsupported version supported. Close the installer and confirm you are launching the installed app.

Linux: the desktop app is in preview. The documented distributions are Ubuntu 24.04/26.04 LTS, Debian 13 and Fedora 43/44, with x64 and ARM64 packages. Check your distribution and processor before downloading from the [official Linux installation page](https://learn.chatgpt.com/docs/linux/linux-app). Other distributions are outside this supported list; successfully installing a package does not establish full support.

```bash Linux terminal; identify the distribution and architecture
cat /etc/os-release
uname -m
```

Use .deb for Ubuntu/Debian and .rpm for Fedora. x86_64 means x64; aarch64 or arm64 means ARM64. Open a terminal in the download folder and run only the row matching your system. If the browser added a number to the filename, check the actual name first.

| System | Architecture | Installation command |
| --- | --- | --- |
| Ubuntu / Debian | x64 | sudo apt install ./chatgpt_amd64.deb |
| Ubuntu / Debian | ARM64 | sudo apt install ./chatgpt_arm64.deb |
| Fedora | x64 | sudo dnf install ./chatgpt.x86_64.rpm |
| Fedora | ARM64 | sudo dnf install ./chatgpt.aarch64.rpm |

Open ChatGPT from the application menu or run chatgpt in a terminal. Later updates use the distribution's package manager. Computer Use is not yet available in the Linux preview, and native Wayland has experimental limitations. You can still practice file edits and inspect the browser yourself. A macOS screenshot should not be presented as a Linux screen.

## Step 2: sign in and select the practice folder

On all three systems, sign in, verify the account and workspace, select Codex, then open a folder or create a project pointing to codex-practice. You should see index.html and the other files directly, rather than the ZIP or its parent directory. If asked to choose a local or other environment, select the location of your own practice copy.

Start a New chat and perform a read-only check first. Paste the following into the Codex task composer, not PowerShell or Terminal. This catches the wrong project, unextracted files or a task running on another host before it edits anything.

```text Codex desktop app, new task composer; verify the working location
Before editing, report the current working folder and list the exercise files.
Read index.html and explain how the page loads its JavaScript.
Do not change files. Tell me if the expected five files are missing.
```

Expect an actual folder path and an explanation of how app.js relates to core.mjs. Compare the path with your file manager instead of accepting “I understand the project.” If the app created a worktree copy, inspect that copy's location; see [Worktrees](article:codex-worktrees). This exercise can start without a Git repository.

## Step 3: request one verifiable change

```text The same Codex desktop task; complete request
Update this Small Steps practice website.
Change the main heading to "Small steps, clear progress."
Use a dark blue heading color with readable contrast on the existing background.
Keep the form labels, task data format, storage key and behavior unchanged.
Do not add dependencies or external services.
Show the changed files, explain the diff and report checks actually performed.
```

After the task responds, open index.html and style.css through its file or changes view. Check the heading string and color against the request, and look for unintended storage changes or removed labels. Added and removed lines in a diff are a comparison, not publication. For the first task, keep a scope you can verify rather than adding accounts, deployment and a database at once.

### Inspect files before the screen

| File | Check for this request |
| --- | --- |
| index.html | The main heading matches the requested text; other labels and text remain |
| style.css | Only necessary heading-color changes; contrast still needs visual inspection |
| app.js, core.mjs, core.test.mjs | Contents match the untouched copy; this request does not change data logic or tests |

If other files changed, ask for an explanation of each difference, then undo only changes outside this request. Do not overwrite the whole folder to hide the cause. “Only two files changed” also does not replace the functional checks that follow.

## Step 4: inspect the browser result

Open a terminal in the practice directory. On Windows, run the following. The server keeps that terminal busy; this is normal. Open a browser separately instead of launching the server again because the shell prompt did not return.

```powershell Windows PowerShell, codex-practice folder
py -m http.server 4173 --bind 127.0.0.1
```

```bash macOS / Linux terminal, codex-practice folder
python3 -m http.server 4173 --bind 127.0.0.1
```

Visit http://127.0.0.1:4173. Check the heading, add Read and Build, and complete Read. Active tasks should show only Build; Completed tasks should show only Read. Reload and confirm the data remains. A whitespace-only task must be rejected: verify this boundary case alongside the normal workflow.

Use responsive mode in browser developer tools at 390 and 1280 pixels, or narrow the window to check the small layout. Text, buttons and the form must not overflow horizontally. Tab should show a visible focus indicator. In another terminal in the same folder, run node --test core.test.mjs: the reference version should pass three tests. If Codex lacks a browser tool, perform visual verification yourself and record that the agent did not run it.

## Troubleshooting, stopping and restoring

No Codex option: check the app update, account and workspace, then account availability. Reinstalling repeatedly does not resolve usage limits or workspace policy. CLI is a separate entry point; installing the desktop app does not establish that a terminal can find the codex command.

Wrong folder: compare the task's absolute path and five files with your copy. If it points to a ZIP, empty directory or different project, stop editing and select the correct location. Inspect any changes already made at the original location; switching projects does not move files.

Blank page or inactive JavaScript: confirm the URL is http://127.0.0.1:4173 rather than a file URL from double-clicking HTML. Check the server terminal and browser Console. If the port is busy, stop your earlier server or choose another port. Browser storage is separate for different ports.

Stop the preview with Ctrl+C. Restore only the heading and styles changed in this exercise, preserving unrelated edits. Reset practice data clears this exercise's dedicated data, not its source code. Task completion, passing tests and a publicly deployed website are separate states.

Try asking for the form button to occupy its own full row on mobile while staying beside the input on desktop. Ask Codex to explain the existing CSS before editing. Verify both widths and the original data workflow. If the current styles already satisfy the request, accept that no change is necessary.
