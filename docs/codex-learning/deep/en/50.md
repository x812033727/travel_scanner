## Goal and preparation

> Narrow a plugin failure to one testable layer and repeat the same document request after a repair. Allow 15 minutes to read and 20 to practice. Prepare the fictional document in [Plugin setup](article:codex-plugins). Inspect your practice connection without changing a production workspace. Without an available plugin, you can complete the environment and error record, but cannot mark retrieval as successful.

## Step 1: Preserve the failure record

Record the date, OS, surface, version, full plugin name, source, sign-in method and failing step. Use the same record on Windows, macOS and Linux. Check the CLI version in a terminal and the desktop version in app information or its update screen. Desktop availability does not establish installation in the CLI on the same computer; record local and remote hosts separately. Enter your actual version rather than copying this article's research date.

```sh Terminal: check CLI version
codex --version
```

```markdown plugin-incident.md
# Plugin incident
Date and time zone:
OS / surface / version:
Local or remote host:
Plugin name and source:
Sign-in method (no secrets):
Failing step:
Exact error (redacted):
Practice document revision:
Change attempted:
Retest result:
```

Keep a shareable error message with email addresses, private document identifiers, tokens and cookies redacted. Authentication URLs may contain one-time codes and should not be copied into tutorials or support notes. Error type, time and reproduction steps are usually enough; use the provider's support process for server records. Change one condition at a time so a successful retest can be attributed to the account, new session or permission change.

## Step 2: Choose a layer by symptom

| Symptom | First check | Observable result |
| --- | --- | --- |
| No Plugins entry | Supported surface | Directory opens on a supported surface |
| Listed but cannot install | Source and workspace policy | Details or management restriction identified |
| Installed but no tools | Enabled state and new session | Capability selectable in a fresh task |
| Tool requests sign-in | External account connection | Correct account authenticated |
| Only one document fails | File access or URL | Same account opens original document |
| Old content in answer | Tool call and document revision | Fresh retrieval returns new marker |

This is a diagnostic order, not a guaranteed error-code mapping. A 401 often concerns authentication and a 403 often concerns denied access, but interpret the provider's response. Missing files, denied access and changed sharing may produce similar messages. For a 429 or temporary outage, record any retry guidance and later retry the same small document instead of repeatedly sending large requests. Do not make an entire drive public to make a read succeed.

## Step 3: Check surface, installation and enablement

On desktop, open Plugins and inspect Installed and the plugin details. In the CLI, start codex, enter /plugins and check the current marketplace and installed entry; Space toggles an installed plugin. Test a new task after installation or re-enabling because an existing task may retain its earlier capabilities. Preserve the old task's results without deleting it or clearing the entire Codex configuration folder.

```text Interactive Codex CLI slash command
/plugins
```

The IDE extension does not support Plugins, so a missing menu is not proof of a broken installation; test desktop or CLI. Chat/Work on iOS and Android can use plugins available on that surface, and Desktop only plugins cannot run on mobile. Linux desktop preview and individual plugins may have additional requirements. Record an unsupported surface rather than repeatedly reinstalling. See [Cross-device workflow](article:codex-cross-device-workflow).

## Step 4: Separate account and document access

Open the practice document on the provider's own site using the same external account as the plugin and check the title and Revision. Access in a browser logged into another account does not prove access for the plugin's account. Correct a mismatch through the provided reconnection flow, then request the same URL in a fresh task. If only that document is denied, check its sharing with the owner; grant only the necessary account access to your own practice file.

ChatGPT subscription sign-in differs from OpenAI API key sign-in; some plugins requiring OAuth are unavailable with API key authentication. Check plugin details and [Accounts](article:codex-account-usage). Do not put a service password in config.toml or use unrestricted approvals to solve OAuth. Host sandboxing governs local work, while the external service governs document access; relaxing one layer does not guarantee access through the other.

## Step 5: Retest with an actual tool result

```text New-task prompt: replace the practice URL
Use the selected plugin to read my practice document at <PRACTICE_DOCUMENT_URL>.
Return its title, source link, Revision, Document marker and task counts.
Use a fresh tool result. If access fails, report the tool error and stop.
Do not edit, share, move or delete anything. Do not infer missing contents.
```

Replace the angle-bracket placeholder with your practice document URL and select the plugin or capability using the supported picker. Inspect tool activity rather than only the sentence 'I read it.' Compare the returned title, source, current Revision, Document marker and counts with the provider's original. If no tool ran, check capability availability. If a tool returned a denial, preserve that error instead of allowing an answer reconstructed from earlier conversation.

Next, manually change the document's Revision and one verifiable count on the provider site without telling Codex the new count. Run the same prompt in another fresh task. If the result is stale, check for a copied-document URL, unsaved edits and a supported refresh or reread option, then record the delay. A correct second answer establishes this case, not a repair for every document and surface.

## Common failures and recovery

If Uninstall is absent, check whether the plugin is workspace-installed or a default managed by an administrator and record the restriction. Uninstalling removes that environment's bundle; separately connected MCP integrations can remain. To close the exercise, check both Installed and external connection management, revoking your practice authorization if needed. Preserve shared connections and do not equate one disconnection with disabling every device.

Use the incident record to restore the single condition you changed: enable a paused plugin, reconnect the intended practice account or restore the document's access. If a fresh task still fails after reconnection, provide the maintainer with the surface, plugin source, redacted error, one attempted fix, expected and actual result. Avoid endless reinstalls. Continue with [MCP troubleshooting](article:codex-mcp-troubleshooting) for server configuration, keeping plugin-directory issues separate from custom-server files.

## Acceptance and next step

Completion means a reproducible record: original failure, identified layer, one change, a fresh tool result for the same document, no tool writes to the original, and the practice connection's retained or revoked state. Without a tool result, record a surface restriction or pending authentication rather than success. Product operations here are documented from official sources, not claimed as tested on your account, OAuth flow or physical phone; article-rendering tests do not prove a plugin connection.

Keep this record separate from [Skill acceptance](article:codex-skill-testing): loading a skill does not establish connection to its backing service. Reuse the fields from [Templates and cheatsheets](article:codex-templates-cheatsheet), updating observed values while retaining dates and unreproduced cases.
