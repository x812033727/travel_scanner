## What you will accomplish

> Complete a verifiable CLI loop: prepare a file, check installation and sign-in, read the correct directory, change one specified line, exit and find the original session. Allow 12 minutes to read and 25 minutes to practice, plus download and sign-in time. GitHub, Node.js and paid external tools are unnecessary for this exercise.

The CLI is a terminal interface to Codex. Your shell starts programs; the Codex composer accepts tasks. Both use text, but interpret it differently. Complete [terminal and path basics](article:codex-terminal-paths) until you can identify the current folder. Diagram 01 represents preflight checks, 02 the session and 03 file verification.

## Before you start: choose one installation method

Use a practice folder writable by your ordinary user account, separate from production work. Check [account and usage basics](article:codex-account-usage) for access, authentication and usage information. Starting the program does not establish available account usage; signing in does not grant access to every target directory.

| Environment | Installation route | Return here after |
| --- | --- | --- |
| Windows | Official standalone PowerShell installer; npm is an option if present | Checking the version in native PowerShell |
| macOS | Official standalone installer; Homebrew cask for existing Homebrew users | Checking the version in Terminal |
| Linux / WSL2 | Official standalone installer in the Linux shell | Checking the version in that same Linux environment |

Follow the separate [Windows](article:codex-cli-windows), [macOS](article:codex-cli-macos) or [Linux / WSL](article:codex-cli-linux-wsl) instructions. These are alternative routes, not three required installations. If a lesson is not yet public, use the official CLI setup page linked below, select your platform, finish installation and reopen the terminal. Then perform these checks. Avoid installing every distribution just to compare the methods.

```text
codex --version
codex --help
```

Run these in the operating-system shell. Expect a version and help text, followed by the shell prompt; no model task has started. If codex is not found, resolve installation before attempting login. Your version may be newer. Compare its help with the official reference rather than installing the preview build used for this article's checks.

## Step 1: prepare an identifiable practice file

Create greeting.txt in a plain-text editor with the content below, then save a second copy as greeting.original.txt. Place both in a new codex-cli-lab folder. Check for accidental .txt.txt extensions and avoid word-processing formats. The second line is a fixed marker that identifies your exercise file; the copy preserves the original for comparison.

```text
Hello, traveler.
Lesson marker: CLI-START-01
```

On Windows, open the folder in File Explorer, choose Open in Terminal with PowerShell, and run Get-Location and Get-ChildItem. On macOS or Linux, enter cd followed by the folder's full quoted path, then pwd and ls. Both files must appear. If you are still in the home or downloads directory, navigate before proceeding; a familiar filename alone is insufficient evidence.

## Step 2: sign in and start a read-only session

```text
codex login
codex login status
codex --sandbox read-only
```

Run each line in the shell only after the previous one completes. Follow login's browser flow and choose the intended account and workspace. login status checks for credentials; it does not prove available usage, connectivity or successful model requests. The last line opens the interactive interface with a read-only sandbox. If folder-trust or sandbox setup appears, verify the path and explanation before choosing settings for this exercise.

Execute /status below only inside the Codex composer. Inspect the working directory, model and permission information shown by your version. Do not paste it into PowerShell. Read-only describes the sandbox policy, not a blanket guarantee that all network or external tools are disabled; those have their own controls. This exercise uses local text files only.

```text
/status
```

```text
Read greeting.txt in the current folder. Report the working directory and both lines exactly. Do not edit files, use external services, or infer missing content. If the file is missing, stop and report that.
```

This is a natural-language task for the Codex conversation. A passing response matches both original lines and the current directory. Inspect the file-reading tool record as evidence that it actually read the file. If the file is missing, stop before requesting edits. If the file exists but sandbox access fails, record the error and scope, then consult [permissions](article:codex-permissions).

## Step 3: change only the specified line

Enter /exit in Codex. Once the shell prompt returns, start the following writable session from the same practice folder. Separating reading from writing makes the permission change visible; a one-line edit does not require unrestricted disk access. If organizational policy disallows this mode, retain the read-only result and check the managed configuration.

```text
codex --sandbox workspace-write --ask-for-approval on-request
```

```text
In greeting.txt, replace only the first line with: Hello, Codex learner.
Preserve the lesson marker and greeting.original.txt. Do not create other project files.
Read the file after editing and report the exact before/after change.
```

The first block starts the program; the second is the request inside Codex. Review proposed commands and changes. If the backup changes or extra project files appear, identify the scope violation, request a correction and read again. Success means the first line is Hello, Codex learner., the marker is unchanged and the backup is intact. A completion message alone is insufficient.

## Step 4: exit, verify and resume

Exit again and independently compare both files in your editor. Add a missing-file test: ask Codex to read greeting-missing.txt and explicitly report absence without creating it. Expect a clear missing-file result while both existing files remain unchanged. This distinguishes inspection from guessing content based on a filename.

After exiting, run codex resume in the shell. Identify this session by time, content and directory rather than assuming it is the most recent. Ask for a summary of changes and remaining work, then reread greeting.txt. Resuming a conversation does not restore disk files to their former state. External edits must be checked against the current files.

```text
codex resume
```

To repeat the exercise, exit and copy the two original lines back into greeting.txt, then confirm equality. Restore just the practice file; there is no need to delete Codex configuration or all sessions. Update through the installation channel you chose and verify the version in a fresh terminal. Check for duplicate installations when changing channels later.

## Troubleshooting and completion check

Command missing: verify the shell, reopen it and use your platform's PATH checks. Browser login complete but CLI waiting: confirm the same login attempt and local return flow; keep login URLs and codes out of public posts. Signed in but unable to submit: distinguish usage, organization policy and network errors. Editing blocked: check whether this is still the read-only session before reinstalling anything.

Keep the version record, correct directory and read evidence, the one-line change, intact backup, missing-file report and resumable session. Continue with [commands](article:codex-commands) and [AGENTS.md](article:codex-agents-md) to add project rules. Local Windows checks cover version/help and exercise-file comparisons. Installation, account and interactive model steps are documentation-verified; macOS and Linux are not claimed as hands-on tests.
