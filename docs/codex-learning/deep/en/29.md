## Goal and preparation

> Create a traceable recurring check of a fictional local list and verify timing, results, edits and pause. Allow 15 minutes to read and 20 to practice, excluding waiting for a scheduled trigger. Use an account and desktop surface offering Scheduled, after [Task management](article:codex-project-management). Prompts here are exercises, not evidence that the author created a schedule on your account.

## Step 1: Choose the execution location

Local files need a desktop host that can access them, with the computer on, app running and folder available. On Windows, macOS and Linux, check whether the installed desktop version offers Scheduled; record missing preview support as unavailable. CLI and IDE have no Scheduled management UI, though they can prepare scripts/prompts before management on a supported desktop or web surface.

| Need | Choice | Environment to check |
| --- | --- | --- |
| Continue tracking in one task | In-chat schedule | Existing context and accessible data |
| Independent report each time | Standalone schedule | Saved prompt and selected project |
| Read local practice files | Desktop host | Power, app and folder |
| Read uploads/connected data | Supported web/mobile surface | Plan, tools and source permissions |

A web schedule does not acquire access to a computer folder; this exercise uses a desktop schedule returning to the same task.

## Step 2: Run an ordinary task first

Create daily-check.md with the content below in an empty practice-schedule folder, save UTF-8 plain text and open that folder as a desktop project. The filename daily does not cause daily execution; the schedule controls whether and when it runs. This fixture contains no client data, credentials or production paths.

```markdown practice-schedule/daily-check.md
# Practice check
Revision: 1
- [x] Read the task instructions
- [ ] Review the practice report
```

```text Ordinary task composer: validate one manual read first
Read daily-check.md from this practice project once now.
Report its Revision, completed count and open count, using the current file contents.
If the file is missing or unreadable, report that exact limitation and stop.
Do not edit files, create a schedule, send messages elsewhere or call external services.
```

Expect Revision 1, completed 1 and open 1, with actual file-read activity. Record the source path/result and verify no file change. Resolve path or permission failures in the ordinary task before scheduling. This tests the action only, not scheduling, the unattended environment or notifications.

## Step 3: Create a traceable natural-language schedule

```text Desktop task: submit when this is the practice schedule you intend to create
Create one recurring check named 'Practice list review' in this existing task.
Run every Monday at 09:00 in the Asia/Taipei time zone.
On each run, reread daily-check.md from this local practice project.
Report the current Revision, completed and open counts. Do not rely on an earlier report.
If the file or required access is unavailable, stop the run and report the limitation.
Keep the source file unchanged and do not contact external services.
Notify me on the first result, meaningful changes or failures; stay quiet when nothing changes.
Show the saved schedule and next run time so I can verify them.
```

Open Scheduled and locate Practice list review. Confirm a saved Active entry, correct time/time zone and the intended practice project/task. A conversational promise is not creation evidence; inspect the stored entry and next run. If created after Monday 09:00, the next occurrence may be next week, so use the displayed calculation instead of assuming it runs today.

Use a Run now action when offered, or save a near-future time you can observe and wait for the actual trigger. Avoid creating another same-name schedule for testing. Record its identity, next occurrence and recent run, distinguishing saved, started, finished and produced-a-result states.

## Step 4: Verify a fresh source read each run

The first scheduled result should match 1/1. Manually change Revision to 2 and check the second item, yielding completed 2/open 0. Do not place the new counts in the saved prompt. Trigger or await the next run and verify it reads the new values from the file, detecting reuse of old summaries rather than repetition of an answer you supplied.

Run the unchanged state again and verify quiet-on-no-change behavior while checking run status in Scheduled. No push notification does not necessarily mean no execution; inspect OS notifications, app notifications and schedule reporting separately. If you want every weekly report even when unchanged, request that explicitly rather than asking both always-notify and silence-on-no-change.

## Step 5: Edit, pause and understand stopping

```text Same parent task: update the existing schedule
Update the existing 'Practice list review' schedule to Wednesday at 10:00 Asia/Taipei.
Keep its task, project, read-only prompt and notification preference unchanged.
Show the updated next run time. Do not create a second schedule.
```

Verify the same entry now has the new time and no duplicate Active task was created. Disambiguate duplicate names by project, prompt and identity. For changes to source/action, manually test the revised prompt before updating. A day/time-only change does not require unrelated functional retesting.

```text End the exercise: pause the same schedule
Pause the existing 'Practice list review' schedule after this practice.
Confirm it is Paused and show whether any run is already in progress.
If a run is in progress, report its state before stopping anything else.
```

Confirm Paused in Scheduled. Pausing future triggers may not cancel an already started run, so inspect it separately. If the schedule is no longer needed, use its delete/remove action and verify it disappears. Existing reports, external changes and other schedules are not automatically reversed. Resume the same entry and inspect its next occurrence instead of creating a replacement under another name.

## Common failures and a negative case

For a missing run, check Active/Paused, time zone and next occurrence, then host power, app and project availability. Do not assume missed runs during sleep are caught up; inspect actual history. For file access failures, verify path and [Permissions](article:codex-permissions). Unattended actions requiring fresh authorization can fail and should report the step rather than treating background execution as blanket permission.

Pause the schedule, temporarily rename your file to daily-check.saved.md, verify the original name is absent and manually test the same read. Expect a missing-file report, not the earlier 2/0 or an empty-list assumption. Restore the name and verify Revision 2. This proves the prompt's missing-file branch only; without a background run it does not prove background failure notification.

Record source, time zone, saved entry, one real scheduled result, fresh reading after change, edited time and Paused state. Mark partial completion if unsupported or no trigger has occurred. Event triggers have separate plan/surface limits; desktop timing is not Gmail/Slack event monitoring. The flow is documented from official sources without creating reader schedules or claiming all-platform tests. Continue to [codex exec](article:codex-exec-scripting).
