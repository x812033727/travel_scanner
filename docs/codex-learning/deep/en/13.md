## Goal and preparation

> Manage two distinct outcomes in one local project: name, switch, pin, archive and restore tasks, while verifying that separate list entries do not isolate files. Allow 12 minutes to read and 20 to practice. Use authenticated desktop and a text editor. The same lab applies to all desktop platforms; controls are documentation-checked, not claimed tested on every OS.

Complete [desktop basics](article:codex-desktop-getting-started). A project organizes shared files and tasks; each task has its own outcome and conversation. Use “Inventory the lab” and “Propose the edit” rather than naming everything “continue.” A ChatGPT project differs from a local project linked to a computer folder; verify that this exercise uses the latter.

## Step 1: Attach the practice folder

Create codex-project-lab with separate note.txt and request.txt samples below. Add it as a local project using desktop basics, then verify folders in the project's Edit project menu. Attach only this lab, not your entire user directory. Use it as the primary folder and check the actual path before starting a task.


The primary folder sets the starting location and default discovery for some project settings. Additional folders may also be readable/writable; they are not isolated copies. This lab has no Git or worktree, making shared files explicit. For concurrent code edits, use [worktrees](article:codex-worktrees) rather than assuming separate task entries are isolation.

## Step 2: Create two tasks with distinct outcomes

Start the first task in this project and send the inventory prompt. Verify both files, PROJECT-LAB and revision 1, then rename it “PROJECT-LAB — Inventory.” Use the task menu to retain a shared marker plus outcome, making it searchable even when you remember only PROJECT-LAB. This task is read-only and needs no new document.

```text
Inventory this practice folder. Read note.txt and request.txt. Report their filenames, the lab marker, revision and current title. Do not edit files or search other directories. This task's outcome is a verified inventory only.
```

Create another new task in the same project with the proposal prompt and name it “PROJECT-LAB — Title proposal.” Expect Small Steps to Daily Steps and only note.txt's title line as the proposed edit, without implementation yet. Switching back to Inventory should retain that task's conversation rather than merging both transcripts.

```text
Read note.txt and request.txt. Propose the smallest title change that satisfies the request. Identify exactly which line would change and how to verify it. Do not implement yet; this task's outcome is a reviewable proposal.
```

## Step 3: Reread files when switching tasks

Simulate work between tasks: manually change only note.txt's Revision to 2, leaving the title Small Steps and request.txt unchanged. In Inventory, send the fresh-read request. Old conversation says 1 while disk now says 2. Ask the proposal task to reread too; both should observe 2 in the same folder.

```text
Read note.txt from disk again now. Compare its current revision with this task's earlier record. Report the actual directory, current revision and unchanged title. Do not repair the mismatch by restoring old contents.
```

The mismatch is intentional, not a request to revert it. Tasks can share files while retaining separate conversations; pinning, renaming and switching do not create another disk copy. If one still says 1, verify path, host and fresh reading, then possible worktree differences. Preserve such revision changes in a [handoff](article:codex-context-handoff) for long work.

## Step 4: Pin, find, archive and restore

Pin the frequently used Title proposal task and check that it remains easy to find after opening another task. Pinning should not change its transcript or files. Use sidebar Search chats for PROJECT-LAB, then distinguish by full title. Use the visible search entry because shortcuts vary by version.

Archive only the Inventory task through its menu after finishing it; avoid the project's bulk Archive chats action. Restore it from Settings → Archived chats and verify its transcript and note.txt revision 2 remain. Archiving organizes lists; it is not feature acceptance, backup or disk cleanup. Delete is unnecessary here.

## When to resume, start fresh or stop

Continue the existing proposal when refining that same title change. Start a fresh task for a distinct outcome such as organizing test evidence, naming the files to read. Do not assume it has read verbal constraints from another conversation. Put durable rules such as unchanged tests in project AGENTS.md, current revisions and pending checks in a handoff, and reference them explicitly.

For running work, first use its visible stop control, verify no more edits are produced, then organize or archive. Stop and archive are distinct. Existing edits are not automatically undone, so reread and inspect changes. Before changing the primary folder, record the old path and verify the new starting location in a fresh task; do not assume existing tasks moved or attached folders are backups.

## Troubleshooting and organizational habits

For a missing task, check another project, host or archive, then search its marker; do not create many duplicates. If both tasks want to edit the same file, keep one read-only while the other makes the change, then let the first review. For genuinely concurrent features, use the worktree and integration lessons.

As work grows, name tasks by outcome and scope, such as “Filters: complete Completed” or “Docs: startup steps.” End each with changes, verification and remaining work. Keep unfinished work in a task-list document as well as chat, so switching does not require retelling the whole project or equating archived with nothing pending.
