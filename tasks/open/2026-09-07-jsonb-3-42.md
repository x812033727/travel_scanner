# 防 jsonb 運算子的測試只守住 3 張表，實際有 42 張

## Why

`apps/api/tests/test_migration_sql_dialect.py` 的存在理由寫在它自己的 docstring 裡：
2026-09-06 有一支 migration 對 PostgreSQL 的 `json` 欄位用了 `jsonb` 才有的運算子，
整個部署因此回滾。這支測試就是為了讓那件事不再發生。

但它靠一份手寫的 `JSON_COLUMNS` 白名單決定要掃哪些欄位，而那份名單只有三張表：

```python
JSON_COLUMNS = {
    "trip_plans": ("data",),
    "trip_plan_items": ("data",),
    "provider_configs": ("config",),
}
```

用 AST 走過 `apps/api/app/models.py` 的結果是 **42 張表、69 個 `JSON` 欄位**。
也就是說這道閘門實際覆蓋 3/42，其餘 39 張表寫錯了不會有人擋。

這不是假設性的。2026-09-07 上線的 `0052_repair_trend_merchant_names` 就寫了
`food_merchants.names_json`——正是沒被守住的欄位之一。那支 migration 剛好寫對了
（用 `CAST(:names AS json)` 與 `names_json::text`，作者還留了註解說明為什麼），
所以沒出事，但**測試不是靠它才通過的，是靠它根本沒被檢查**。

名單會過期是必然的：每加一張帶 `JSON` 欄位的新表，白名單就再落後一格，
而落後的方式是「安靜地少檢查一個」，不是紅燈。

## Definition of done

- [ ] 新增一支帶 `jsonb` 運算子、針對名單外欄位（例如 `food_merchants.names_json`）的假 migration 時，測試會紅。
- [ ] 之後新增帶 `JSON` 欄位的資料表，不需要有人記得回來改這份名單。
- [ ] 既有 52 支 migration 全部通過，沒有為了讓測試過而放寬規則。

## Steps

- [ ] 把 `JSON_COLUMNS` 改成從 `apps/api/app/models.py` 推導，不要手寫。
      走 AST 找 `mapped_column(JSON, ...)` 的 `AnnAssign`，配上該 class 的 `__tablename__`；
      別用 regex，很多宣告是跨行的（我第一次就是這樣只找到 1 個欄位而不是 69 個）。
      另一條路是走 SQLAlchemy metadata 讀 `Table.columns` 的型別，更準但要 import 整個 models。
- [ ] 保留一個「名單不得為空且至少涵蓋 40 張表」的自我檢查，否則推導壞掉時測試會安靜地變成永遠通過——
      那正是現在這個 bug 的形狀。
- [ ] 順手補 `0052_repair_trend_merchant_names` 的測試案例。
      它是這系列唯一沒有測試的資料修復 migration：0042、0043、0044、0045、0046、0048
      都在 `test_migration_dead_branches.py` 有案例，0047 與 0050 有自己的檔案。
      （這條超出目前 scope，要做的話先把 `apps/api/tests/test_migration_dead_branches.py` 加進 scope。）

## How to verify

```bash
cd apps/api && uv run pytest tests/test_migration_sql_dialect.py -v
```

再手動造一個反例確認閘門真的會擋：在任一 migration 暫時加一行
`op.execute("UPDATE food_merchants SET names_json = names_json || '{}'::jsonb")`，
跑上面的指令應該要紅，然後把那行刪掉。

## Notes

- `json` 與 `jsonb` 的差別在這個 repo 咬過人，見 [[travel-scanner-migration-pitfalls]] 那則記憶：
  `provider_configs.config` 是 `json`，用 `jsonb_set` 會在部署當下才爆。
- 這是 2026-09-07 部署後稽核 165 個 commit（含 0050/0051/0052）時發現的。
  那次稽核零個阻斷問題，這是唯一一個「已經上線、但防護網有洞」的結構性發現。
- 數字是用 AST 走 `models.py` 算的，不是估的：42 張表、69 個欄位、白名單 3 張表。
