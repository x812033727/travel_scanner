# 撤回：對比度不足的發現來自量測程式的解析錯誤

## 這張任務是錯的，不要照著做

原始主張是「底部主導覽標籤 3.62:1、3.30:1，Logo 2.65:1，『經典摩卡』1.38:1，全站 766 處未達 WCAG AA」。

**全部是假的。** 用修正後的量測程式重跑，同樣的元素實際數值是：

| 元素 | 原報告 | 實際 | 標準 |
| --- | --- | --- | --- |
| 「收藏」「我的旅程」「我的」（手機底部列） | 3.62:1 | **5.60:1** | 4.5 ✓ |
| 同上（桌面頁首） | 3.62:1 | **5.14:1** | 4.5 ✓ |
| 「探索」（作用中） | 3.30:1 | **5.51:1** | 4.5 ✓ |
| Logo「Moka」 | 2.65:1 | **7.02:1** | 3 ✓ |
| 「經典摩卡」 | 1.38:1 | **13.17:1** | 4.5 ✓ |

八條代表性路由重掃，淺色與深色**都是 0 處未達標**。

## 成因

量測程式的顏色解析只處理 `rgb()` / `rgba()`。但這個專案的背景色大量使用 `color-mix()`，瀏覽器回傳的是 **`color(srgb 1 0.988235 0.972549 / 0.92)`** 格式——分量是 **0–1** 範圍。解析器把 `1`、`0.988` 當成 0–255 的值又除了一次 255，於是把近白的背景算成近黑，比值自然全錯。

這也解釋了報告裡「深色模式把對比從 43 降到 0」那個看似漂亮的對照：**深色配色用的是純 `rgb()`，解析器碰巧算對；淺色用 `color-mix`，全部算錯。** 那不是設計發現，是同一個 bug 的兩面。

修正後的解析要做兩件事：認得 `color(srgb …)` 的 0–1 分量，以及由外往內把半透明背景真正合成起來，而不是取第一個非透明祖先就當作背景。

## 對其他發現的影響

只有對比度這一項用到顏色解析。其餘量測不受影響，仍然成立：

- 觸控目標尺寸 —— `getBoundingClientRect()`
- 文字截斷 —— `scrollWidth` / `clientWidth`
- 被固定列遮住 —— 矩形相交
- 橫向溢位 —— `scrollWidth`
- 圖片失效 —— `naturalWidth`

## 給下一個人

若要為這個專案加對比度的自動化檢查，**不要自己寫顏色解析**。用現成的函式庫，或至少先對 `color-mix()` 產生的值寫測試——這個專案的 token 系統大量依賴它。
