# apps/web 的文案目錄

## 目錄長什麼樣

| 東西 | 在哪裡 |
| --- | --- |
| 語系 | `en`、`ja`、`ko`、`zh-TW`、`zh-CN`（`apps/web/i18n/routing.ts`；預設 `zh-TW`，網址一律帶語系前綴） |
| 目錄檔 | `apps/web/messages/<locale>/<namespace>.json`，每個語系 25 個 namespace（2026-09-25 數過；`docs/ui-text-overrides.md` 寫的 22 已經過時） |
| 載入 | `apps/web/i18n/request.ts` 的 `namespaces` 陣列，每次 render 動態 import 該語系的每個檔，再疊上後台覆寫 |
| 基準語系 | `en`。`tools/check-i18n.mjs` 拿每個語系跟 `en` 比，不是跟 zh-TW 比 |
| 元件測試用的目錄 | `apps/web/vitest.setup.tsx` 只 import **zh-TW** 的檔，自己做一個簡化的 `useTranslations`／`getTranslations` mock |

元件用 `useTranslations("<namespace>")`（client）或 `getTranslations("<namespace>")`（server），鍵是巢狀 JSON 的點號路徑。

## 加一個鍵

1. 在**五個**語系的同一個 namespace、同一個巢狀位置加同名鍵。先寫 `en`（它是基準），再寫 `zh-TW`（元件測試斷言的是它），最後 `ja`、`ko`、`zh-CN`。
2. 參數用 `{name}`，每個語系的參數名集合要完全一樣。**參數名不要翻譯**（`{count}` 不能變成 `{件数}`）。
3. 複數與 select 只在需要的語系寫 ICU：英文 `{count, plural, one {# merchant} other {# merchants}}`，中日韓通常直接 `{count} 家`。分支內容**用 `#` 開頭**：檢查器的參數抽取式是 `\{([A-Za-z_][\w]*)`，`one {one merchant}` 會被當成一個叫 `one` 的參數，和其他語系對不上。
4. 單元測試的 mock 只做 `{name}` 的字串替換，不懂 ICU plural；要斷言複數句的元件測試會看到原樣的 ICU。zh-TW 句子寫成不需要 plural 的形式就沒這個問題。
5. 跑 `npm run check:i18n`。要看缺了哪些鍵，跑 `node .agents/skills/web-i18n-e2e/scripts/i18n-diff.mjs <namespace>`。

改既有句子：只改文字、不改參數集合，五個語系可以分次改（檢查器只比鍵與參數，不比內容）。刪鍵要五個語系一起刪。

## 加一個 namespace（七處，漏一處就紅或靜靜壞掉）

| # | 改什麼 | 漏了會怎樣 |
| --- | --- | --- |
| 1 | 五個語系各一個 `apps/web/messages/<locale>/<ns>.json` | check:i18n：`<locale>: namespace files differ from en` |
| 2 | `apps/web/i18n/request.ts` 的 `namespaces` 陣列 | **沒有檢查會抓**：頁面上顯示原始鍵路徑 |
| 3 | `apps/web/vitest.setup.tsx`：import zh-TW 的檔並放進 `catalogs` | 元件測試拿到鍵路徑而不是中文，斷言紅 |
| 4 | `apps/web/lib/ui-text.ts` 的 `EDITABLE_NAMESPACES` | check:i18n：allowlist differs |
| 5 | `apps/api/app/ui_text/schemas.py` 的 `UI_TEXT_NAMESPACES` | check:i18n：allowlist differs；後台無法編輯 |
| 6 | 五個語系 `admin.json` 的 `uiText.namespaces.<ns>`（編輯器下拉選單的名稱） | check:i18n：`uiText.namespaces does not describe every editable namespace` |
| 7 | `apps/api/tests/test_ui_text.py` 斷言 `len(UI_TEXT_NAMESPACES)` 是固定數字 | api 的 pytest 紅 |

`legacy` 是例外：它餵 `apps/web/components/legacy-ui-localizer.tsx`（用 zh-TW 字面字串改寫 DOM），不可編輯，不進第 4–6 處。新文字不要放進 `legacy`。

## 另一種目錄：`lib/*-messages/` 與 `*-copy.ts`

有些後台與功能頁的文字不在 `messages/`，而是 `apps/web/lib/<feature>-messages/<locale>.json` 加一支 `apps/web/lib/<feature>-copy.ts`（例如 `admin-news-copy.ts`、`stay22-copy.ts`、`itinerary-copy.ts`）。它們：

- 不經過 next-intl，由 copy 模組依語系挑檔，`{name}` 用模組自己的替換函式，不是 ICU；
- **不受 check:i18n 檢查**，鍵的一致靠 TypeScript（`Record<string, typeof en>`，`npm run typecheck:web` 會抓缺鍵），參數一致沒人檢查；
- 不能從後台覆寫。

跟著所在功能既有的做法走：功能已經用 copy 模組就加在那裡，否則放 `messages/`。要讓站主能在後台改的文字，一定放 `messages/`。

## 後台文案覆寫疊在目錄上

完整規格在 `docs/ui-text-overrides.md`。寫程式時要記住的：

- JSON 目錄是預設值，資料庫 `ui_text_overrides` 只存站主改過的句子（每個 namespace＋鍵＋語系一列）。`apps/web/i18n/request.ts` 每次 render 讀 `GET /api/v1/runtime/ui-text?locale=`，用 `applyUiTextOverrides`（`apps/web/lib/ui-text.ts`）做 copy-on-write 合併。
- 合併**不會新增鍵**：覆寫的鍵已不在目錄、或參數集合跟目前預設不同，就跳過，在 `/admin/ui-text` 列為孤兒。所以**改鍵名或改參數，會讓站主既有的覆寫失效**；PR 說明要寫出來，讓站主去後台重做。
- 改一句預設文字不會蓋掉站主的覆寫。站主覆寫過的句子，改 JSON 在正式站看不到變化，這不是 bug。
- API 取不到覆寫時退回純目錄（fail open）；e2e 的假 API 回空的 `entries`，所以 e2e 看到的永遠是 JSON 原文。
- 參數規則三方一致：API、`ui-text.ts` 的合併、`tools/check-i18n.mjs` 用同一個抽取式，`apps/web/lib/ui-text.test.ts` 釘住這件事。改其中一邊的正規式要三邊一起改。

## 不在這裡處理的文字

- API 回來的錯誤訊息、`apps/web/lib/api.ts` 裡的字典、BFF 自己寫的 problem 字串：不在目錄裡，也不能覆寫。
- 文章內容（內容包的 locale 檔）：走 skill `content-pipeline` 與 `article-localization`。
